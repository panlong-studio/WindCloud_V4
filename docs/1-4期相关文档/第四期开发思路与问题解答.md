# 第四期开发思路与问题解答

## 1. 阅读结论

我先基于当前仓库代码和以下文档做了交叉阅读：

- `docs/项目概述.md`
- `docs/数据库netdisk_db说明.md`
- `docs/1-3期相关文档/V3整体项目架构详解.md`
- `src/client/*.c`
- `src/server/*.c`
- `include/*.h`

当前 V3 的真实架构，不是“命令级线程池”，而是：

1. 服务端主线程只负责 `accept` 新连接。
2. 新连接进入线程池队列。
3. 某个工作线程取出这个连接后，会一直在 `handle_request()` 里阻塞循环处理这个连接，直到客户端断开。
4. 也就是说，当前线程池是“一个线程长期服务一个连接”的模型。

客户端当前也只有一条控制连接：

1. 主线程读标准输入。
2. `process_command()` 直接在主线程里发命令。
3. `puts/gets` 在主线程里完整执行。
4. 所以上传/下载期间，客户端主线程会被阻塞，不能继续做别的交互。

这两个点决定了：**第四期不能只在客户端随手加一个线程池就完事，必须连协议、连接模型、会话模型一起改。**

## 2. 先回答你的三个核心疑惑

## 2.1 长短命令分离，你现在的理解对不对？

你的理解方向是对的，但还差一个很关键的点：

> 不是“只要客户端把长命令放到子线程里”就完成了，而是“长命令必须和短命令分离到不同连接上”才真正成立。

### 为什么只加客户端线程还不够？

因为当前客户端所有命令都走同一个 `sock_fd`。

如果你让：

- 主线程继续在这个 `sock_fd` 上发 `cd`、`ls`
- 子线程同时也在这个 `sock_fd` 上发 `puts`、`gets`

就会马上出现两个问题：

1. **协议串包**
   - 主线程和子线程同时往一个 socket 写数据，包顺序容易交错。
   - 服务端也分不清当前收到的是哪个命令链路里的包。
2. **服务端仍然是单线程处理该连接**
   - 当前服务端一个工作线程会一直卡在某个连接的 `handle_request()` 里。
   - 即使客户端开了子线程，只要还是同一个连接，服务端仍然不会并行处理这个连接上的长短命令。

所以，第四期里真正合理的模型不是：

- 一个连接
- 多个线程共用这个连接

而是：

- 一条“控制连接”处理短命令
- 一条或多条“传输连接”处理上传/下载

### 客户端能不能加线程池？

可以，但**不建议第一版就上线程池**。

对于当前这个学习项目，更简单直观的做法是：

1. 客户端主线程保留一条长期存在的控制连接。
2. 用户输入 `puts/gets` 时：
   - 主线程创建一个传输任务
   - 启动一个子线程
   - 子线程自己新建一条传输连接去和服务端传文件
3. 文件传完后，这个子线程退出

这样做的优点：

1. 代码直观。
2. 容易调试。
3. 不会引入“线程池队列 + 多任务调度 + 生命周期管理”的额外复杂度。

### 那什么时候再考虑客户端线程池？

当你要支持下面这些能力时，再考虑线程池更合适：

- 同一个客户端同时下载多个文件
- 同一个客户端同时上传多个文件
- 需要限制最大并发传输数，比如最多同时 2 个或 4 个

所以我的建议是：

**第四期第一版：先不要做客户端线程池，先做“主线程 + 每个传输任务一个子线程 + 每个传输任务一条新连接”。**

这是最适合 C 新手学习项目的方案。

## 2.2 JWT 的意义是什么？它和当前 `ClientContext` 冲突吗？

### 先说结论

1. **JWT 不和 `ClientContext` 冲突。**
2. **JWT 不是拿来替代 `ClientContext` 的。**
3. **JWT 在这个项目里的核心意义，是为“新开的传输连接”提供用户身份凭证。**

### 当前 `ClientContext` 是干什么的？

当前 `ClientContext` 保存的是：

- `user_id`
- `current_path`
- `current_dir_id`

它的本质是：

> 当前这个 TCP 连接，在服务端内存里的“会话上下文”

它只对“这一个连接”有效。

也就是说：

- 连接不断开，`ClientContext` 就一直在
- 连接一断，`ClientContext` 就没了

### JWT 是干什么的？

JWT 的本质是：

> 服务端签发给客户端的一张“可验证的身份凭证”

客户端以后再发请求时，把这张凭证带上，服务端就能知道：

- 这是谁
- 令牌有没有过期
- 令牌有没有被篡改

### 为什么当前项目到了第四期才需要 JWT？

因为 V3 基本还是“单连接模型”。

在单连接模型下：

- 用户登录后
- 服务端直接把 `user_id` 放在这个连接对应的 `ClientContext` 里

这就够用了。

但是第四期一旦做“长短命令分离”，情况就变了：

1. 用户主线程先用控制连接登录。
2. 随后客户端子线程又新开一条传输连接。
3. 这条新连接到达服务端后，并没有原来控制连接的 `ClientContext`。

这时服务端必须回答：

> 这条新来的传输连接，到底属于哪个用户？

这就是 JWT 的用武之地。

### JWT 在当前项目里的具体作用

在这个项目里，JWT 的实际作用应该理解为：

1. 用户登录成功后，服务端签发 JWT 给客户端。
2. 客户端保存这个 JWT。
3. 以后客户端如果新建传输连接，就把 JWT 一起带过去。
4. 服务端校验 JWT，解析出 `user_id`。
5. 于是这个传输线程即使没有原控制连接的 `ClientContext`，也依然知道“自己在为哪个用户服务”。

所以，JWT 在当前项目里的核心价值不是“分布式”这类大词，而是：

> **让不同连接、不同线程处理请求时，服务端仍然能可靠识别用户身份。**

### `ClientContext` 和 JWT 怎么分工？

最合理的分工是：

#### `JWT` 负责：

- 证明“你是谁”
- 提供 `user_id`
- 提供过期时间 `exp`

#### `ClientContext` 负责：

- 当前这个连接处于哪个虚拟目录
- 当前目录节点 ID 是多少
- 这个连接最近一次活动时间是什么时候
- 这个连接是控制连接还是传输连接

所以二者关系是：

> JWT 负责“身份认证”，ClientContext 负责“连接上下文”。

### 那当前虚拟目录 `current_path` 要不要放进 JWT？

**不建议放。**

原因很简单：

1. `current_path` 经常变。
2. JWT 适合存“相对稳定”的身份字段，不适合存频繁变化的工作状态。
3. 如果把路径放进 JWT，那么每次 `cd` 后你都要重新签发一个 JWT，很不划算。

更合理的做法是：

1. JWT 里只放 `user_id`、`exp` 等少量身份字段。
2. 当前目录路径由控制连接自己的 `ClientContext` 维护。
3. 需要发起上传/下载时，客户端把“目标虚拟路径”显式发给服务端。

### 所以 JWT 对当前项目是不是“必须”？

答案分两种情况：

#### 情况一：如果仍然坚持单连接模型

那 JWT 不是刚需。

因为单连接里，`ClientContext` 已经够用。

#### 情况二：如果要做第四期的长短命令分离

那 JWT 很有价值，而且非常合理。

因为它正好解决：

> 新开的传输连接如何确认用户身份

这个问题。

## 2.3 时间轮算法的原理是什么？它有什么优势？

### 先说它是为了解决什么问题

我们要做“超时踢出”时，最朴素的办法是：

1. 每秒触发一次定时器
2. 把所有连接遍历一遍
3. 检查每个连接的 `last_active_time`
4. 超过 30 秒没活动就踢掉

这个办法能用，但缺点是：

- 每秒都要扫描全部连接
- 连接数一多，扫描成本就上来了

### 时间轮的核心思想

时间轮可以理解成一个循环数组。

假设超时时间是 30 秒，那么可以先做一个长度为 30 的数组：

```c
slot[0], slot[1], ..., slot[29]
```

每个槽位里放一批“将在未来某个时刻检查是否超时的连接”。

### 一个最简单的理解方式

假设现在是第 `100` 秒，一个连接刚刚有活动。

如果超时阈值是 `30` 秒，那么它的过期时刻就是：

```c
expire_tick = 100 + 30 = 130
slot_index = 130 % 30 = 10
```

那就把这个连接挂到 `slot[10]` 里。

当时间一秒一秒往前走，时间轮指针也一格一格往前走。

当指针再次走到 `slot[10]` 时：

- 如果当前时间已经到 `130`
  - 说明这个连接真超时了，可以踢掉
- 如果当前时间还没到 `130`
  - 说明只是因为数组循环了一圈又走回来了，它还没到真正过期时间，不能踢

所以，时间轮实现里通常要给每个连接记录一个：

- `expire_tick`

或者：

- `round`

用来区分“这次经过当前槽位时，是否真的应该过期”。

### 为什么连接有活动时要“挪槽”

如果某个连接本来会在第 130 秒过期，但它在第 115 秒又收到了一条命令，那它就不该在第 130 秒被踢。

这时要做的就是：

1. 把它从旧槽位移除
2. 重新计算新的过期时刻
3. 重新插入新槽位

这就是时间轮里的“刷新超时”。

### 时间轮的优势

它最大的优势不是“更神奇”，而是：

> **把“每秒扫描所有连接”变成了“每秒只处理当前槽位里的那一小批连接”。**

因此它特别适合：

- 连接很多
- 大多数连接平时是空闲的
- 需要频繁做超时清理

### 对当前项目有什么价值？

第四期做完后，服务端会有很多控制连接长期在线：

- 有人登录后挂着不动
- 有人偶尔敲一条命令
- 有人正在等待下一步操作

如果还用“一个线程长期守一个连接”的模型，这些连接会非常浪费线程资源。

一旦改成“主线程 `epoll` 管理控制连接”，时间轮就特别合适：

1. 控制连接很多
2. 每条连接的命令都很短
3. 主要问题是识别长期不活动的连接

这正是时间轮擅长的场景。

### 这个项目里最简单的时间轮实现建议

对这个学习项目，我建议采用下面这个最简单版本：

1. 一个长度为 `60` 的数组，表示 60 个槽位。
2. `timerfd` 每秒触发一次。
3. 每个控制连接都有一个 `expire_tick`。
4. 连接建立、收到命令、发送响应成功后，都刷新一次 `expire_tick`。
5. 当前秒对应的槽位到期时，只检查这个槽位里的连接。

为什么建议 60 而不是 30？

因为：

1. 60 秒轮更直观。
2. 就算你的实际超时阈值是 30 秒，也可以照样用 60 个槽位。
3. 后面如果要把超时时间改成 45 秒、50 秒，扩展更自然。

## 3. 第四期最推荐的整体方案

## 3.1 总原则

第四期我建议遵循三条原则：

1. **先把结构改对，再加功能。**
2. **优先选择连接分离，而不是在同一连接上做复杂复用。**
3. **优先选择“简单直观但靠谱”的实现，不追求一步到位的高级设计。**

---

## 3.2 推荐架构：控制连接 + 传输连接

### 控制连接负责短命令

控制连接上只处理：

- `login`
- `register`
- `pwd`
- `cd`
- `ls`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

特点：

- 命令很短
- 很快就能返回
- 适合由服务端主线程 `epoll` 统一管理

### 传输连接负责长命令

传输连接上只处理：

- `puts`
- `gets`

特点：

- 耗时长
- 可能要占用 socket 很久
- 适合丢给独立的传输线程池处理

### 这样分离后会得到什么效果？

1. 某个客户端正在上传大文件时，控制连接仍然可以继续 `ls`、`pwd`、`cd`。
2. 服务端不会再让一个线程长期空耗在“等某个用户下一条命令”这件事上。
3. 短命令处理延迟会显著降低。

---

## 3.3 客户端推荐方案

客户端建议新增一个全局状态结构体：

```c
typedef struct {
    int ctrl_fd;
    int logged_in;
    int user_id;
    char token[1024];
    char current_path[256];
    pthread_mutex_t lock;
} ClientState;
```

这个结构体的作用：

1. `ctrl_fd` 保存控制连接。
2. `token` 保存登录后拿到的 JWT。
3. `current_path` 保存客户端自己认知中的当前远端路径。
4. `lock` 用来保护 `token/current_path` 的并发读写。

### 客户端命令处理建议

#### 短命令

主线程直接在控制连接上处理：

- `pwd`
- `cd`
- `ls`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

#### 长命令

主线程只负责：

1. 解析用户输入
2. 读取当前 `token`
3. 读取当前 `current_path`
4. 构造一个传输任务
5. 创建一个传输线程

传输线程负责：

1. 新建一条 socket 连接
2. 向服务端发送“我是传输连接”的握手包
3. 发送 JWT
4. 发送本次传输请求的目标路径、文件名、命令类型
5. 独立完成 `puts/gets`
6. 结束后关闭自己的 socket

### 这里最关键的一点

**不要让主线程和传输线程共用同一个 socket。**

这是第四期能否稳定实现的分水岭。

---

## 3.4 服务端推荐方案

### 服务端拆成两类处理逻辑

#### 第一类：控制连接

由主线程 `epoll` 直接管理。

主线程负责：

1. `accept` 新连接
2. 读取连接初始化握手，判断它是控制连接还是传输连接
3. 如果是控制连接：
   - 加入 `epoll`
   - 分配一份 `ControlConn`
   - 主线程自己处理其短命令

#### 第二类：传输连接

收到握手后，如果是传输连接：

1. 不加入控制 `epoll`
2. 直接丢进“传输线程池”
3. 某个传输线程取出后独占处理这次 `puts/gets`
4. 传输完成后关闭连接

### 推荐新增的服务端连接状态结构

```c
typedef struct {
    int fd;
    int user_id;
    char current_path[256];
    int current_dir_id;
    long long expire_tick;
    int wheel_slot;
} ControlConn;
```

这个结构体不是 JWT。

它是：

> 服务端内存中的“控制连接上下文”

也就是第四期版的 `ClientContext`。

### 为什么控制连接要保留 `current_path`

因为短命令里：

- `cd`
- `pwd`
- `ls`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

都依赖当前所在虚拟目录。

所以控制连接仍然要有自己的路径上下文。

但是传输连接不一定要维护完整目录状态。

对于传输连接，更简单的做法是：

1. 客户端直接发“本次目标完整虚拟路径”
2. 服务端校验 JWT 拿到 `user_id`
3. 然后按“用户 + 完整虚拟路径”去处理上传/下载

这样传输线程就不需要维护一个长期存在的 `current_path`。

## 3.5 JWT 在第四期里的推荐用法

### JWT 里建议只放这些字段

```json
{
  "uid": 123,
  "iat": 1710000000,
  "exp": 1710003600
}
```

建议保持最小化。

不要一上来塞太多字段。

### 不建议放的字段

- `current_path`
- `current_dir_id`
- 本次要上传的文件名
- 本次要下载的目标目录

这些都属于“业务现场状态”，不属于“身份凭证”。

### JWT 的典型流程

#### 登录时

1. 客户端发用户名和密码。
2. 服务端校验成功。
3. 服务端签发 JWT。
4. 客户端保存 JWT。

#### 控制连接上的普通短命令

有两种方式：

##### 方式一：控制连接登录后一直保留 `user_id`

这时短命令不必每次带 JWT。

优点：

- 更简单

缺点：

- 控制连接断开重连时，需要重新登录或自动恢复

##### 方式二：控制连接每次命令也带 JWT

优点：

- 更统一

缺点：

- 现有协议改动更大

### 对当前项目的建议

第四期第一版建议采用：

1. **控制连接仍然保留内存态 `user_id/current_path`**
2. **传输连接必须携带 JWT**

这是最平衡、最容易落地的方案。

---

## 3.6 超时踢出推荐方案

### 推荐分两部分处理

#### 控制连接

使用：

- `epoll`
- `timerfd`
- 时间轮

#### 传输连接

第一版建议直接使用：

- `SO_RCVTIMEO`
- `SO_SNDTIMEO`

也就是说：

1. 控制连接用时间轮统一踢空闲用户。
2. 传输连接用 socket 收发超时，避免某个传输线程永久卡死。

为什么这样建议？

因为这对初学者最简单：

1. 控制连接集中在主线程，最适合时间轮。
2. 传输连接散落在工作线程里，如果第一版也硬塞进统一时间轮，代码复杂度会明显上升。

等第四期第一版稳定后，再考虑把传输连接也统一纳入时间轮。

## 4. 具体实现上，建议怎样拆步骤

## 4.1 第一步：先做“协议扩展”，不要先改业务逻辑

推荐新增两个协议结构体。

### 1. 连接初始化包

```c
typedef enum {
    CONN_ROLE_CTRL = 1,
    CONN_ROLE_TRANSFER = 2
} conn_role_t;

typedef struct {
    int role;
} conn_init_packet_t;
```

作用：

- 新连接建立后，先告诉服务端“我是控制连接还是传输连接”

### 2. 传输认证请求包

```c
typedef struct {
    int cmd_type;              // CMD_TYPE_PUTS / CMD_TYPE_GETS
    char token[1024];
    char full_path[512];
    char file_name[256];
} transfer_auth_packet_t;
```

作用：

- 传输线程新连上来后
- 先带 JWT
- 再声明自己要做 `puts` 还是 `gets`
- 再给出目标完整虚拟路径

这样服务端传输线程一上来就知道：

1. 你是谁
2. 你要干什么
3. 你要操作哪个虚拟路径

### 为什么推荐新包，而不是把现有 `command_packet_t` 强行塞满？

因为第四期后：

- 控制命令
- 文件协商
- 身份认证

这三类数据已经不是同一个层面的东西。

如果继续全部塞在 `command_packet_t.data[256]` 里，会越来越乱。

---

## 4.2 第二步：客户端先引入 `ClientState`

这个步骤非常重要，因为后面很多功能都要依赖它：

1. 登录后保存 JWT
2. 保存客户端视角下的当前远端路径
3. 传输线程启动时读取路径和 token

### 当前路径怎样维护最简单？

最简单的做法是：

1. 登录成功后：
   - `current_path = "/"`
2. `cd` 成功后：
   - 更新 `current_path`
3. 如果控制连接断开重连：
   - 重新把 `current_path` 设为 `/`
   - 或者自动发一次 `pwd` 重新同步

### 这一步为什么值得做？

因为传输线程不能依赖服务端控制连接里的 `ClientContext`。

它必须从客户端这里拿到：

- 当前路径
- JWT

然后自行发起新传输连接。

---

## 4.3 第三步：登录成功后签发 JWT

建议新建一个模块：

- `include/jwt_utils.h`
- `src/common/jwt_utils.c`

只暴露两个最简单的接口：

```c
int create_jwt_for_user(int user_id, char *token, size_t size);
int verify_jwt_and_get_user(const char *token, int *user_id);
```

### 为什么要单独封装成工具模块？

因为 JWT 不应该散落在：

- `auth.c`
- `session.c`
- `file_transfer.c`

这些业务文件里到处拼。

应该把“生成”和“校验”都封装起来，让业务层只关心：

- 生成成功没有
- 校验通过没有
- 用户 ID 是多少

### 第四期第一版的最简 JWT 策略

建议：

1. 只做 access token
2. 有效期设置短一些，比如 30 分钟或 1 小时
3. 暂时不做 refresh token
4. 暂时不做服务端黑名单

原因：

> 这是一个学习项目，先把“跨连接认证”做通，比把 token 体系做大全更重要。

---

## 4.4 第四步：服务端把当前“连接级线程池”改成“两套模型”

当前模型是：

1. 新连接
2. 入队
3. 一个线程长期处理到断开

第四期推荐改成：

### 控制连接模型

1. 主线程 `accept`
2. 读 `conn_init_packet_t`
3. 如果是控制连接：
   - 设置为控制 fd
   - 放入 `epoll`
   - 分配 `ControlConn`
4. 当控制 fd 可读时：
   - 主线程直接收一条命令
   - 直接执行业务
   - 直接回响应

### 传输连接模型

1. 主线程 `accept`
2. 读 `conn_init_packet_t`
3. 如果是传输连接：
   - 丢进传输任务队列
   - 唤醒一个传输工作线程
4. 传输线程：
   - 校验 JWT
   - 处理 `puts/gets`
   - 完成后关闭连接

### 这样改的最大收益

短命令不再被长连接线程长期占住。

这是第四期真正的性能改造点。

---

## 4.5 第五步：把当前 `handle_puts/handle_gets` 改造成“按完整虚拟路径工作”

当前 `handle_puts/handle_gets` 很依赖传入参数和 `ctx->current_path` 拼接路径。

第四期后，传输连接更推荐直接发：

- `full_path`

例如：

- `/doc/a.txt`
- `/code/main.c`

这样传输线程只需要：

1. 校验 JWT 拿到 `user_id`
2. 用 `user_id + full_path` 去查 `paths`

就行了。

### 为什么这是个关键改造？

因为传输线程本来就不应该再依赖“某条控制连接当时处在哪个目录”。

传输线程应该是：

> 一次请求带齐信息，到服务端即可独立处理

这才符合长短命令分离后的结构。

---

## 4.6 第六步：加时间轮

推荐新增两个模块：

- `include/time_wheel.h`
- `src/server/time_wheel.c`

### 推荐的数据结构

```c
#define WHEEL_SIZE 60

typedef struct ControlConn ControlConn;

typedef struct WheelNode {
    ControlConn *conn;
    struct WheelNode *prev;
    struct WheelNode *next;
} WheelNode;

typedef struct {
    WheelNode *slots[WHEEL_SIZE];
    long long current_tick;
    int timeout_sec;
} TimeWheel;
```

然后在 `ControlConn` 里挂一个：

```c
WheelNode *wheel_node;
long long expire_tick;
int wheel_slot;
```

### 每次什么时候刷新超时？

建议在下面几个时机刷新：

1. 控制连接刚建立时
2. 收到一条合法命令后
3. 成功发送完响应后

### 每秒 tick 时做什么？

1. `timerfd` 触发
2. `current_tick++`
3. 取 `slot[current_tick % WHEEL_SIZE]`
4. 遍历当前槽位
5. 对每个连接判断：
   - 如果 `expire_tick <= current_tick`，踢掉
   - 否则保留，等下一轮

### 踢掉连接时要做什么？

1. 从 `epoll` 删除 fd
2. 从时间轮删除节点
3. 关闭 socket
4. 释放 `ControlConn`

## 5. 第四期的推荐开发顺序

为了降低出错概率，建议按下面顺序做。

## 第 1 步：先把客户端状态结构做好

目标：

- 能保存 token
- 能保存 current_path
- 为后续传输线程做准备

## 第 2 步：引入 JWT 工具模块

目标：

- 登录成功能生成 token
- 传输连接能校验 token

## 第 3 步：新增连接握手协议

目标：

- 服务端能区分控制连接和传输连接

## 第 4 步：先把 `gets` 改成独立传输连接

为什么先做下载？

因为下载比上传简单一点：

1. 不涉及服务端接收大块数据写文件
2. 不涉及秒传
3. 不涉及上传断点续传恢复

## 第 5 步：再把 `puts` 改成独立传输连接

目标：

- 复用现有秒传
- 复用现有上传续传
- 但把身份和路径获取方式改成“JWT + full_path”

## 第 6 步：把控制连接改成 epoll + 时间轮

目标：

- 主线程统一管理控制连接
- 不再让线程长期守着空闲连接

## 第 7 步：最后再做自动重连（选做）

如果控制连接因为超时被踢，而客户端没退出，可以考虑：

1. 主线程发现控制连接断开
2. 自动重连
3. 带着 JWT 重新认证
4. 当前路径重新同步

这一步可以放到最后。

---

## 6. 我对“简单直观实现”的最终建议

如果把第四期做成最适合新手学习的版本，我会建议你们坚持下面这组取舍：

### 建议做的

1. 控制连接和传输连接分离
2. 长命令每次新建一个传输线程
3. 传输线程每次新建一条连接
4. JWT 只负责身份，不负责路径
5. 控制连接保存 `current_path`
6. 传输请求显式带 `full_path`
7. 控制连接用时间轮踢空闲

### 暂时不要做复杂化的

1. 不要让多个线程共用同一个 socket
2. 不要一开始就给客户端做复杂线程池
3. 不要把 `current_path` 塞进 JWT
4. 不要一开始就做 refresh token
5. 不要一开始就把所有连接统一纳入同一套超时框架

---

## 7. 一句话总结

第四期最本质的改造，不是“加 JWT”，也不是“加时间轮”，而是：

> **把当前 V3 的“单连接 + 连接级线程占用”模型，改造成“控制连接处理短命令 + 独立传输连接处理长命令”的模型。**

在这个基础上：

- JWT 解决“新连接如何识别用户”
- 时间轮解决“控制连接空闲太久如何清理”

这三者是配套关系，不是孤立功能。
