# WindCloud_V4 全流程时序图详解

## 1. 文档目标

这份文档专门用**时序图**来解释当前 V4 代码中的关键交互顺序。

这三份“全流程图解”文档的分工如下：

1. [V4全流程活动图详解.md](/home/liwenshuo/my_project/WindCloud_V4/docs/V4全流程活动图详解.md:1)
   重点看流程骨架、判断分支和循环结构。
2. [V4全流程时序图详解.md](/home/liwenshuo/my_project/WindCloud_V4/docs/V4全流程时序图详解.md:1)

3. [V4全流程状态图详解.md](/home/liwenshuo/my_project/WindCloud_V4/docs/V4全流程状态图详解.md:1)
   重点看核心对象的状态变化和状态切换条件。

如果说活动图主要回答的是：

- 先做什么
- 后做什么
- 在哪里分支

那么时序图主要回答的是：

- 是谁先调用了谁
- 是谁先给谁发送了什么数据
- 某一步完成后，下一步由哪个模块继续接手
- 某个失败分支到底在哪一侧被发现，又是如何返回的

本文会把当前 V4 的时序拆成下面这些核心场景：

1. 客户端登录成功并接收 token
2. 客户端注册
3. 一条普通短命令的完整交互
4. `cd` 命令成功后客户端和服务端如何同步路径
5. `puts` 上传的完整交互
6. `puts` 的秒传分支
7. `puts` 的续传 / 中断分支
8. `gets` 下载的完整交互
9. `gets` 的本地续传分支
10. 主连接超时断开和客户端重新登录
11. 服务端退出时主线程与工作线程的协作

本文主要对照这些代码：

- `src/client/client.c`
- `src/client/client_command_handle.c`
- `src/client/client_puts.c`
- `src/client/client_gets.c`

## 3. 登录成功并接收 token 时序图

这是 V4 所有后续链路的起点。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant MainConn as 主连接
    participant SMain as 服务端主线程
    participant Sess as session_handle_main_command
    participant Auth as handle_login
    participant DBU as dao_user
    participant DB as MySQL
    participant JWT as jwt_create_token

    U->>CMain: 输入 login 用户名/密码
    CMain->>CMain: process_command()
    CMain->>CMain: parse_input + get_cmd_type
    CMain->>MainConn: send command_packet_t(LOGIN, "用户名/密码")
    MainConn->>SMain: recv_command_packet()
    SMain->>Sess: session_handle_main_command()
    Sess->>Sess: conn_state_to_client_ctx()
    Sess->>Sess: parse_login_user_name()
    Sess->>Auth: handle_login()
    Auth->>DBU: dao_get_user_by_name()
    DBU->>DB: SELECT users(id, password_hash, salt)
    DB-->>DBU: 返回用户记录
    DBU-->>Auth: 返回 user_id / hash / salt
    Auth->>Auth: hash_password_with_salt()
    Auth->>MainConn: send_msg("登录成功...")
    Sess->>JWT: jwt_create_token(user_id, user_name, 3600)
    JWT-->>Sess: 返回 token
    Sess->>Sess: state->token = token
    Sess->>MainConn: send token_packet_t(token, is_ok=1)
    Sess->>Sess: conn_state_sync_from_client_ctx()
    MainConn-->>CMain: recv_server_reply()
    MainConn-->>CMain: recv_token_packet()
    CMain->>CMain: 保存 token 到 ClientAppContext
    CMain->>CMain: is_logged_in = 1, current_path = "/"
```

### 3.1 这条时序最关键的四件事

#### A. 登录命令本身仍然只是普通短命令

客户端先发的是：

```c
command_packet_t
```

不是特殊协议。

这一点在 `client_command_handle.c` 里很清楚：

```c
init_command_packet(&cmd_packet, cmd_type, arg);
send_command_packet(ctx->sock_fd, &cmd_packet);
```

#### B. token 不是和登录文本响应混在一起发的

服务端登录成功后，会连续发两包：

1. 普通文本响应包
2. `token_packet_t`

对应客户端代码：

```c
ret = recv_server_reply(ctx->sock_fd, &reply_packet);
if (cmd_type == CMD_TYPE_LOGIN && ret == 1) {
    recv_login_token(ctx);
}
```

#### C. token 是长命令链的前提

客户端只有在这里拿到 token，后面才有资格启动：

- `puts`
- `gets`

否则 `handle_puts_command()` / `handle_gets_command()` 会直接拒绝：

```c
if (!ctx->is_logged_in || ctx->token[0] == '\0') {
    printf("请先登录后再上传文件。\n");
    return -1;
}
```

#### D. 登录成功时，服务端会同时初始化目录状态

在 `session_handle_main_command()` 里，首次登录成功后会执行：

```c
strcpy(ctx.current_path, "/");
ctx.current_dir_id = 0;
```

这一步很重要，因为：

1. 后续主连接短命令要依赖当前目录
2. 后续传输连接也要从当前路径恢复目录上下文

## 4. 注册命令时序图

注册没有 token，下图可以和登录流程对照看。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant MainConn as 主连接
    participant SMain as 服务端主线程
    participant Sess as session_handle_main_command
    participant Auth as handle_register
    participant DBU as dao_user
    participant DB as MySQL

    U->>CMain: 输入 register 用户名/密码
    CMain->>MainConn: send command_packet_t(REGISTER, "用户名/密码")
    MainConn->>SMain: recv_command_packet()
    SMain->>Sess: session_handle_main_command()
    Sess->>Auth: handle_register()
    Auth->>Auth: generate_salt()
    Auth->>Auth: hash_password_with_salt()
    Auth->>DBU: dao_insert_user()
    DBU->>DB: INSERT INTO users
    DB-->>DBU: 插入结果
    Auth->>DBU: dao_get_user_by_name()
    DBU->>DB: SELECT id
    DB-->>DBU: 返回新用户记录
    Auth->>MainConn: send_msg("注册成功！请继续登录。")
    MainConn-->>CMain: recv_server_reply()
```

### 4.1 为什么注册不下发 token

因为当前项目里：

> token 代表“已经通过登录校验的会话身份”

注册只是创建用户，并不代表已经进入登录态。  
所以注册成功后客户端仍然停留在登录菜单，而不是直接进入已登录主循环。

## 5. 普通短命令时序图

下面先用 `pwd` 作为最简单的短命令例子。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant MainConn as 主连接
    participant SMain as 服务端主线程
    participant Sess as session_handle_main_command
    participant Biz as handle_pwd

    U->>CMain: 输入 pwd
    CMain->>CMain: process_command()
    CMain->>MainConn: send command_packet_t(PWD, "")
    MainConn->>SMain: recv_command_packet()
    SMain->>Sess: session_handle_main_command()
    Sess->>Sess: conn_state_to_client_ctx()
    Sess->>Biz: handle_pwd(client_fd, &ctx)
    Biz-->>MainConn: send_msg(current_path)
    Sess->>Sess: conn_state_sync_from_client_ctx()
    SMain->>SMain: time_wheel_refresh()
    MainConn-->>CMain: recv_server_reply()
    CMain->>U: 输出当前路径
```

### 5.1 这条链路的关键点

#### A. 短命令不会进入线程池

在 `server.c` 里，只要首包不是 `CMD_TYPE_AUTH`，主线程就直接：

```c
recv_command_packet(fd, &cmd_packet);
session_handle_main_command(fd, state, &cmd_packet);
time_wheel_refresh(&time_wheel, state);
```

所以：

- `pwd`
- `ls`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

都是主线程直接处理。

#### B. 短命令处理完成后会刷新时间轮

这表示：

> 一条普通短命令本身就代表“这个主连接最近有活动”

所以超时位置要往后顺延。

## 6. `cd` 成功后的路径同步时序图

`cd` 比 `pwd` 多一层“客户端本地路径也要同步”的动作。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant MainConn as 主连接
    participant SMain as 服务端主线程
    participant Sess as session_handle_main_command
    participant Biz as handle_cd
    participant VFS as dao_vfs
    participant DB as MySQL

    U->>CMain: 输入 cd doc
    CMain->>MainConn: send command_packet_t(CD, "doc")
    MainConn->>SMain: recv_command_packet()
    SMain->>Sess: session_handle_main_command()
    Sess->>Sess: conn_state_to_client_ctx()
    Sess->>Biz: handle_cd()
    Biz->>VFS: dao_get_node_by_path(target_path)
    VFS->>DB: SELECT id, type FROM paths
    DB-->>VFS: 返回目录节点
    Biz->>Biz: 更新 ctx.current_path / current_dir_id
    Sess->>Sess: conn_state_sync_from_client_ctx()
    Sess->>MainConn: send_msg("切换目录成功" 等)
    SMain->>SMain: time_wheel_refresh()
    MainConn-->>CMain: recv_server_reply()
    CMain->>CMain: build_next_cd_path()
    CMain->>CMain: 更新 ClientAppContext.current_path
```

### 6.1 为什么 `cd` 要两边都更新

服务端更新是为了后续业务正确执行。  
客户端更新是为了后续长命令线程在发 `auth_packet_t` 时，能带上正确的 `current_path`。

所以 `cd` 这条短命令会同时影响：

1. 服务端 `ServerConnState`
2. 客户端 `ClientAppContext`

这正是长短命令分离能跑起来的基础之一。

## 7. `puts` 上传完整时序图

这张图是第二步里最重要的一张图之一。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CThread as 客户端上传线程
    participant MainConn as 主连接
    participant TransConn as 传输连接
    participant SMain as 服务端主线程
    participant Sess as session_build_transfer_task
    participant JWT as jwt_verify_token
    participant VFS as dao_vfs
    participant Worker as 工作线程
    participant FT as handle_puts
    participant DF as dao_file
    participant DB as MySQL
    participant Disk as test/files/hash

    U->>CMain: 输入 puts a.txt
    CMain->>CMain: process_command() 识别为长命令
    CMain->>CMain: handle_puts_command()
    CMain->>CThread: 创建上传线程并复制 arg/current_path/token/ip/port
    Note over CMain,MainConn: 主连接不参与实际文件传输

    CThread->>TransConn: init_socket() 建立独立传输连接
    CThread->>TransConn: send auth_packet_t(PUTS, current_path, token)
    TransConn->>SMain: 新连接可读
    SMain->>SMain: peek_cmd_type() -> CMD_TYPE_AUTH
    SMain->>Sess: recv_auth_packet()
    Sess->>JWT: jwt_verify_token(token)
    JWT-->>Sess: 返回 user_id
    Note over Sess,VFS: 根目录直接返回 current_dir_id=0，非根目录才查询 paths 表
    Sess->>VFS: restore_current_dir_id()
    VFS->>DB: SELECT paths(id, type)
    DB-->>VFS: 返回目录节点
    Sess->>TransConn: recv command_packet_t(PUTS, "a.txt")
    Sess-->>SMain: 构造 transfer_task_t
    SMain->>SMain: del_epoll_fd + conn_manager_remove
    SMain->>Worker: 任务入队并唤醒线程

    Worker->>FT: session_handle_transfer_task() -> handle_puts()
    CThread->>FT: send file_packet_t(file_size, hash)
    FT->>VFS: dao_get_node_by_path(检查重名)
    VFS->>DB: SELECT paths(id, type)
    DB-->>VFS: 返回是否重名
    FT->>DF: dao_file_find_by_sha256()
    DF->>DB: SELECT files(id, size)
    DB-->>DF: 返回是否已有相同 hash
    FT->>Disk: 检查真实文件是否完整
    alt 可直接复用
        FT->>VFS: dao_create_file_node()
        VFS->>DB: INSERT paths
        FT->>DF: dao_file_add_ref_count()
        DF->>DB: UPDATE files count+1
        FT-->>CThread: send file_packet_t(hash 相同)
        CThread->>U: 输出 秒传成功
    else 进入正常上传 / 续传
        FT-->>CThread: send file_packet_t(offset=服务端已有大小)
        CThread->>Disk: 读取本地文件并定位 offset
        CThread->>FT: send 文件内容
        FT->>Disk: mmap + 写入真实文件
        FT->>FT: finish_upload_db_work()
        FT->>DF: dao_file_insert() 或 dao_file_find_by_sha256()
        DF->>DB: INSERT files 或 SELECT files
        FT->>VFS: dao_create_file_node()
        VFS->>DB: INSERT paths
        opt 并发复用已有 files 记录
            FT->>DF: dao_file_add_ref_count()
            DF->>DB: UPDATE files count+1
        end
        FT-->>CThread: send_msg("上传完成！")
    end

    Worker->>TransConn: shutdown + close
```

## 7.1 为什么 `puts` 的时序要分成“主线程接入”和“工作线程执行”

因为当前 V4 的实现明确分成了两层：

### 第一层：主线程前置整理

主线程负责：

1. 看首包是不是 `CMD_TYPE_AUTH`
2. 校验 JWT
3. 恢复目录上下文
4. 收真正的 `PUTS` 命令包
5. 组装 `transfer_task_t`

### 第二层：工作线程执行业务

工作线程负责：

1. 真正进入 `handle_puts()`
2. 收 `file_packet_t`
3. 秒传 / 续传 / 正常上传判断
4. 写真实文件
5. 补数据库关系

如果把这两层不分开，就很难看清为什么 V4 线程池已经和 V3 不一样了。

## 7.2 `puts` 的协议顺序一定要记住

在真实代码里，上传链上的包顺序是：

1. `auth_packet_t`
2. `command_packet_t(PUTS, 文件名)`
3. `file_packet_t(file_size, hash, offset=0)`
4. 服务端回 `file_packet_t(offset=已有进度 或 hash 相同)`
5. 如果不是秒传，再继续发送真实文件内容
6. 服务端最后回普通文本结果

这个顺序一旦记混，客户端和服务端就会协议错位。

## 8. `puts` 秒传分支时序图

秒传是 `puts` 的一个重要分支，单独拆出来更容易理解。

```mermaid
sequenceDiagram
    participant CThread as 客户端上传线程
    participant FT as handle_puts
    participant DF as dao_file
    participant VFS as dao_vfs
    participant DB as MySQL
    participant Disk as test/files/hash

    CThread->>FT: send file_packet_t(file_size, hash)
    FT->>VFS: 检查当前目录是否已重名
    VFS->>DB: SELECT paths(id, type)
    DB-->>VFS: 不重名
    FT->>DF: dao_file_find_by_sha256(hash)
    DF->>DB: SELECT files(id, size)
    DB-->>DF: 返回 file_id / size
    FT->>Disk: check_store_file_ready(hash, size)
    alt 真实文件存在且大小匹配
        FT->>VFS: dao_create_file_node(user_id, path, file_id)
        VFS->>DB: INSERT paths
        FT->>DF: dao_file_add_ref_count(file_id)
        DF->>DB: UPDATE files SET count=count+1
        FT-->>CThread: send file_packet_t(hash=客户端 hash)
        CThread->>CThread: 比较 hash 相等
        CThread->>CThread: 识别为秒传成功
    else 真实文件缺失或不完整
        FT-->>CThread: send file_packet_t(offset=服务端当前已有大小)
        CThread->>CThread: 进入正常上传 / 续传流程
    end
```

### 8.1 当前项目里，秒传不只看数据库

这一点必须特别明确。

服务端不会因为 `files` 表里查到相同 hash，就立刻秒传。  
它还会继续检查：

1. `test/files/<hash>` 是否存在
2. 它是不是普通文件
3. 它的大小是否和 `files.size` 一致

只有三者都成立，才会真正进入秒传。

对应代码在 `file_transfer.c`：

```c
int store_ready = check_store_file_ready(client_file_packet.hash, existed_file_size, &store_size);
if (store_ready == 1) {
    ...
}
```

这条设计避免了：

> 数据库有记录，但真实文件不完整时仍被错误复用

另外，真实文件缺失或不完整时，服务端并不会在这里直接结束上传流程；它会继续回到正常上传 / 续传握手，向客户端返回当前真实文件已有的偏移量。

## 9. `puts` 续传 / 中断分支时序图

```mermaid
sequenceDiagram
    participant CThread as 客户端上传线程
    participant FT as handle_puts
    participant Disk as test/files/hash
    participant DF as dao_file
    participant VFS as dao_vfs
    participant DB as MySQL

    CThread->>FT: send file_packet_t(total_size, hash)
    FT->>Disk: open(hash 文件)
    FT->>Disk: fstat 读取当前 local_size
    FT-->>CThread: send file_packet_t(offset=local_size)
    CThread->>CThread: lseek 到 local_size
    loop remaining > 0
        CThread->>FT: send 文件内容块
        FT->>Disk: 写入映射区
    end
    alt 中途断开，未收满 remaining
        FT->>Disk: ftruncate(local_size + received_count)
        FT->>FT: 尝试 send_msg("传输中断，已保存当前进度。")
        Note over FT,CThread: 客户端通常已经断开，这条提示不一定能被收到
    else 全部收满
        FT->>FT: finish_upload_db_work()
        FT->>DF: dao_file_insert() 或 dao_file_find_by_sha256()
        DF->>DB: INSERT files 或 SELECT files
        FT->>VFS: dao_create_file_node()
        VFS->>DB: INSERT paths
        opt 并发复用已有 files 记录
            FT->>DF: dao_file_add_ref_count()
            DF->>DB: UPDATE files count+1
        end
        FT-->>CThread: send_msg("上传完成！")
    end
```

### 9.1 为什么中断后还要 `ftruncate`

因为服务端在接收前可能已经：

```c
ftruncate(file_fd, file_len);
```

把文件扩展到了目标总大小。  
如果中途断开却不把它截回真实收到的位置，就会留下尾部空洞或脏内容。

所以当前代码在未收满时会做：

```c
ftruncate(file_fd, local_size + received_count);
```

这一步是续传能继续成立的关键。

需要再补充一点：服务端在中断分支里虽然会尝试发送“已保存当前进度”的普通文本提示，但很多情况下客户端连接已经断开，因此这条提示不一定真的能被客户端线程收到。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程

    participant TransConn as 传输连接

    U->>CMain: 输入 gets a.txt
    CMain->>CMain: process_command() 识别为长命令
    CMain->>CThread: 创建下载线程并复制参数

    SMain->>Sess: recv_auth_packet()
    Sess->>JWT: jwt_verify_token()
    JWT-->>Sess: 返回 user_id
    Note over Sess,VFS: 根目录直接返回 current_dir_id=0，非根目录才查询 paths 表
    Sess->>VFS: restore_current_dir_id()
    VFS->>DB: SELECT paths(id, type)
    DB-->>VFS: 返回目录节点

    SMain->>Worker: 任务入队

    Worker->>FT: session_handle_transfer_task() -> handle_gets()
    FT->>VFS: dao_get_file_info_by_path()
    VFS->>DB: SELECT paths(id, file_id, type)
    DB-->>VFS: 返回 node_id / file_id
    FT->>DF: dao_file_get_info_by_id(file_id)
    DF->>DB: SELECT LOWER(HEX(sha256sum)), size
    DB-->>DF: 返回 sha256 / size
    FT->>Disk: open(test/files/hash)
    FT-->>CThread: send file_packet_t(file_size)
    CThread->>CThread: 检查本地文件大小
    CThread-->>FT: send file_packet_t(offset=本地已有大小)
    FT->>Disk: sendfile(offset..end)
    FT-->>CThread: 剩余字节流
    CThread->>CThread: 写入本地文件
    Worker->>TransConn: shutdown + close
```

## 10.1 `gets` 的核心链路是“双跳查找”

下载时，服务端不是直接“文件名 -> 磁盘文件”。

它必须经过：

1. 逻辑路径查 `paths.file_id`
2. `file_id` 再查 `files.sha256sum`
3. `sha256sum` 再拼接成真实文件路径

也就是：

```text
逻辑路径 -> paths.file_id -> files.sha256 -> test/files/<sha256>
```

这也是为什么 V4 虽然改了连接模型，但下载业务本体仍然和虚拟文件系统紧密绑定。

## 11. `gets` 本地续传分支时序图

```mermaid
sequenceDiagram
    participant U as 用户
    participant CThread as 客户端下载线程
    participant FT as handle_gets
    participant Disk as 客户端本地文件

    FT-->>CThread: send file_packet_t(file_size=服务端总大小)
    CThread->>Disk: stat 本地同名文件
    alt 本地文件不存在
        CThread->>CThread: request_offset = 0
    else 本地文件比服务端小
        CThread->>CThread: request_offset = local_size
    else 本地文件和服务端一样大
        CThread->>CThread: request_offset = file_size
    else 本地文件更大或异常
        CThread->>CThread: request_offset = 0
    end
    CThread-->>FT: send file_packet_t(offset=request_offset)
    alt request_offset == file_size
        CThread->>CThread: 识别为“本地已经完整”
        CThread->>U: 输出无需下载
    else
        FT-->>CThread: 从 offset 开始发送剩余内容
        CThread->>Disk: lseek 到 offset
        loop remaining > 0
            CThread->>CThread: recv_full(once)
            CThread->>Disk: write_file_full()
        end
    end
```

### 11.1 为什么下载续传偏移由客户端决定

因为只有客户端自己知道：

1. 本地是否已经有同名文件
2. 本地这个文件现在有多大

所以下载协议里是：

1. 服务端先告诉客户端“服务器文件总大小”
2. 客户端再回传“我本地已经有多少”

上传则正好相反，是服务端回给客户端已有进度。

## 12. 主连接超时断开与客户端重新登录时序图

这一条链路把时间轮和客户端重连逻辑连接起来。

```mermaid
sequenceDiagram
    participant SMain as 服务端主线程
    participant Wheel as time_wheel
    participant Conn as conn_manager
    participant MainConn as 主连接
    participant CMain as 客户端主线程

    SMain->>SMain: epoll_wait(timeout=1000ms)
    SMain->>Wheel: process_time_wheel_tick()
    Wheel->>Wheel: current_tick++
    Wheel->>Conn: conn_manager_get(fd)
    Conn-->>Wheel: 返回 state
    alt state 仍存在 且 expire_tick 匹配
        Wheel-->>SMain: 返回 expired_fds
        SMain->>Conn: conn_manager_get(fd)
        Conn-->>SMain: 返回 state
        SMain->>SMain: close_managed_connection()
        Note over SMain,MainConn: 主连接被服务端关闭
    end

    CMain->>MainConn: 下一次发送短命令
    MainConn-->>CMain: send/recv 失败
    CMain->>CMain: reset_client_login_state()
    CMain->>CMain: process_command() 返回 -1
    CMain->>CMain: 检测到 is_logged_in == 0
    CMain->>CMain: reconnect_and_login()
    CMain->>MainConn: close 旧连接
    CMain->>MainConn: init_socket() 重建主连接
    CMain->>CMain: 重新进入 client_login_menu()
```

### 12.1 这里最容易误解的一点

客户端并不会在“服务端关闭连接的瞬间”立刻知道自己掉线。  
它通常是在：

1. 下一次发送命令
2. 或下一次接收响应

失败时，才发现主连接已经失效。

所以当前实现属于：

> 服务端主动关闭  
> 客户端按需发现并恢复

## 13. 服务端退出时主线程和工作线程协作时序图

```mermaid
sequenceDiagram
    participant Parent as 父进程
    participant Child as 服务端子进程主线程
    participant Pool as 线程池
    participant Queue as 任务队列
    participant Worker as 工作线程
    participant Busy as busy_fds

    Parent->>Parent: 收到 SIGINT
    Parent->>Child: 向 pipe_fd[1] 写退出字节
    Child->>Child: epoll 监听到 pipe_fd[0]
    Child->>Pool: pool.exitFlag = 1
    loop 队列仍有未处理任务
        Child->>Queue: deQueue()
        Queue-->>Child: 返回 transfer_task_t
        Child->>Child: shutdown + close task.client_fd
    end
    loop 遍历 busy_fds
        Child->>Busy: 检查每个工作线程是否正在忙
        alt busy_fds[i] != -1
            Child->>Worker: shutdown(正在处理的传输连接)
        end
    end
    Child->>Worker: pthread_cond_broadcast()
    Worker->>Pool: 被唤醒后看到 exitFlag == 1
    Worker-->>Child: 线程退出
    Child->>Child: pthread_join 全部工作线程
    Child->>Child: destroy_thread_pool / conn_manager / time_wheel / db_pool
    Child-->>Parent: 子进程退出
```

### 13.1 为什么退出链路也要看时序

因为这里不是“主线程退出，工作线程自然消失”这么简单。  
当前代码明确考虑了三类资源：

1. 队列里尚未开始的任务
2. 工作线程已经拿到手的任务
3. 线程池本身和连接状态管理结构

这个时序图能帮助你看清：

> 退出不是一个点，而是一整条有先后顺序的回收链

## 16. 一句话总结

从时序角度看，当前 V4 的本质可以概括成下面这句话：

> 登录通过主连接建立长期身份并下发 token；短命令始终由客户端主线程和服务端主线程直接交互；`puts/gets` 则由客户端启动独立线程建立独立传输连接，服务端主线程先完成认证和任务整理，再把真正的上传下载交给工作线程；时间轮负责关闭长时间无活动的主连接，而客户端在下一次命令失败时负责重新建立主连接并重新登录。
