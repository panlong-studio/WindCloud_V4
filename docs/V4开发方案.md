# WindCloud_V4 开发方案

## 1. 目标

本方案基于 V3 现有工程继续扩展，重点完成以下三项能力：

1. 长短命令分离
2. JWT 身份校验
3. 空闲连接超时断开（时间轮）

本次改造遵循以下原则：

1. 尽量不改动 V3 现有目录结构
2. 尽量复用 `protocol`、`auth`、`file_cmds`、`file_transfer`、`thread_pool`、`worker` 现有代码
3. 不引入新的大型第三方库，JWT 优先复用当前已链接的 OpenSSL 能力实现
4. 客户端和服务端代码风格继续保持初学者易读、直观、步骤清晰

---

## 2. V3 现状与第四期矛盾点

### 2.1 当前 V3 的处理方式

当前 V3 服务端模型是：

1. 主线程 `accept` 新连接
2. 把 `client_fd` 放入线程池队列
3. 工作线程调用 `handle_request(client_fd)`
4. 一个线程长期服务一个客户端连接，直到客户端断开

当前 V3 客户端模型是：

1. 只有一个 socket
2. 普通命令和文件传输都走这一个 socket
3. `puts/gets` 执行期间，客户端主循环会处于等待状态

### 2.2 第四期要解决的问题

第四期要求的核心问题有三个：

1. 一个客户端连接长期占住一个工作线程，线程利用率低
2. 上传和下载时，客户端不能继续处理普通命令，交互体验差
3. 一旦把传输任务拆到独立连接，就必须解决“服务端如何识别用户身份”的问题

---

## 3. 选定方案

本次采用方案 A：`主连接处理短命令 + 独立传输连接处理长命令`。

### 3.1 客户端侧

客户端保留一个主连接，专门处理：

1. `login`
2. `register`
3. `pwd`
4. `cd`
5. `ls`
6. `mkdir`
7. `touch`
8. `rm`
9. `rmdir`

客户端执行 `puts/gets` 时：

1. 主线程不复用主连接
2. 启动一个子线程
3. 子线程重新建立一个独立传输连接
4. 子线程携带 JWT 和当前虚拟路径信息
5. 子线程单独完成一次上传或下载
6. 传输结束后关闭这个独立连接

### 3.2 服务端侧

服务端主线程负责：

1. 监听新连接
2. 管理所有主连接的短命令
3. 校验传输连接带来的 JWT
4. 把通过校验的上传下载任务交给线程池
5. 维护时间轮，处理空闲连接超时断开

服务端工作线程负责：

1. 只处理长命令任务
2. 即上传和下载任务
3. 一个线程处理一个传输连接
4. 传输完成后关闭该传输连接并退出本次任务

---

## 4. 总体结构调整

### 4.1 保持不变的模块

以下模块继续保留原职责：

1. `auth.c` 继续负责登录和注册主流程
2. `file_cmds.c` 继续负责目录类命令
3. `file_transfer.c` 继续负责上传下载、断点续传、秒传
4. `dao_user.c`、`dao_vfs.c`、`dao_file.c` 继续负责数据库访问
5. `db_pool.c`、`db_init.c`、`log.c`、`config.c` 继续保持原有职责

### 4.2 需要新增或扩展的模块

建议新增以下轻量模块：

1. `jwt` 模块
作用：生成 JWT、校验 JWT、解析用户信息和过期时间

2. `conn_manager` 模块
作用：管理主连接状态，保存每个主连接对应的 `user_id`、当前路径、当前目录 id、JWT、最后活跃时间

3. `time_wheel` 模块
作用：维护空闲连接超时断开逻辑

4. `transfer_session` 或 `transfer_dispatch` 模块
作用：处理“传输连接认证通过后，如何交给线程池”的逻辑

### 4.3 线程池的调整方向

V3 的线程池队列目前只保存 `client_fd`。

V4 中线程池队列改为保存“传输任务结构体”，结构体中至少包含：

1. `client_fd`
2. `cmd_type`
3. `user_id`
4. `current_path`
5. `current_dir_id`

这样工作线程拿到任务后，就不再需要像 V3 一样先做完整登录会话循环，而是处理一次 `puts` 或 `gets`。

---

## 5. 协议设计

### 5.1 继续保留的协议包

V3 中已有两种固定协议包：

1. `command_packet_t`
2. `file_packet_t`

这两种协议继续保留，不推翻重写。

### 5.2 新增的协议包

建议新增一个固定结构体，例如 `auth_packet_t`，用于独立传输连接的认证。

建议字段如下：

1. `int cmd_type`
2. `int transfer_cmd`
3. `char current_path[256]`
4. `char token[512]`

作用如下：

1. `cmd_type` 固定表示“这是认证包”
2. `transfer_cmd` 表示本次是 `puts` 还是 `gets`
3. `current_path` 表示客户端主连接当前所在虚拟路径
4. `token` 表示登录成功后服务端签发给客户端的 JWT

### 5.3 登录成功后的返回

登录成功后，服务端除了继续发送原有的文字提示，还需要额外发送一个 JWT 响应包。

这样做的好处：

1. 不破坏 V3 现有“普通命令返回文字消息”的处理习惯
2. 客户端只需在登录成功分支多接收一次 JWT 包
3. 其余短命令处理方式基本不变

---

## 6. JWT 方案

### 6.1 JWT 的实现策略

本项目不额外引入新的 JWT 三方库，使用 OpenSSL 封装一个简化版 HS256 JWT。

原因如下：

1. 当前工程已经链接 `-lcrypto`
2. 不需要再修改开发环境安装步骤
3. 对汇报材料更友好，结构变动更小

### 6.2 JWT 内建议包含的信息

JWT 载荷建议包含：

1. `uid`
2. `uname`
3. `iat`
4. `exp`

其中：

1. `uid` 用于服务端快速恢复用户身份
2. `uname` 用于辅助日志和调试
3. `iat` 表示签发时间
4. `exp` 表示过期时间

### 6.3 JWT 的使用方式

登录成功时：

1. 服务端根据用户信息生成 JWT
2. 服务端把 JWT 发给客户端主线程
3. 客户端缓存 JWT

上传下载时：

1. 客户端子线程新建传输连接
2. 先发送 `auth_packet_t`
3. 服务端主线程校验 JWT
4. 校验通过后恢复本次传输的 `user_id` 和目录上下文
5. 再把任务交给工作线程

---

## 7. 主连接与传输连接的职责划分

### 7.1 主连接

主连接只做短命令。

服务端主线程在这个连接上处理：

1. 登录注册
2. 目录切换
3. 目录查看
4. 创建目录
5. 创建空文件
6. 删除文件
7. 删除目录

主连接需要长期保留以下状态：

1. `user_id`
2. `current_path`
3. `current_dir_id`
4. `jwt`
5. `last_active_time`

### 7.2 传输连接

传输连接只做一次 `puts` 或一次 `gets`。

一个传输连接的生命周期如下：

1. 建立连接
2. 发送 `auth_packet_t`
3. 服务端校验 JWT
4. 服务端构造一次传输任务并投递到线程池
5. 工作线程处理一次上传或下载
6. 任务结束后关闭连接

这样可以保证：

1. 主连接不被大文件传输占住
2. 线程池只负责真正耗时的部分
3. 与 V3 的 `file_transfer.c` 对接最自然

---

## 8. 会话状态设计

### 8.1 服务端新增主连接状态结构

建议新增一个结构体，例如 `ServerConnState`：

1. `int fd`
2. `int is_logged_in`
3. `int user_id`
4. `char current_path[256]`
5. `int current_dir_id`
6. `char token[512]`
7. `time_t last_active_time`
8. `int wheel_slot`

### 8.2 为什么要增加这个结构

原因如下：

1. V3 的 `ClientContext` 只存在于单个线程函数内部
2. V4 中主连接改成由主线程长期维护
3. 因此必须把连接状态从“函数局部变量”提升为“主线程可管理的数据结构”

### 8.3 当前路径的一致性

主连接上的 `cd` 成功后：

1. 服务端更新该连接对应的 `current_path`
2. 服务端更新 `current_dir_id`
3. 客户端本地也同步更新一个当前路径副本

这样客户端子线程发起传输时，才能把正确的 `current_path` 放进 `auth_packet_t`。

---

## 9. 时间轮设计

### 9.1 时间轮管理对象

本期时间轮只管理主连接。

原因如下：

1. 主连接是长期存在的
2. 传输连接本身就是一次性任务连接
3. 只管理主连接，逻辑更清晰，改动也更小

### 9.2 基本做法

建议用长度固定的循环数组实现时间轮。

例如：

1. 时间轮长度为 `TIMEOUT_SECONDS`
2. 每个槽位保存一个连接集合
3. 主线程每秒推进一次指针
4. 新连接或收到短命令时，把连接移到新的槽位
5. 当某个槽位过期时，检查其中连接是否确实超时
6. 超时则关闭连接并清理状态

### 9.3 超时判定规则

建议默认规则：

1. 登录前连接也参与超时判定
2. 登录后连接超过固定秒数没有短命令活动，则断开
3. 传输子连接不进时间轮

### 9.4 客户端表现

如果主连接因超时被服务端关闭：

1. 客户端不要立即退出
2. 下次用户再输入普通命令时，提示“连接已失效，请重新登录”

这一版先不做自动重连，保证整体实现稳定、可控。

---

## 10. 客户端改造方案

### 10.1 客户端主线程新增状态

建议在客户端维护一个轻量上下文，例如：

1. `sock_fd`
2. `is_logged_in`
3. `current_path`
4. `token`
5. `server_ip`
6. `server_port`

### 10.2 登录成功后的处理

登录成功后，客户端需要：

1. 接收服务端返回的 JWT
2. 保存 JWT
3. 把 `current_path` 重置为 `/`

### 10.3 `cd` 成功后的处理

客户端收到 `cd` 成功后，需要同步更新本地 `current_path`。

处理方式：

1. `cd ..`、`cd .`、`cd 目录名`、`cd /绝对路径`
2. 客户端按和服务端相同的规则更新自己的路径副本
3. 如果服务端返回失败，则不修改本地路径

### 10.4 `puts/gets` 的处理

客户端执行 `puts/gets` 时：

1. 主线程创建一个传输线程
2. 传输线程重新连接服务端
3. 先发送 `auth_packet_t`
4. 再按原 V3 协议发送 `command_packet_t` 和 `file_packet_t`
5. 传输完成后线程结束

---

## 11. 服务端改造方案

### 11.1 `server.c`

`server.c` 将成为第四期改造重点。

需要完成以下调整：

1. `epoll` 不再只监听 `listen_fd` 和退出管道
2. 新连接接入后要登记连接类型和连接状态
3. 主连接上的短命令由主线程处理
4. 传输连接的认证包由主线程校验
5. 认证通过后把传输任务压入线程池
6. 主循环中增加时间轮推进

### 11.2 `session.c`

`session.c` 不再负责“一个连接上的完整生命周期循环”。

建议拆成两类函数：

1. 主连接短命令分发函数
2. 传输任务单次处理函数

### 11.3 `worker.c`

`worker.c` 从“处理完整连接会话”改成“处理一次传输任务”。

即：

1. 线程从队列中取一个传输任务
2. 根据任务中的 `cmd_type` 判断是 `puts` 还是 `gets`
3. 调用 `file_transfer.c` 中现有函数
4. 任务结束后关闭这个传输连接

### 11.4 `thread_pool.c` 与 `queue.c`

这里需要把队列元素从 `fd` 升级为“任务结构体”。

升级后线程池仍保持原来的写法风格：

1. 主线程入队
2. 工作线程出队
3. 条件变量唤醒
4. 不引入复杂模板或泛型结构

---

## 12. 数据库方案

本期数据库建议不新增表。

原因如下：

1. JWT 是无状态校验，本身不要求数据库保存会话
2. 当前用户身份和目录树已经能通过 `users`、`paths`、`files` 表满足
3. 本次重点在连接管理和任务切分，不在数据库扩展

因此：

1. `users` 表继续用于账号校验
2. `paths` 表继续用于恢复当前目录
3. `files` 表继续用于文件实体和秒传

---

## 13. 具体开发顺序

### 第一阶段

先扩展协议和基础结构：

1. 在 `protocol.h` 中增加 JWT 包和认证包定义
2. 在 `protocol.c` 中补充对应的初始化、发送、接收函数
3. 为线程池任务新增结构体

### 第二阶段

实现 JWT 模块：

1. Base64URL 编码
2. Base64URL 解码
3. HS256 签名
4. JWT 生成
5. JWT 校验

### 第三阶段

实现服务端主连接状态管理和时间轮：

1. 新增连接状态表
2. 新增时间轮结构
3. 新连接接入
4. 短命令活动刷新
5. 超时连接关闭

### 第四阶段

改造服务端命令调度：

1. 主线程处理短命令
2. 主线程校验传输连接 JWT
3. 主线程构造传输任务
4. 工作线程只处理上传下载

### 第五阶段

改造客户端：

1. 保存 JWT
2. 保存当前虚拟路径
3. `cd` 成功后更新本地路径
4. `puts/gets` 改为子线程独立连接传输

### 第六阶段

整体联调和补文档：

1. 登录流程联调
2. 短命令联调
3. 上传下载联调
4. 超时断开联调
5. 编写 V4 开发记录

## 14. 需要重点注意的风险

### 风险一：客户端本地路径与服务端路径不一致

解决方式：

1. 只有服务端返回成功时客户端才更新本地路径
2. 登录成功后统一重置为 `/`
3. 如果主连接失效，则本地路径也清回 `/`

### 风险二：传输连接认证通过后，工作线程拿不到完整上下文

解决方式：

1. 主线程在投递任务前就把 `user_id`、`current_path`、`current_dir_id` 填好
2. 工作线程不再自己做登录判断

### 风险三：超时关闭和 epoll/线程池并发冲突

解决方式：

1. 时间轮只管理主连接
2. 传输连接不进入时间轮
3. 传输任务一旦投递到线程池，就由工作线程负责关闭

### 风险四：JWT 过期后客户端还继续发传输请求

解决方式：

1. 服务端拒绝该传输连接
2. 客户端提示重新登录

## 16. 本方案的最终效果

完成后，V4 的运行方式将变成：

1. 客户端主连接一直负责短命令
2. 上传下载由客户端子线程独立连接服务端处理
3. 服务端主线程负责短命令和传输认证
4. 服务端工作线程只处理真正耗时的文件传输
5. 服务端能按时间轮清理空闲主连接
6. 传输连接通过 JWT 识别用户身份

这样既满足第四期要求，也能最大程度保留 V3 现有结构和汇报口径。
