# 第五期双实例联调环境准备方案

## 1. 文档目标

本文档用于指导你按下面这套更直观的方式完成第五期双实例联调：

1. 在本地 WSL2 启动一个服务端
2. 在另一台虚拟机启动另一个服务端
3. 在本地 WSL2 启动客户端
4. 验证客户端一次 `gets` 时，能从两个不同服务端拿到同一个文件的不同分片

这版方案不再使用项目内的 `instance2` 这类目录。  
每台机器都只保留自己的一份项目代码、自己的 `config/config.ini`、自己的 `test/server_files`。

---

## 2. 先说核心原则

双实例联调要成立，必须满足下面 3 件事：

1. 两个服务端要连接同一个数据库
2. 两个服务端都要持有同一个真实文件
3. 数据库里的 `file_sources` 表里要有两条不同服务端的数据源记录

如果少了其中任何一条，第五期客户端就拿不到真正的“双数据源下载方案”。

---

## 3. 推荐的整体拓扑

推荐你按下面这个结构来搭：

```text
本地 WSL2:
  - WindCloud 项目代码
  - server_app（服务端 A）
  - client_app（客户端）

虚拟机:
  - WindCloud 项目代码
  - MySQL
  - server_app（服务端 B）
```

也就是说：

1. 客户端和本地服务端在 WSL2
2. 第二个服务端和数据库都放到虚拟机

这样做的好处是：

1. 本地客户端连本地服务端最直接
2. 两个服务端都能共享虚拟机上的同一个数据库
3. 不需要在 WSL2 里再硬起第二套服务端目录结构

---

## 4. 为什么推荐把 MySQL 放在虚拟机

因为双实例联调最关键的是“两个服务端共享同一个数据库”。

如果 MySQL 放在虚拟机：

1. 虚拟机服务端连自己的本机 MySQL 最直接
2. WSL2 本地服务端只需要远程连虚拟机的 MySQL
3. 配置关系更清楚

相比之下，如果把 MySQL 放在 WSL2，再让虚拟机远程连回 WSL2，网络和权限通常更麻烦一些。

---

## 5. 两台机器分别需要什么

## 5.1 本地 WSL2

你需要准备：

1. 当前项目代码
2. `bin/server_app`
3. `bin/client_app`
4. `config/config.ini`
5. `test/client_files`
6. `test/server_files`

## 5.2 虚拟机

你需要准备：

1. 同版本项目代码
2. `bin/server_app`
3. MySQL
4. `config/config.ini`
5. `test/server_files`

注意：

1. 两边代码版本必须一致
2. 两边数据库表结构必须一致
3. 两边最好都先执行一次 `make -j2`

---

## 6. 启动方式的简化结论

当前项目的配置文件和 `test` 目录都支持从项目根目录直接启动：

1. `config/config.ini` 可以通过 `./config/config.ini` 找到
2. `test/client_files` 和 `test/server_files` 可以通过 `./test/...` 找到

所以这次最简单的做法就是：

### 本地 WSL2

在项目根目录启动：

```bash
./bin/server_app
```

以及：

```bash
./bin/client_app
```

### 虚拟机

也在项目根目录启动：

```bash
./bin/server_app
```

不需要再人为准备 `instance1/run`、`instance2/run` 这类目录。

---

## 7. 虚拟机网络要求

你至少要确认一件事：

> 本地 WSL2 能访问虚拟机的 IP 和端口

建议你在虚拟机里先查到自己的 IP，例如：

```bash
ip addr
```

你当前已经能通过下面这个地址连接虚拟机：

```text
ssh://lws@192.168.193.128:22
```

这通常就说明：

> 当前对你本地 WSL2 可达、适合本次联调使用的虚拟机 IP，就是 `192.168.193.128`

因此，下面文档里的示例 IP 全部直接按 `192.168.193.128` 来写。

虚拟机 IP 直接按下面使用：

```text
192.168.193.128
```

那你在 WSL2 里至少要能通：

```bash
ping 192.168.193.128
```

如果 `ping` 不通，后面的双实例下载也一定做不成。

---

## 8. MySQL 需要怎样配置

因为本地 WSL2 服务端要远程连接虚拟机上的 MySQL，所以你需要在虚拟机上允许远程访问。

至少要确认下面几项：

1. MySQL 正常启动
2. MySQL 监听的地址不是只绑定 `127.0.0.1`
3. 防火墙允许 `3306`
4. 给 WSL2 所在地址或网段授予数据库访问权限

### 8.1 监听地址

在虚拟机的 MySQL 配置里，通常要把：

```ini
bind-address = 127.0.0.1
```

改成：

```ini
bind-address = 0.0.0.0
```

### 8.2 授权

例如在虚拟机 MySQL 中执行：

```sql
CREATE DATABASE IF NOT EXISTS netdisk_db;

CREATE USER IF NOT EXISTS 'windcloud'@'%' IDENTIFIED BY '123456';
GRANT ALL PRIVILEGES ON netdisk_db.* TO 'windcloud'@'%';
FLUSH PRIVILEGES;
```

你也可以继续用现有用户，但从联调角度，单独建一个 `windcloud` 用户更清楚。

### 8.3 连通性检查

在 WSL2 里执行：

```bash
mysql -h 192.168.193.128 -uwindcloud -p123456 -D netdisk_db -e "SELECT 1;"
```

如果这一步不通，就先不要继续做服务端联调。

---

## 9. 两台机器的配置文件应该怎么写

下面假设：

1. 虚拟机 IP 是 `192.168.193.128`
2. MySQL 在虚拟机
3. 本地服务端端口用 `9090`
4. 虚拟机服务端端口也用 `9090`

注意这里两边都可以用 `9090`，因为它们不在同一台机器上，不冲突。

## 9.1 本地 WSL2 的 `config/config.ini`

建议这样改：

```ini
ip=127.0.0.1
port=9090
db_host=192.168.193.128
db_user=windcloud
db_pwd=123456
db_name=netdisk_db
log=INFO
client_log=./log/client.log
server_log=./log/server.log
client_file_dir=client_files
server_file_dir=server_files
ctrl_timeout_sec=60
```

说明：

1. 本地服务端 `ip=127.0.0.1` 即可
2. 因为客户端就在本地 WSL2，控制连接和本地数据源连接都走本机
3. 但数据库要连虚拟机，所以 `db_host` 写虚拟机 IP

## 9.2 虚拟机里的 `config/config.ini`

建议这样改：

```ini
ip=192.168.193.128
port=9090
db_host=127.0.0.1
db_user=windcloud
db_pwd=123456
db_name=netdisk_db
log=INFO
client_log=./log/client.log
server_log=./log/server.log
client_file_dir=client_files
server_file_dir=server_files
ctrl_timeout_sec=60
```

说明：

1. `ip` 一定要写成虚拟机可被 WSL2 访问的实际 IP
2. 这样虚拟机服务端登记到 `file_sources` 里的地址，客户端才能连得到
3. 虚拟机服务端访问自己的 MySQL，所以 `db_host=127.0.0.1`

---

## 10. 两边的真实文件目录怎么处理

虽然两台机器都可以把目录名都叫做：

```text
test/server_files
```

但它们是两台机器上的两份独立目录，不是同一份物理目录。

这正是我们需要的效果。

也就是说：

### 本地 WSL2

真实文件在：

```text
./test/server_files
```

### 虚拟机

真实文件也在：

```text
./test/server_files
```

但这是虚拟机自己的那份。

---

## 11. 真正联调前的准备顺序

建议你严格按下面顺序来。

### 第一步：两边都编译

本地 WSL2：

```bash
make -j2
```

虚拟机：

```bash
make -j2
```

### 第二步：先只验证数据库

本地 WSL2：

```bash
mysql -h 192.168.193.128 -uwindcloud -p123456 -D netdisk_db -e "SELECT 1;"
```

虚拟机：

```bash
mysql -h 127.0.0.1 -uwindcloud -p123456 -D netdisk_db -e "SELECT 1;"
```

### 第三步：启动两个服务端

本地 WSL2：

```bash
./bin/server_app
```

虚拟机：

```bash
./bin/server_app
```

### 第四步：先在本地客户端上传测试文件

本地 WSL2：

```bash
./bin/client_app
```

登录后执行：

```text
puts demo_big.bin
```

这样会先把文件上传到本地 WSL2 服务端，并在共享数据库里登记第一条数据源记录：

```text
127.0.0.1:9090
```

## 12. 如何把同一个真实文件同步到虚拟机服务端

第五期当前不会自动把真实文件复制到另一台服务器，所以这一步要你手工做。

### 12.1 先找到本地真实文件

本地 WSL2 上传完成后，去看：

```text
./test/server_files
```

你会看到一个以 SHA-256 命名的真实文件。

### 12.2 把它复制到虚拟机

你可以用：

1. `scp`
2. 共享文件夹
3. WinSCP
4. 手工复制

把这个文件复制到虚拟机项目的：

```text
./test/server_files
```

### 12.3 为什么必须复制

因为双实例联调不是只要数据库里有两条记录就行。  
第二个服务端自己也必须真的持有这份真实文件，否则客户端拿到第二数据源地址后，一连上就会失败。

---

## 13. 如何补第二条 `file_sources` 记录

文件复制到虚拟机后，还要把第二台服务端登记进数据库。

### 13.1 先查文件对应的 `file_id`

在虚拟机 MySQL 或本地 MySQL 客户端执行：

```sql
SELECT p.path, f.id, HEX(f.sha256sum), f.size
FROM paths p
JOIN files f ON p.file_id = f.id
WHERE p.path = '/demo_big.bin';
```

假设查到：

```text
file_id = 7
```

### 13.2 插入第二条数据源

执行：

```sql
INSERT INTO file_sources (file_id, server_ip, server_port, status)
VALUES (7, '192.168.193.128', '9090', 1)
ON DUPLICATE KEY UPDATE status = 1;
```

### 13.3 检查结果

执行：

```sql
SELECT file_id, server_ip, server_port, status
FROM file_sources
WHERE file_id = 7;
```

预期至少有两条：

```text
7  127.0.0.1      9090  1
7  192.168.193.128  9090  1
```

## 14. 正式双实例联调步骤

## 14.1 删除本地客户端已有文件

在本地 WSL2，把源文件先备份，然后删除正式下载目标：

```bash
cp ./test/client_files/demo_big.bin ./test/client_files/demo_big.bin.src
rm -f ./test/client_files/demo_big.bin
```

### 14.2 本地客户端执行下载

在本地客户端里执行：

```text
gets demo_big.bin
```

### 14.3 你应该重点观察什么

#### 观察 1：数据库里确实有两个数据源

如果没有两条 `file_sources`，客户端就只会拿到一个下载源。

#### 观察 2：两个服务端日志都出现下载处理记录

本地 WSL2 服务端日志里应出现：

```text
传输连接进入线程池
一次性传输票据消费成功
下载完成
```

虚拟机服务端日志里也应出现同类型记录。

如果只有本地服务端有日志，说明客户端实际上还是只用了一个数据源。

#### 观察 3：最终文件哈希正确

本地 WSL2 执行：

```bash
sha256sum ./test/client_files/demo_big.bin ./test/client_files/demo_big.bin.src
```

预期：

两个哈希完全一致。

---

## 15. 如何判断双实例联调真的成功

必须同时满足下面 4 条，才算真正通过：

1. 两个服务端都启动成功
2. `file_sources` 里有两条不同服务端记录
3. 两个服务端日志里都出现本次 `gets` 的下载处理记录
4. 客户端最终文件哈希正确

如果只是“客户端把文件下完了”，但第二台虚拟机服务端没有实际参与传输，那还不能算真正的双实例联调通过。

---

## 16. 最常见的失败点

### 16.1 WSL2 连不到虚拟机 MySQL

表现：

- 本地 WSL2 服务端启动时报数据库连接失败

优先检查：

1. 虚拟机 MySQL 是否允许远程连接
2. `3306` 是否开放
3. `db_host` 是否写对

### 16.2 客户端连不到虚拟机服务端

表现：

- 控制连接方案申请成功
- 但某个分片线程连接虚拟机服务端失败

优先检查：

1. 虚拟机 `ip` 配置是否写成真实可访问 IP
2. 虚拟机 `9090` 是否监听成功
3. 防火墙是否放行 `9090`

### 16.3 虚拟机服务端有记录，但下载时报文件不存在

表现：

- 客户端能拿到虚拟机数据源
- 一连接虚拟机就失败

优先检查：

1. 真实文件是否真的复制到了虚拟机的 `test/server_files`
2. 文件名是否就是 SHA-256 文件名

### 16.4 `file_sources` 只有一条记录

表现：

- 客户端始终只有一个下载源

优先检查：

1. 第二条 `INSERT INTO file_sources` 是否真的成功
2. `file_id` 是否查对

---

## 17. 最简操作清单

如果你只想看最短步骤，就按下面做：

1. 在虚拟机装好 MySQL，并允许本地 WSL2 远程连它
2. 本地 WSL2 和虚拟机都准备同版本 WindCloud 代码
3. 本地配置指向虚拟机 MySQL，`ip=127.0.0.1`
4. 虚拟机配置指向自己的 MySQL，`ip=虚拟机实际IP`
5. 两边都启动 `./bin/server_app`
6. 本地启动 `./bin/client_app`
7. 本地上传一个测试文件
8. 把本地 `test/server_files/<sha256文件>` 复制到虚拟机的 `test/server_files/`
9. 往数据库里补一条虚拟机的数据源记录
10. 本地删除测试文件，再执行 `gets`
11. 看本地和虚拟机两边日志是否都处理了本次下载
12. 最后比对下载结果哈希

---

## 18. 一句话总结

这次最简单、最容易理解的双实例联调方式就是：

> 本地 WSL2 跑客户端和服务端 A，虚拟机跑 MySQL 和服务端 B，两台服务端共用同一个数据库、各自保存一份同名真实文件，然后由本地客户端发起 `gets` 来验证双数据源下载。
