## 4. 区间票据改动记录

## 4.1 改动目的

第四期的一次性票据只绑定：

1. 用户 id
2. 命令类型
3. 完整虚拟路径

第五期后，这已经不够了。

因为多点下载里的每个分片，还必须绑定：

1. 分片起始位置
2. 分片结束位置
3. 允许连接的数据源服务器 IP
4. 允许连接的数据源服务器端口

否则客户端就可以随意修改分片请求范围，或者拿同一张票据去连接别的服务器。

## 4.2 改动内容

本次扩展了传输票据的负载字段。

当前传输票据中额外包含：

1. `start`
2. `end`
3. `sip`
4. `sport`

对应改造包括：

1. `jwt_create_transfer_ticket()`
2. `jwt_verify_transfer_ticket()`
3. `issue_transfer_ticket()`
4. `verify_and_consume_transfer_ticket()`

当前效果是：

1. 控制服务器为每个下载分片单独签发票据
2. 票据被传输服务器消费时，会同时校验用户、路径、区间和目标服务器

## 6. 控制连接协商改动记录

## 6.1 改动目的

第四期中，控制连接上的 `gets` 只做一件事：

1. 直接申请一次性传输票据

第五期后，`gets` 的控制连接流程改成两步：

1. 先申请多点下载方案
2. 再为每个分片申请区间票据

因此 `session.c` 需要新增新的控制层处理逻辑。

## 6.2 改动内容

本次在会话层新增了：

1. `parse_gets_range_ticket_request()`
2. `load_available_sources_for_file()`
3. `is_requested_source_allowed()`
4. `handle_multi_gets_plan()`
5. `handle_gets_range_ticket_prepare()`

当前控制连接职责变化如下：

### `CMD_TYPE_GETS`

负责：

1. 校验目标文件是否存在
2. 查询文件 hash 和文件大小
3. 查询可用数据源列表
4. 返回 `multi_gets_plan_packet_t`

### `CMD_TYPE_GETS_RANGE`

负责：

1. 解析客户端发来的分片区间和目标数据源
2. 校验该数据源是否在可用列表中
3. 为当前分片签发区间票据

## 7. 服务端下载链路改动记录

## 7.1 改动目的

第四期的下载链路只支持：

1. 从某个偏移位置开始
2. 一直发送到文件末尾

第五期的多点下载需要服务端支持：

1. 只发送某个固定区间
2. 客户端对这个区间内部继续做断点续传

所以下载发送端必须从“整文件发送”改成“整文件或指定区间发送”。

## 7.2 改动内容

本次把下载逻辑改造成：

1. `handle_gets()` 继续负责完整文件下载
2. 新增 `handle_gets_range()` 负责区间下载
3. 内部统一复用 `handle_gets_common()`

在区间下载模式下：

1. 服务端先把“本区间总长度”发给客户端
2. 客户端回传的 `offset` 表示“本分片已经完成的字节数”
3. 服务端再把这个相对偏移换算成真实文件里的绝对偏移位置
4. 最终只发送 `[range_start, range_end]` 这一段

无论小文件 `sendfile` 还是大文件 `mmap`，都已经支持这种区间发送方式。

## 10. 客户端多点下载与本地任务记录改动记录

## 10.1 改动目的

这是第五期最核心的一部分。

客户端的 `gets` 不再是：

1. 一个传输线程
2. 一条传输连接
3. 一个完整文件

而是改成：

1. 一个后台管理线程
2. 多个分片下载线程
3. 多个独立传输连接
4. 本地元数据文件记录进度

## 10.2 改动内容

本次新增了元数据模块：

1. `MultipartPartInfo`
2. `MultipartTaskMeta`
3. `multipart_task_prepare()`
4. `multipart_task_sync_progress()`
5. `multipart_task_cleanup()`

元数据模块负责：

1. 创建 `.multipart/<file_hash>` 任务目录
2. 生成 `meta.ini`
3. 记录每个分片的：
   - 起始位置
   - 结束位置
   - 已完成字节数
   - 对应数据源地址
4. 下次继续执行 `gets` 时恢复已有下载进度

同时客户端下载模块被整体改造：

1. 新增 `GetsPartTask`
2. 新增 `GetsManagerTask`
3. 新增 `run_gets_part_transfer()`
4. 新增 `gets_part_thread_func()`
5. 新增 `merge_part_files()`
6. 新增 `all_parts_finished()`
7. 新增 `gets_manager_thread_func()`

当前 `handle_gets_command()` 的流程变为：

1. 申请多点下载方案
2. 准备本地任务目录和元数据
3. 刷新已有分片进度
4. 为尚未完成的分片逐个申请区间票据
5. 创建后台管理线程
6. 后台管理线程再并发创建多个分片下载线程
7. 所有分片完成后合并文件
8. 计算最终文件 hash 做校验
9. 校验通过后清理分片临时文件和元数据

## 12. 当前限制与说明

虽然第五期第一版核心代码已经完成，但当前仍需注意以下几点：

1. 本次已完成编译验证，但还没有做完整的多服务器联调记录。
2. `file_sources` 当前只会在上传成功后自动登记当前服务器，跨服务器副本同步仍然不在本期范围内。
3. 多点下载恢复依赖客户端本地 `.multipart` 目录和 `meta.ini`，没有使用数据库记录客户端下载任务。
4. 当前多点下载分片策略固定为“按数据源数量平均切分”，还没有做动态重分片。
5. 如果数据源列表变化，客户端会按最新方案重建任务元数据，不做复杂迁移。
