# 服务端源码目录结构说明

## 1. 调整目的

当前项目已经进入第五期，`src/server` 下的代码文件数量明显增多。  
如果继续把所有 `.c` 文件都平铺在一个目录里，查找入口、定位职责、阅读调用关系都会越来越费劲。

因此，本次把 `src/server` 按职责拆成了多个子目录。这样处理后：

1. 查看服务端主流程时，优先看 `core`
2. 查看网络和并发基础设施时，优先看 `net`
3. 查看数据库和 DAO 时，优先看 `data`
4. 查看文件命令和文件传输时，优先看 `file`
5. 查看认证和票据时，优先看 `security`

## 2. 新目录结构

```text
src/server/

│   ├── session.c

```

## 3. 各目录职责

### 3.1 `core`

这一层放“服务端运行主链路”上的核心文件。

- `server.c`
  负责服务端启动、读取配置、创建监听套接字、初始化线程池、初始化控制连接管理和事件循环。
- `session.c`
  负责控制连接命令分发、传输连接票据校验、把请求转给具体业务处理函数。
- `worker.c`
  负责线程池工作线程，处理传输连接任务。

如果要理解“客户端请求到底是怎么走进服务端的”，应该先看这一层。

### 3.2 `net`

这一层放网络通信和并发基础设施。

- `control_conn.c`
  负责控制连接对象管理。
- `epoll.c`
  负责 `epoll` 相关封装。
- `queue.c`
  负责任务队列。
- `server_socket.c`
  负责监听套接字创建。
- `thread_pool.c`
  负责线程池初始化与线程管理。
- `time_wheel.c`
  负责控制连接超时踢出。

如果要理解“连接怎么被接收、保存、分发、超时处理”，应该看这一层。

### 3.3 `data`

这一层放数据库初始化、数据库连接池和 DAO。

- `db_init.c`
  负责建库建表。
- `db_pool.c`
  负责数据库连接池。
- `dao_user.c`
  负责用户表查询和写入。
- `dao_vfs.c`
  负责虚拟文件系统路径节点。
- `dao_file.c`
  负责真实文件记录。
- `dao_file_source.c`
  负责第五期新增的数据源服务器记录。

如果要理解“某个路径、某个文件、某个用户的数据到底怎么查出来”，应该看这一层。

### 3.4 `file`

这一层放文件业务逻辑。

- `file_cmds.c`
  负责 `pwd/cd/ls/mkdir/touch/rm/rmdir`
- `file_transfer.c`
  负责 `puts/gets`、断点续传、秒传、多点下载的区间发送
- `path_utils.c`
  负责路径相关工具函数

如果要理解“文件相关命令到底怎么执行”，应该主要看这一层。

### 3.5 `security`

这一层放认证与票据相关逻辑。

- `auth.c`
  负责登录、注册、密码校验、登录 JWT 返回。
- `transfer_ticket.c`
  负责一次性传输票据的签发、校验、消费。
- `server_identity.c`
  负责读取当前服务器自己的地址信息。

如果要理解“用户身份怎么确认、票据怎么限制传输连接”，应该看这一层。

## 4. 为什么没有继续拆 `src/client`

当前 `src/client` 只有 6 个 `.c` 文件，数量还不算多：

- `client.c`
- `client_command_handle.c`
- `client_gets.c`
- `client_puts.c`
- `client_socket.c`
- `multipart_meta.c`

这一部分暂时继续保持单层结构，查找成本还不高。  
后续如果客户端继续扩展，例如再加入上传分片管理、更多状态模块、更多网络封装，再考虑进一步拆分会更合适。

## 5. 构建脚本同步调整

原来的 `Makefile` 只会编译 `src/server/*.c` 这一层。  
服务端拆成子目录后，`Makefile` 已同步改成递归查找 `src/server` 下的全部 `.c` 文件。

也就是说，后续如果继续在 `src/server` 下新增新的功能子目录，只要文件还是 `.c`，默认就能被编译进去。
