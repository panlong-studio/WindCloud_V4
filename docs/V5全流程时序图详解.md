# WindCloud_V5 全流程时序图详解

## 1. 文档目标

这份文档用**时序图**解释 V5 代码中的关键交互顺序。

这三份“全流程图解”文档的分工如下：

1. [V5全流程活动图详解.md](/home/liwenshuo/my_project/WindCloud_V4/docs/V5全流程活动图详解.md)
   重点看流程骨架、判断分支和循环结构。
2. [V5全流程时序图详解.md](/home/liwenshuo/my_project/WindCloud_V4/docs/V5全流程时序图详解.md)
   重点看模块交互顺序、协议包顺序和调用顺序。
3. `V5全流程状态图详解.md`
   重点看核心对象的状态变化和状态切换条件。

如果说活动图主要回答的是：

- 先做什么
- 后做什么
- 在哪里分支

那么时序图主要回答的是：

- 是谁先调用了谁
- 是谁先给谁发送了什么数据
- 某一步完成后，下一步由哪个模块继续接手
- 某个失败分支在哪一侧被发现，又是如何返回的

本文会把 V5 的时序拆成下面这些核心场景：

1. 客户端登录成功并接收 JWT
2. 客户端注册
3. 一条普通短命令的完整交互
4. `cd` 成功后客户端和服务端如何同步路径
5. `puts` 在控制连接上申请一次性票据
6. `puts` 上传的完整交互
7. `puts` 的秒传分支
8. `puts` 的续传 / 中断分支
9. `gets` 在控制连接上申请多点下载方案
10. `gets` 为每个分片申请区间票据
11. `gets` 单个分片下载的完整交互
12. 下载管理线程合并和恢复流程
13. 控制连接超时断开
14. 服务端退出时主线程与工作线程的协作

本文主要对照这些代码：

- `src/client/client.c`
- `src/client/client_command_handle.c`
- `src/client/client_puts.c`
- `src/client/client_gets.c`
- `src/client/multipart_meta.c`
- `src/server/core/server.c`
- `src/server/core/session.c`
- `src/server/core/worker.c`
- `src/server/file/file_transfer.c`
- `src/server/security/auth.c`
- `src/server/security/transfer_ticket.c`
- `src/server/data/dao_vfs.c`
- `src/server/data/dao_file.c`

- `src/common/protocol.c`

## 2. 阅读时序图的方法

### 2.1 先看参与者，再看消息

Mermaid 的 `sequenceDiagram` 里最重要的是两件事：

1. 左右有哪些参与者
2. 这些参与者之间按什么顺序传递消息

在本文里，常见参与者有：

- `U`：用户输入
- `CMain`：客户端主线程
- `CPut`：客户端上传线程
- `CGetMgr`：客户端下载管理线程
- `CGetPart`：客户端分片下载线程
- `CtrlConn`：客户端控制连接
- `TransConn`：客户端独立传输连接
- `SMain`：服务端主线程
- `Sess`：`session.c`
- `Auth`：`auth.c`
- `Ticket`：`transfer_ticket.c`
- `Worker`：工作线程
- `FT`：`file_transfer.c`
- `VFS`：`dao_vfs.c`
- `DF`：`dao_file.c`
- `FSrc`：`dao_file_source.c`
- `DB`：MySQL
- `Disk`：`test/server_files/<sha256>` 里的真实文件
- `Meta`：`.multipart` 元数据文件

### 2.2 时序图和活动图的关系

活动图文档偏重：

- 流程骨架
- 判断分支
- 循环结构

这一份时序图文档偏重：

- 消息顺序
- 协议包顺序
- 模块交接顺序

可以把两份文档配合起来读：

1. 先用活动图确定流程大方向
2. 再用时序图看这条链里每一步是谁和谁交互

图中的背景色按阶段区分：蓝色多用于入口和控制请求，黄色用于连接建立或准备动作，绿色用于认证、票据和正常业务处理，紫色用于数据读写或数据库协作，红色用于关闭、失败或收尾。

## 3. 登录成功并接收 JWT 时序图

这是 V5 所有后续链路的起点。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CtrlConn as 控制连接
    participant SMain as 服务端主线程
    participant Sess as dispatch_control_command
    participant Auth as handle_login
    participant DBU as dao_user
    participant DB as MySQL
    participant JWT as jwt_create_for_user

    rect rgba(220, 235, 255, 0.35)
    U->>CMain: 输入 login 用户名/密码
    CMain->>CMain: process_command()
    CMain->>CtrlConn: send command_packet_t(LOGIN, "用户名/密码")
    CtrlConn->>SMain: recv_command_packet()
    SMain->>Sess: dispatch_control_command()
    Sess->>Auth: handle_login()
    Auth->>DBU: dao_get_user_by_name()
    DBU->>DB: SELECT users(id, password_hash, salt)
    DB-->>DBU: 返回用户记录
    DBU-->>Auth: 返回 user_id / hash / salt
    Auth->>Auth: hash_password_with_salt()
    Auth->>JWT: jwt_create_for_user(user_id)
    JWT-->>Auth: 返回 token
    Auth-->>CtrlConn: send auth_reply_packet_t(success, user_id, message, token)
    Sess->>Sess: ctx.current_path = "/"
    Sess->>Sess: ctx.current_dir_id = 0
    CtrlConn-->>CMain: recv_auth_reply_packet()
    CMain->>CMain: set_login_success_state()
    end
```

### 3.1 这条时序最关键的四件事

#### A. 登录成功后只返回一包 `auth_reply_packet_t`

和 V4 不同，V5 登录成功后不再是：

1. 先回文本响应
2. 再回独立 token 包

而是直接一次返回：

```c
auth_reply_packet_t
```

里面同时包含：

1. `success`
2. `user_id`
3. `message`
4. `token`

#### B. JWT 是登录态的一部分

客户端登录成功后会保存：

1. `logged_in = 1`
2. `user_id`
3. `token`
4. `current_path = "/"`

后续控制连接不会每次都显式发 JWT，但传输票据签发前必须先经过这条登录链。

#### C. 登录成功时，服务端会同时初始化目录状态

在 `dispatch_control_command()` 里，首次登录成功后会执行：

```c
strcpy(ctx->current_path, "/");
ctx->current_dir_id = 0;
```

这一步很重要，因为：

1. 后续控制连接短命令要依赖所在目录
2. 后续传输票据要根据所在目录拼完整虚拟路径

## 4. 注册命令时序图

注册没有 JWT，下图可以和登录流程对照看。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CtrlConn as 控制连接
    participant SMain as 服务端主线程
    participant Sess as dispatch_control_command
    participant Auth as handle_register
    participant DBU as dao_user
    participant DB as MySQL

    rect rgba(220, 235, 255, 0.35)
    U->>CMain: 输入 register 用户名/密码
    CMain->>CtrlConn: send command_packet_t(REGISTER, "用户名/密码")
    CtrlConn->>SMain: recv_command_packet()
    SMain->>Sess: dispatch_control_command()
    Sess->>Auth: handle_register()
    Auth->>Auth: generate_salt()
    Auth->>Auth: hash_password_with_salt()
    Auth->>DBU: dao_insert_user()
    DBU->>DB: INSERT INTO users
    DB-->>DBU: 插入结果
    Auth->>DBU: dao_get_user_by_name()
    DBU->>DB: SELECT id
    DB-->>DBU: 返回新用户记录
    Auth-->>CtrlConn: send_msg("注册成功！请继续登录。")
    CtrlConn-->>CMain: recv_server_reply()
    end
```

### 4.1 为什么注册不下发 JWT

因为项目里：

> JWT 代表“已经通过登录校验的会话身份”

注册只是创建用户，并不代表已经进入登录态。
因此注册成功后，客户端仍停留在登录菜单，而不是直接进入已登录主循环。

## 5. 普通短命令时序图

下面先用 `pwd` 作为最简单的短命令例子。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CtrlConn as 控制连接
    participant SMain as 服务端主线程
    participant Sess as dispatch_control_command
    participant Biz as handle_pwd
    participant Wheel as time_wheel_refresh

    rect rgba(220, 235, 255, 0.35)
    U->>CMain: 输入 pwd
    CMain->>CMain: process_command()
    CMain->>CtrlConn: send command_packet_t(PWD, "")
    CtrlConn->>SMain: recv_command_packet()
    SMain->>Sess: dispatch_control_command()
    Sess->>Biz: handle_pwd(client_fd, &ctx)
    Biz-->>CtrlConn: send_msg(current_path)
    SMain->>Wheel: time_wheel_refresh()
    CtrlConn-->>CMain: recv_server_reply()
    CMain->>U: 输出当前路径
    end
```

### 5.1 这条链路的关键点

#### A. 短命令不会进入线程池

V5 中，控制连接上的：

- `pwd`
- `ls`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

都是主线程在 `handle_control_event()` 里直接收包，再交给 `dispatch_control_command()` 处理。

#### B. 短命令处理完成后会刷新时间轮

这表示：

> 一条普通短命令本身就代表“这个控制连接最近有活动”

因此，超时位置要往后顺延。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CtrlConn as 控制连接
    participant SMain as 服务端主线程
    participant Sess as dispatch_control_command
    participant Biz as handle_cd

    participant DB as MySQL

    rect rgba(220, 235, 255, 0.35)
    U->>CMain: 输入 cd doc
    CMain->>CtrlConn: send command_packet_t(CD, "doc")
    CtrlConn->>SMain: recv_command_packet()
    SMain->>Sess: dispatch_control_command()
    Sess->>Biz: handle_cd()
    Biz->>VFS: dao_get_node_by_path(target_path)
    VFS->>DB: SELECT id, type FROM paths
    DB-->>VFS: 返回目录节点
```

### 6.1 为什么 `cd` 要两边都更新

服务端更新是为了后续业务正确执行。
客户端更新是为了后续：

1. `puts` 申请传输票据
2. `gets` 申请下载方案

都能基于正确的远端目录拼出完整虚拟路径。

## 7. `puts` 在控制连接上申请一次性票据

这张图对应 `request_transfer_ticket()` 和服务端 `handle_transfer_prepare()`。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CtrlConn as 控制连接
    participant SMain as 服务端主线程
    participant Sess as dispatch_control_command
    participant Prep as handle_transfer_prepare
    participant SID as server_identity
    participant Ticket as issue_transfer_ticket
    participant JWT as jwt_create_transfer_ticket

    rect rgba(220, 235, 255, 0.35)
    U->>CMain: 输入 puts a.txt
    CMain->>CMain: handle_puts_command()
    CMain->>CtrlConn: send command_packet_t(PUTS, "a.txt")
    CtrlConn->>SMain: recv_command_packet()
    SMain->>Sess: dispatch_control_command()
    Sess->>Prep: handle_transfer_prepare()
    Prep->>Prep: build_transfer_full_path(ctx.current_path, "a.txt")
    Prep->>SID: get_current_server_address()
    Prep->>Ticket: issue_transfer_ticket(user_id, PUTS, full_path, 0, -1, ip, port)
    Ticket->>Ticket: generate_ticket_id()
    Ticket->>JWT: jwt_create_transfer_ticket(...)
    JWT-->>Ticket: 返回 ticket 字符串
    Ticket->>Ticket: 在内存票据表登记 active ticket_id
    Ticket-->>Prep: 返回 ticket
    Prep-->>CtrlConn: send transfer_ticket_reply_packet_t(success, message, ticket)
    CtrlConn-->>CMain: recv_transfer_ticket_reply_packet()
    CMain->>CMain: 保存 ticket 给上传线程
    end
```

### 7.1 这张图的关键点

#### A. 控制连接上的 `puts` 不传文件内容

它只负责：

1. 把 `current_path + 文件名` 拼成完整虚拟路径
2. 读取本服务端地址
3. 签发一张一次性传输票据

文件内容完全不走控制连接。

#### B. 票据里不仅绑定用户和命令，还绑定目标数据源地址

也就是说，后续传输连接拿着这张票据，只能连到票据中指定的那台服务器。

## 8. `puts` 上传的完整交互

这是 V5 里最重要的图之一。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CPut as 客户端上传线程
    participant TransConn as 传输连接
    participant SMain as 服务端主线程
    participant Worker as 工作线程
    participant Sess as handle_transfer_request
    participant Ticket as verify_and_consume_transfer_ticket
    participant SID as server_identity
    participant FT as handle_puts
    participant VFS as dao_vfs
    participant DF as dao_file
    participant FSrc as dao_file_source
    participant DB as MySQL
    participant Disk as test/server_files/hash

    rect rgba(220, 235, 255, 0.35)
    U->>CMain: 输入 puts a.txt
    CMain->>CMain: handle_puts_command() 已拿到 ticket
    CMain->>CPut: 创建 detached 上传线程
    end

    rect rgba(255, 245, 210, 0.45)
    CPut->>TransConn: init_socket() 建立独立传输连接
    CPut->>TransConn: send conn_init_packet_t(CONN_ROLE_TRANSFER)
    TransConn->>SMain: recv_conn_init_packet()
    SMain->>Worker: 传输连接 fd 入队
    end

    rect rgba(225, 255, 235, 0.38)
    CPut->>TransConn: send transfer_auth_packet_t(ticket)
    Worker->>Sess: handle_transfer_request()
    Sess->>Ticket: verify_and_consume_transfer_ticket(ticket)
    Ticket->>Ticket: jwt_verify_transfer_ticket()
    Ticket->>Ticket: 查内存票据表并立刻消费
    Ticket-->>Sess: 返回 user_id / cmd_type / full_path / source_ip / source_port
    Sess->>SID: get_current_server_address()
    Sess->>Sess: 校验票据绑定地址是否等于本服务器
    Sess->>Sess: build_transfer_context()
    Sess->>FT: handle_puts(client_fd, &ctx, file_name)
    end

    rect rgba(243, 236, 255, 0.38)
    CPut->>CPut: 计算本地文件 SHA-256
    CPut->>FT: send file_packet_t(PUTS, file_size, hash)
    FT->>VFS: dao_get_node_by_path(检查重名)
    VFS->>DB: SELECT paths(id, type)
    DB-->>VFS: 返回是否重名
    alt 目标目录下已经有同名文件
        FT-->>CPut: send file_packet_t(offset=file_size)
        FT-->>CPut: send_msg("错误：该文件已存在")
    else 允许继续上传
        FT->>DF: dao_file_find_by_sha256()
        DF->>DB: SELECT files(id, size)
        DB-->>DF: 返回是否已有相同 hash
        FT->>Disk: 打开或检查 test/server_files/hash
        FT-->>CPut: send file_packet_t(offset=服务端已有大小 或 hash=相同 hash)

        alt 服务端返回相同 hash
            CPut->>U: 输出 极速秒传成功
        else 进入正常上传 / 续传
            CPut->>CPut: 从 offset 定位本地文件
            CPut->>FT: send 剩余文件内容
            FT->>Disk: 写入真实文件
            FT->>DF: 插入或复用 files 记录
            DF->>DB: INSERT files 或 SELECT/UPDATE files
            FT->>VFS: dao_create_file_node()
            VFS->>DB: INSERT paths
            FT->>SID: get_current_server_address()
            FT->>FSrc: dao_file_source_upsert(file_id, ip, port)
            FSrc->>DB: INSERT ... ON DUPLICATE KEY UPDATE file_sources
            FT-->>CPut: send_msg("上传完成！")
        end
    end
    end

    rect rgba(255, 230, 230, 0.38)
    Worker->>TransConn: shutdown + close
    end
```

## 8.1 为什么 `puts` 的时序要分成“主线程接入”和“工作线程执行”

因为 V5 的实现明确分成了两层：

### 第一层：主线程做连接角色分流

主线程只负责：

1. 收 `conn_init_packet_t`
2. 判断这是控制连接还是传输连接
3. 把传输连接 fd 投递给线程池

### 第二层：工作线程执行传输

工作线程负责：

1. 收 `transfer_auth_packet_t`
2. 校验并消费一次性票据
3. 恢复传输上下文
4. 进入 `handle_puts()`

这和 V4 明显不同，V5 不再需要“主线程先 peek 再收 auth 包再构造任务”的那一套。

## 9. `puts` 秒传分支时序图

秒传是 `puts` 的一个重要分支，单独拆出来更容易理解。

```mermaid
sequenceDiagram
    participant CPut as 客户端上传线程
    participant FT as handle_puts
    participant VFS as dao_vfs
    participant DF as dao_file
    participant FSrc as dao_file_source
    participant DB as MySQL
    participant Disk as test/server_files/hash

    rect rgba(220, 235, 255, 0.35)
    CPut->>FT: send file_packet_t(file_size, hash)
    FT->>VFS: 检查目标目录是否已重名
    VFS->>DB: SELECT paths(id, type)
    DB-->>VFS: 不重名
    FT->>DF: dao_file_find_by_sha256(hash)
    DF->>DB: SELECT files(id, size)
    DB-->>DF: 返回 file_id / size
    FT->>Disk: check_store_file_ready(hash, size)
    alt 校验过程异常
        FT-->>CPut: send_msg("秒传失败：服务端无法校验真实文件")
    else 真实文件存在且大小匹配
        FT->>VFS: dao_create_file_node(user_id, path, file_id)
        VFS->>DB: INSERT paths
        FT->>DF: dao_file_add_ref_count(file_id)
        DF->>DB: UPDATE files SET count=count+1
        FT-->>CPut: send file_packet_t(hash=客户端 hash)
        CPut->>CPut: 比较 hash 相等
        CPut->>CPut: 识别为秒传成功
    else 真实文件缺失或不完整
        FT-->>CPut: send file_packet_t(offset=服务端已有大小)
        CPut->>CPut: 进入正常上传 / 续传流程
    end
    end
```

### 9.1 秒传不只看数据库

服务端不会因为 `files` 表里查到相同 hash，就立刻秒传。
它还会继续检查：

1. `test/server_files/<hash>` 是否存在
2. 它是不是普通文件
3. 它的大小是否和 `files.size` 一致

只有这几项都成立，才会进入秒传。

## 10. `puts` 续传 / 中断分支时序图

```mermaid
sequenceDiagram
    participant CPut as 客户端上传线程
    participant FT as handle_puts
    participant Disk as test/server_files/hash
    participant DF as dao_file
    participant VFS as dao_vfs
    participant FSrc as dao_file_source
    participant DB as MySQL

    rect rgba(220, 235, 255, 0.35)
    CPut->>FT: send file_packet_t(total_size, hash)
    FT->>Disk: open(hash 文件)
    FT->>Disk: fstat 读取 local_size
    alt local_size 大于 total_size
        FT->>Disk: ftruncate(0)
        FT->>Disk: local_size 重置为 0
    end
    FT-->>CPut: send file_packet_t(offset=local_size)
    CPut->>CPut: lseek 到 local_size
    alt remaining <= 0
        FT->>DF: 插入或复用 files 记录
        DF->>DB: INSERT files 或 SELECT files
        FT->>VFS: dao_create_file_node()
        VFS->>DB: INSERT paths
        FT->>FSrc: dao_file_source_upsert()
        FSrc->>DB: INSERT ... ON DUPLICATE KEY UPDATE file_sources
        FT-->>CPut: send_msg("上传完成！")
    else 还需要继续传数据
        alt file_len == 0
            FT->>DF: 插入或复用 files 记录
            DF->>DB: INSERT files 或 SELECT files
            FT->>VFS: dao_create_file_node()
            VFS->>DB: INSERT paths
            FT->>FSrc: dao_file_source_upsert()
            FSrc->>DB: INSERT ... ON DUPLICATE KEY UPDATE file_sources
            FT-->>CPut: send_msg("上传完成！")
        else 进入正常续传循环
            FT->>Disk: ftruncate(file_len)
            loop remaining > 0
                CPut->>FT: send 文件内容块
                FT->>Disk: recv + write 或 mmap 写入
            end
            alt 中途断开，未收满 remaining
                FT->>Disk: ftruncate(local_size + received_count)
                FT-->>CPut: send_msg("传输中断，已保存当前进度。")
            else 全部收满
                FT->>DF: 插入或复用 files 记录
                DF->>DB: INSERT files 或 SELECT files
                FT->>VFS: dao_create_file_node()
                VFS->>DB: INSERT paths
                FT->>FSrc: dao_file_source_upsert()
                FSrc->>DB: INSERT ... ON DUPLICATE KEY UPDATE file_sources
                FT-->>CPut: send_msg("上传完成！")
            end
        end
    end
    end
```

### 10.1 为什么中断后还要 `ftruncate`

因为服务端在接收前可能已经：

```c
ftruncate(file_fd, file_len);
```

把文件扩展到了目标总大小。
如果中途断开却不把它截回真实收到的位置，就会留下尾部空洞或脏内容。

## 11. `gets` 在控制连接上申请多点下载方案

这是第五期新增的重要时序。

```mermaid
sequenceDiagram
    participant U as 用户
    participant CMain as 客户端主线程
    participant CtrlConn as 控制连接
    participant SMain as 服务端主线程
    participant Sess as dispatch_control_command
    participant Plan as handle_multi_gets_plan
    participant VFS as dao_vfs
    participant DF as dao_file
    participant FSrc as dao_file_source
    participant DB as MySQL

    rect rgba(220, 235, 255, 0.35)
    U->>CMain: 输入 gets report.pdf
    CMain->>CMain: handle_gets_command()
    CMain->>CtrlConn: send command_packet_t(GETS, "report.pdf")
    CtrlConn->>SMain: recv_command_packet()
    SMain->>Sess: dispatch_control_command()
    Sess->>Plan: handle_multi_gets_plan()
    Plan->>Plan: build_transfer_full_path()
    Plan->>VFS: dao_get_file_info_by_path(user_id, full_path)
    VFS->>DB: SELECT paths 获取 node_id 和 file_id
    DB-->>VFS: 返回 file_id
    Plan->>DF: dao_file_get_info_by_id(file_id)
    DF->>DB: SELECT files 获取 sha256sum 和 size
    DB-->>DF: 返回 file_size / file_hash
    Plan->>FSrc: dao_file_source_list(file_id)
    FSrc->>DB: SELECT file_sources 可用数据源列表
    DB-->>FSrc: 返回 sources[]
    Plan-->>CtrlConn: send multi_gets_plan_packet_t(success, file_size, file_hash, sources)
    CtrlConn-->>CMain: recv_multi_gets_plan_packet()
    CMain->>CMain: 得到 file_size / file_hash / source_count
    end
```

### 11.1 这条时序的关键点

#### A. 控制连接上的 `gets` 不是“直接下载”

它现在只负责：

1. 查逻辑文件
2. 查真实文件大小和 hash
3. 查可用数据源服务器
4. 返回一份完整下载方案

#### B. `file_sources` 是第五期多点下载的关键表

没有这张表，控制服务器就不知道：

> 哪些服务器可以提供同一份真实文件

## 12. `gets` 为每个分片申请区间票据

```mermaid
sequenceDiagram
    participant CMain as 客户端主线程
    participant Meta as multipart_meta
    participant CtrlConn as 控制连接
    participant SMain as 服务端主线程

    participant VFS as dao_vfs
    participant FSrc as dao_file_source

    participant DB as MySQL

    rect rgba(220, 235, 255, 0.35)

    Meta->>Meta: 按 source_count 切分分片
    Meta->>Meta: multipart_task_sync_progress()
    end

    rect rgba(255, 245, 210, 0.45)

        CMain->>CtrlConn: send command_packet_t(GETS_RANGE, "文件名|start|end|ip|port")
        CtrlConn->>SMain: recv_command_packet()
        SMain->>Sess: dispatch_control_command()
        Sess->>Range: handle_gets_range_ticket_prepare()
        Range->>Range: parse_gets_range_ticket_request()
        Range->>Range: build_transfer_full_path()
        Range->>VFS: dao_get_file_info_by_path()

    end
    end
```

### 12.1 为什么每个分片都要单独申请票据

因为票据绑定了：

1. 用户
2. 命令类型
3. 完整路径
4. 分片区间
5. 目标数据源服务器

因此，每个分片天然都应该拿到自己的独立票据。

```mermaid
sequenceDiagram

    participant TransConn as 传输连接

    CGetPart->>TransConn: send conn_init_packet_t(CONN_ROLE_TRANSFER)
    TransConn->>SMain: recv_conn_init_packet()
    SMain->>Worker: 传输连接 fd 入队
    end

    rect rgba(255, 245, 210, 0.45)
    CGetPart->>TransConn: send transfer_auth_packet_t(ticket_i)
    Worker->>Sess: handle_transfer_request()
    Sess->>Ticket: verify_and_consume_transfer_ticket(ticket_i)
    Ticket-->>Sess: 返回 user_id / full_path / range_start / range_end / source_ip / source_port
    Sess->>SID: get_current_server_address()
    Sess->>Sess: 校验票据绑定的数据源地址

    VFS->>DB: SELECT paths(id, file_id, type)
    DB-->>VFS: 返回 file_id
    FT->>DF: dao_file_get_info_by_id(file_id)
    DF->>DB: SELECT files(sha256sum, size)
    DB-->>DF: 返回 sha256 / size
    FT->>Disk: open(test/server_files/hash)
    FT-->>CGetPart: send file_packet_t(file_size = 本分片总长度)
    CGetPart->>PartFile: stat 本地分片临时文件
    CGetPart-->>FT: send file_packet_t(offset = 已完成字节数)
    FT->>FT: offset += effective_start
    alt 分片大于 100MB
        FT-->>CGetPart: mmap 发送剩余区间
    else 分片不大于 100MB
        FT-->>CGetPart: sendfile 发送剩余区间
    end
    CGetPart->>PartFile: 写入 part_i 临时文件
    end
```

### 13.1 这条时序里最重要的两个点

#### A. V5 的分片下载仍然复用了旧的“服务端先发 file_packet，客户端再回 offset”协议骨架

因此，第五期不是重写下载协议，而是在原协议外面又包了一层：

1. 下载方案申请
2. 区间票据申请
3. 传输连接认证

#### B. 分片线程并不直接写最终文件

它只写：

```text
.multipart/<file_hash>/part_i
```

最终文件是在下载管理线程里统一合并出来的。

## 14. 下载管理线程合并和恢复时序图

```mermaid
sequenceDiagram
    participant CMain as 客户端主线程
    participant CGetMgr as 下载管理线程
    participant CGetPart as 分片线程们
    participant Meta as multipart_meta
    participant FinalFile as test/client_files/目标文件

    rect rgba(220, 235, 255, 0.35)

    CGetPart-->>CGetMgr: 各分片线程结束
```

### 14.1 为什么第五期必须单独有这张图

因为下载流程已经不再是“一个线程拉完整文件”。

而是：

1. 主线程负责申请方案和票据
2. 管理线程负责组织整轮下载
3. 分片线程负责联网收数据
4. 管理线程最后再负责合并和校验

如果不把管理线程单独画出来，就很难解释为什么：

1. 分片没下完时还能恢复
2. 最终文件不是边下边写出来的

```mermaid
sequenceDiagram
```

### 15.1 这里和 V4 的一个关键差异

V5 客户端代码里没有自动重连逻辑。
所以服务端把控制连接超时关闭后，客户端后续只会表现为：

1. 控制连接上的命令发送失败或接收失败
2. 主循环继续存在
3. 由用户决定后续如何处理

## 16. 服务端退出时主线程与工作线程的协作

```mermaid
sequenceDiagram
    participant Parent as 父进程
    participant Pipe as pipe_fd
    participant SMain as 服务端主线程
    participant Pool as 线程池
    participant Worker as 工作线程
    participant Ctrl as 控制连接们
    participant DBP as db_pool

    rect rgba(220, 235, 255, 0.35)
    Parent->>Pipe: SIGINT 后写入一个字节
    Pipe->>SMain: pipe_fd[0] 可读
    SMain->>Pool: pool.exitFlag = 1
    SMain->>Pool: 清空队列里未处理的传输连接
    SMain->>Worker: shutdown busy_fds
    SMain->>Pool: pthread_cond_broadcast()
    SMain->>SMain: close(listen_fd)
    SMain->>Ctrl: 关闭全部控制连接
    Worker-->>SMain: 各工作线程退出
    SMain->>Pool: pthread_join 全部工作线程
    SMain->>Pool: destroy_thread_pool()
    SMain->>DBP: destroy_db_pool()
    SMain->>SMain: 关闭 timerfd/epoll/pipe/log
    end
```

### 16.1 为什么退出流程也值得画时序图

因为服务端退出不是“主线程自己结束”这么简单。

它还要和：

1. 父进程
2. 管道
3. 工作线程
4. 控制连接
5. 数据库连接池

发生一整串协作，才能把进程退出做干净。

## 17. 总结

V5 的时序骨架可以概括成一句话：

> 控制连接负责登录、短命令、上传票据、下载方案和分片票据；传输连接只负责拿着一次性票据做文件传输；第五期 `gets` 又在客户端内部拆成“主线程申请方案 + 管理线程组织 + 分片线程下载 + 管理线程合并”的四段时序。
