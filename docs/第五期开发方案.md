# 第五期开发方案

## 1. 文档目标

本文档用于作为 WindCloud 项目第五期开发的正式实施方案。

后续开发统一以本文档为准，目标是：

1. 将 `docs/项目概述.md` 中第五期“多点下载”的要求，转化为可执行的技术方案。
2. 在当前第四期代码基础上，继续保持结构清晰，避免把实现做得过重。
3. 保持实现简单直观，适合当前 C 语言学习项目继续演进。

---

## 2. 第五期范围

第五期只做以下核心内容：

1. 多点下载
2. 多点下载中断后的本地任务记录
3. 基于第四期控制连接和传输连接模型的下载扩展

### 2.1 本期只增强 `gets`

第五期明确只增强：

- `gets`

不增强：

- `puts`
- `ls`
- `cd`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

原因：

1. 项目概述第五期只要求多点下载。
2. 当前第四期的上传链路已经较复杂，再把多点传输同时扩展到上传，复杂度会明显上升。
3. 先把下载分片模型做清楚，再考虑后续是否扩展到上传。

### 2.2 本期不做自动副本同步

第五期不做：

1. 服务器之间自动复制文件
2. 自动同步数据库
3. P2P 下载
4. BitTorrent 风格节点发现

本期只假设：

1. 某些服务器已经持有完整真实文件
2. 客户端可以从这些服务器并行下载不同片段

这样更符合当前学习项目节奏。

## 3. 当前第四期基线

当前项目已经具备以下基础：

1. 客户端有控制连接和传输连接的分离模型
2. `gets` 已经是“控制连接先申请票据，传输线程再下载”
3. 服务端已经可以按文件 hash 定位 `test/server_files/<sha256>`
4. 服务端已经支持普通下载和断点续传
5. 客户端已经有统一本地目录 `test/client_files`
6. 服务端已经有统一真实文件目录 `test/server_files`

这意味着第五期不需要重新设计整个连接模型，只需要在“下载任务”这一层继续扩展：

> 从单传输线程单连接下载，升级为多传输线程多连接分片下载

## 4. 第五期总体设计

## 4.1 总体原则

本期开发遵循以下原则：

1. 多点下载只在 `gets` 上生效。
2. 控制连接继续只负责短命令和下载任务协商。
3. 分片数据传输继续走独立传输连接。
4. 每个分片下载线程只负责一个固定字节区间。
5. 中断恢复先依赖客户端本地任务记录，不依赖复杂数据库事务恢复。
6. 优先支持“多个服务器都有完整文件”，不做“多个服务器各自只有部分文件”的复杂方案。

## 4.2 总体架构

第五期采用“三层职责”：

### 客户端

1. 主线程负责发起 `gets`
2. 主线程先向调度服务器申请“多点下载方案”
3. 主线程根据返回结果创建多个分片下载线程
4. 每个分片线程连接不同服务器，下载固定区间
5. 主线程等待所有分片线程完成后再合并结果

### 调度服务器

1. 接收客户端的 `gets` 请求
2. 查询目标文件的基础信息
3. 查询哪些服务器拥有该文件
4. 返回“文件信息 + 可用数据源列表”

### 数据源服务器

1. 接收客户端分片下载请求
2. 校验本次下载票据
3. 根据客户端要求发送指定字节区间

---

## 5. 核心设计决策

## 5.1 第五期采用“调度服务器 + 数据源服务器”模型

本期不采用：

- 客户端自己盲连多个服务器试探

本期采用：

1. 客户端先连当前登录的控制服务器
2. 控制服务器返回可用数据源列表
3. 客户端再去连接这些数据源服务器下载分片

原因：

1. 当前项目已经有控制连接模型，复用最自然。
2. 客户端不需要自己维护全网服务器清单。
3. 权限校验、文件存在性校验都更容易集中处理。

## 5.2 第五期采用“每个数据源服务器都持有完整文件”的简化模型

本期不采用：

- 服务器 A 持有前半段，服务器 B 持有后半段

本期采用：

- 每个可用数据源服务器都持有完整文件

客户端只是让不同服务器发送不同区间。

原因：

1. 当前服务端真实文件就是按 hash 存完整实体。
2. 这样可以直接复用当前真实文件定位逻辑。
3. 不需要为第五期再引入复杂的分布式块管理。

## 5.3 第五期先不做自动合并到正式文件

本期下载过程中，建议先写到：

1. `test/client_files/.multipart/任务目录/part_0`
2. `test/client_files/.multipart/任务目录/part_1`
3. `test/client_files/.multipart/任务目录/meta`

等所有分片都成功后，再按顺序合并到：

- `test/client_files/目标文件名`

原因：

1. 分片独立写文件最容易理解。
2. 失败恢复时不容易把正式文件写乱。
3. 合并逻辑更直观。

## 5.4 第五期中断恢复采用“本地任务元数据文件”

本期不采用：

- 客户端内存里记住状态，退出后丢失
- 用数据库记录客户端下载任务

本期采用：

- 本地元数据文件记录分片进度

元数据文件建议放在：

- `test/client_files/.multipart/<任务编号>/meta.ini`

记录内容建议包括：

1. 文件名
2. 文件总大小
3. 文件 hash
4. 分片总数
5. 每个分片负责的起止位置
6. 每个分片当前已完成字节数
7. 每个分片对应的数据源服务器地址

原因：

1. 最直观
2. 最容易调试
3. 符合项目概述里“客户端本地需要记录多点下载信息”的要求

## 5.5 第五期继续复用一次性票据机制

本期不采用：

- 客户端直接拿登录 JWT 去连所有数据源服务器

本期采用：

1. 控制服务器签发“分片下载票据”
2. 每个分片线程使用自己的票据连接对应数据源服务器

票据中建议包含：

1. `user_id`
2. `file_hash`
3. `full_path`
4. `range_start`
5. `range_end`
6. `source_server_ip`
7. `source_server_port`
8. `expire`
9. `ticket_id`

原因：

1. 当前项目已经有票据机制，继续复用最自然。
2. 每个分片票据绑定固定区间，权限边界更清楚。
3. 可以避免客户端随意修改请求区间。

## 6. 协议与数据结构规划

## 6.1 新增的数据源信息结构

建议新增：

```c
typedef struct {
    char ip[64];
    char port[16];
} source_server_t;
```

职责：

1. 描述一个可用数据源服务器
2. 供控制服务器返回给客户端

## 6.2 新增多点下载协商响应结构

建议新增：

```c
#define MAX_SOURCE_SERVER_COUNT 8

typedef struct {
    int success;
    off_t file_size;
    char file_name[FILE_NAME_LEN];
    char file_hash[64];
    int source_count;
    source_server_t sources[MAX_SOURCE_SERVER_COUNT];
    char message[256];
} multi_gets_plan_packet_t;
```

职责：

1. 返回文件大小
2. 返回文件 hash
3. 返回当前可用的数据源列表

## 6.3 新增分片下载认证结构

建议新增：

```c
typedef struct {
    char ticket[TRANSFER_TICKET_LEN];
    off_t range_start;
    off_t range_end;
} range_auth_packet_t;
```

职责：

1. 携带分片票据
2. 携带请求区间

## 6.4 新增客户端分片任务结构

建议新增：

```c
typedef struct {
    int part_index;
    off_t range_start;
    off_t range_end;
    off_t finished_bytes;
    char ip[64];
    char port[16];
    char ticket[TRANSFER_TICKET_LEN];
    char part_file_path[MAX_PATH_LEN];
} DownloadPartTask;
```

职责：

1. 描述一个分片线程该做什么
2. 支撑中断恢复

## 7. 服务端模块设计

## 7.1 控制服务器新增“多点下载协商”

当前 `gets` 是：

1. 直接申请一次性票据
2. 再启动单线程下载

第五期改成：

1. 控制连接先请求多点下载方案
2. 服务端返回文件信息和数据源列表
3. 客户端按列表拆分任务
4. 再逐个申请分片票据，或者一次返回全部分片票据

本期更建议采用：

> 先返回数据源列表，再由客户端按分片结果逐个申请票据

原因：

1. 客户端自己决定分几片更灵活。
2. 服务端协议更简单。
3. 便于后续调整分片策略。

## 7.2 数据源服务器新增“按区间发送”

当前 `handle_gets()` 是：

- 按续传偏移发送“直到文件末尾”

第五期需要补充：

1. 校验 `range_start`
2. 校验 `range_end`
3. 只发送 `[range_start, range_end]` 这一段

因此下载发送函数需要新增“指定区间发送”的能力。

无论小文件 `sendfile` 还是大文件 `mmap`，都要支持：

1. 起始偏移
2. 结束偏移
3. 本次区间长度

## 7.3 数据源登记方式

第五期最简单的做法，不是自动发现服务器，而是：

1. 新增一张数据源表
2. 记录某个文件 hash 对应哪些服务器有完整实体

建议增加一张表，例如：

```sql
CREATE TABLE file_sources (
    id INT PRIMARY KEY AUTO_INCREMENT,
    file_id INT NOT NULL,
    server_ip VARCHAR(64) NOT NULL,
    server_port VARCHAR(16) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1
);
```

说明：

1. 这张表只描述“哪个服务器有这个文件”
2. 本期不要求自动维护同步关系
3. 可以先通过初始化脚本或测试接口手动插入数据

这样足以支撑第五期多点下载。

## 8. 客户端模块设计

## 8.1 客户端新增多点下载调度流程

客户端执行 `gets 文件名` 时，整体流程改成：

1. 通过控制连接请求多点下载方案
2. 拿到文件总大小和数据源列表
3. 根据数据源数量决定分片数量
4. 生成本地任务目录和元数据文件
5. 为每个分片申请票据
6. 创建多个分片下载线程
7. 等待所有线程完成
8. 合并分片文件
9. 校验最终文件大小和 hash
10. 成功后删除中间分片和元数据

## 8.2 分片策略

第五期第一版建议采用最简单策略：

1. 分片数 = 可用数据源数
2. 按文件总大小平均切分
3. 最后一个分片负责剩余字节

例如文件大小 `1000` 字节，3 个数据源：

1. `part0: 0 - 332`
2. `part1: 333 - 665`
3. `part2: 666 - 999`

优点：

1. 实现简单
2. 调试方便
3. 对当前项目足够

## 8.3 客户端本地目录组织

建议在 `test/client_files` 下新增隐藏目录：

- `test/client_files/.multipart`

每个下载任务使用一个子目录，例如：

- `test/client_files/.multipart/<file_hash>`

目录中保存：

1. `meta.ini`
2. `part_0`
3. `part_1`
4. `part_2`

这样不会影响用户最终看到的正式文件目录。

## 8.4 中断恢复策略

如果客户端下载过程中断开，下次再次执行相同 `gets`，客户端先做以下判断：

1. `test/client_files/.multipart/<file_hash>/meta.ini` 是否存在
2. 元数据中的文件名、总大小、hash 是否匹配
3. 已有分片文件大小是否与记录一致

如果匹配，则继续多点下载。

如果不匹配，则：

1. 删除旧任务目录
2. 从头开始重新多点下载

这是当前项目最直观、最安全的做法。

目标：

1. 改造当前下载发送逻辑

1. 新增分片任务结构

1. 验证中断后继续下载

## 10. 验收标准

第五期完成后，应满足以下条件：

1. 客户端对同一大文件可以同时连接多个服务器下载
2. 服务端可以按客户端请求发送指定区间
3. 客户端可以把多个分片合并成完整文件
4. 合并后的文件大小正确
5. 合并后的文件 hash 与服务端一致
6. 下载中断后，客户端再次执行 `gets` 时可以继续分片下载
7. 单服务器场景下，仍然可以退化成普通单点下载

---

## 11. 测试方案

第五期建议至少覆盖以下测试：

1. 单服务器退化下载
2. 两服务器分片下载
3. 三服务器分片下载
4. 小文件下载
5. 大文件下载
6. 下载到一半时手动终止客户端，再次下载继续恢复
7. 某个数据源服务器中途断开，观察任务失败行为
8. 合并后文件 hash 校验
9. 分片元数据损坏后的重新下载逻辑

---

## 12. 本期明确不做的内容

第五期不纳入以下内容：

1. 自动副本同步
2. 自动发现其它服务器
3. 多点上传
4. 分布式一致性
5. 数据源负载均衡
6. 动态分片重调度
7. P2P 节点互传

这些内容都明显超出当前学习项目所需复杂度。

---

## 13. 结论

第五期的本质，不是简单地把 `gets` 开成多个线程，而是让当前第四期已经建立的“双连接模型”继续往前走一步：

1. 控制连接负责协商下载方案
2. 多个传输连接负责并行拿不同分片
3. 客户端本地负责记录和恢复分片进度

对当前项目来说，最合适的第五期实现路线是：

> 先做“多服务器都有完整文件”的多源分片下载，不做自动同步，不做 P2P，不做多点上传

这样既能满足 `项目概述.md` 的第五期要求，也能保持代码仍然适合当前项目风格和学习目标。
