# WindCloud_V4 开发记录

## 1. 本次开发目标

本次开发基于 V3 原有工程继续扩展，完成了以下第四期能力：

1. 长短命令分离
2. JWT 身份校验
3. 空闲主连接超时断开
4. 客户端主连接失效后的重新登录

本次实现坚持两个原则：

1. 尽量不改动 V3 目录结构
2. 尽量复用原有 `auth`、`file_cmds`、`file_transfer`、`thread_pool`、`protocol` 模块

---

## 2. 协议层改动

### 2.1 修改文件

1. `include/protocol.h`
2. `src/common/protocol.c`

### 2.2 新增内容

新增了两个命令类型：

1. `CMD_TYPE_AUTH`
2. `CMD_TYPE_TOKEN`

新增了两个固定协议结构体：

1. `auth_packet_t`
2. `token_packet_t`

新增了对应的初始化与收发函数：

1. `init_auth_packet`
2. `send_auth_packet`
3. `recv_auth_packet`
4. `init_token_packet`
5. `send_token_packet`
6. `recv_token_packet`

### 2.3 作用

1. `auth_packet_t` 用于客户端独立传输连接发送认证信息
2. `token_packet_t` 用于服务端登录成功后向客户端下发 token

## 3. 服务端基础模块新增

### 3.1 新增文件

1. `include/jwt.h`
2. `src/server/jwt.c`
3. `include/conn_manager.h`
4. `src/server/conn_manager.c`
5. `include/time_wheel.h`
6. `src/server/time_wheel.c`

### 3.2 各模块职责

`jwt` 模块：

1. 生成 HS256 token
2. 校验 token
3. 解析 token 中的用户信息和过期时间

`conn_manager` 模块：

1. 管理主连接状态
2. 保存 `user_id`
3. 保存 `current_path`
4. 保存 `current_dir_id`
5. 保存 `token`
6. 保存连接最近活动时间

`time_wheel` 模块：

1. 维护循环槽位
2. 刷新主连接超时位置
3. 推进时间轮并找出真正超时的连接

## 4. 线程池与任务模型改动

### 4.1 修改文件

1. `include/queue.h`
2. `src/server/queue.c`
3. `src/server/worker.c`

### 4.2 改动内容

V3 中线程池队列保存的是单个 `client_fd`。  
V4 中线程池队列保存的是 `transfer_task_t`。

`transfer_task_t` 中保存了：

1. `client_fd`
2. `cmd_type`
3. `ClientContext`
4. `arg`

### 4.3 改动结果

工作线程现在不再负责“整条连接会话”，而是只负责“一次上传”或“一次下载”。

这样线程池的职责变成：

1. 只接耗时任务
2. 不再长期占住短命令主连接

---

## 5. 服务端调度模型改动

### 5.1 修改文件

1. `include/session.h`
2. `src/server/session.c`
3. `src/server/server.c`

### 5.2 `session.c` 的变化

V3 中 `session.c` 负责一条连接上的完整循环。  
V4 中 `session.c` 被拆成三类职责：

1. `send_msg`
2. `session_handle_main_command`
3. `session_build_transfer_task`
4. `session_handle_transfer_task`

### 5.3 `server.c` 的变化

V3 中服务端主线程只负责：

1. `accept`
2. 把连接加入线程池队列

V4 中服务端主线程负责：

1. `accept` 新连接
2. 把连接加入 `epoll`
3. 维护连接状态管理器
4. 维护时间轮
5. 处理短命令
6. 识别 `CMD_TYPE_AUTH` 认证连接
7. 构造传输任务并投递到线程池

### 5.4 当前主线程分流逻辑

主连接收到普通命令时：

1. 主线程接收 `command_packet_t`
2. 调用目录类或登录类处理函数
3. 更新连接状态
4. 刷新时间轮

独立传输连接到来时：

1. 主线程先看首包是不是 `CMD_TYPE_AUTH`
2. 收 `auth_packet_t`
3. 校验 token
4. 根据路径恢复目录上下文
5. 再收后续 `command_packet_t`
6. 组装成 `transfer_task_t`
7. 投递到线程池

## 6. 登录与 JWT 改动

### 6.1 修改文件

1. `src/server/session.c`

### 6.2 改动内容

登录成功后，服务端现在会：

1. 继续发送原有登录成功文字消息
2. 生成 JWT
3. 再发送一个 `token_packet_t`

这样客户端可以在不改登录命令格式的前提下，接收后续传输要用的 token。

## 7. 客户端结构改动

### 7.1 修改文件

1. `include/client_command_handle.h`
2. `src/client/client.c`
3. `src/client/client_command_handle.c`
4. `src/client/client_puts.c`
5. `src/client/client_gets.c`

### 7.2 新增客户端上下文

新增了 `ClientAppContext`，保存：

1. 主连接 `sock_fd`
2. 登录状态
3. 当前虚拟路径
4. token
5. 服务端 IP
6. 服务端端口

### 7.3 登录成功后的处理

客户端现在在登录成功后会：

1. 接收服务端普通文本响应
2. 再接收 `token_packet_t`
3. 保存 token
4. 把本地当前路径重置为 `/`

### 7.4 `cd` 成功后的处理

客户端会在 `cd` 成功后同步更新自己的 `current_path`，这样后续独立传输线程就能带上正确路径。

## 8. 客户端长短命令分离改动

### 8.1 设计变化

V3 中：

1. `puts/gets` 复用主连接
2. 执行期间主线程无法继续处理其它命令

V4 中：

1. 主连接只处理短命令
2. `puts/gets` 启动独立线程
3. 独立线程重新连接服务端
4. 独立线程先发 `auth_packet_t`
5. 然后按原有文件协议继续上传或下载

### 8.2 `client_puts.c`

上传线程会做以下事情：

1. 新建传输连接
2. 发送 `auth_packet_t`
3. 发送 `command_packet_t`
4. 发送 `file_packet_t`
5. 继续沿用原来的断点续传和秒传逻辑

### 8.3 `client_gets.c`

下载线程会做以下事情：

1. 新建传输连接
2. 发送 `auth_packet_t`
3. 发送 `command_packet_t`
4. 接收服务端文件信息
5. 继续沿用原来的断点续传逻辑

## 9. 超时断开后的客户端处理

### 9.1 修改文件

1. `src/client/client.c`

### 9.2 改动内容

当主连接因为超时被服务端断开后：

1. 客户端检测到“接收服务端响应失败”
2. 把本地状态重置为未登录
3. 重新建立主连接
4. 重新进入登录菜单

当前这一版没有做自动免密重连，而是要求用户重新登录，这样实现更稳，逻辑也更清楚。

## 10. 联调中修过的问题

### 问题一：传输连接认证失败后会导致后续文件协议错位

原因：

1. 服务端原本在认证失败时回普通文本
2. 客户端后续却按文件协议继续接收
3. 这样会读错结构体

处理：

1. 服务端在独立传输连接认证失败时不再发送普通文本
2. 关闭该连接

### 问题二：主连接超时后客户端没有回到登录态

原因：

1. 超时后主连接已被服务端关闭
2. 客户端只打印“接收服务端响应失败”
3. 没有后续恢复逻辑

处理：

1. 客户端发现主连接失效后，重置本地登录状态
2. 自动重新建立主连接
3. 重新回到登录菜单
