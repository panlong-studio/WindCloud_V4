# 第四期一次性传输票据改进说明

## 1. 文档目标

本文档用于记录本次在第四期现有实现基础上继续做的一次关键优化：

1. 控制连接继续负责短命令
2. 传输连接继续保持独立
3. 传输连接不再直接使用登录时返回的长期 JWT
4. 改成由控制连接先申请一张短时一次性传输票据，再由传输连接使用

本文档重点说明：

1. 为什么要做这次改进
2. 这次改进后的完整流程是什么
3. 具体改了哪些代码
4. 本次改动带来的实际效果
5. 当前还保留了哪些边界和后续可继续优化的点

---

## 2. 改进背景

第四期前一版已经完成了：

1. 控制连接负责短命令
2. 传输连接负责 `puts/gets`
3. 登录成功后服务端返回 JWT
4. 传输连接建立时直接携带 JWT 完成身份认证

这个方案已经能工作，但经过前面的测试发现一个明显问题：

### 旧方案的问题

控制连接超时关闭后：

1. 短命令会失效
2. 但是客户端如果还缓存着登录时拿到的 JWT，就仍然可以继续发起新的传输连接

这说明旧方案里：

- 控制连接超时，只是把“控制面”断开了
- 但“传输面”仍然可以绕过控制连接继续工作

从结构上看，这会带来两个问题：

## 2.1 登录 JWT 的职责过重

登录 JWT 原本更适合表达：

1. 用户是谁
2. 登录是否有效

但在旧方案里，它还被直接拿去做每一次上传下载的传输认证。

这样就导致：

1. 一张票据用途太宽
2. 一张票据可重复使用很多次
3. 一旦控制连接失效，旧 JWT 仍可能继续被传输线程复用

## 2.2 控制连接和传输连接的边界还不够严格

第四期的目标本来是：

- 控制连接掌控短命令和会话控制
- 传输连接只做具体文件传输

但如果传输连接可以脱离控制连接，长期直接使用旧 JWT，那么这条边界其实还不够彻底。

因此，本次继续优化的目标就是：

> 让“每一次上传下载”都必须先经过控制连接批准，才能拿到一张短时有效、只能用一次的传输票据。

---

## 3. 改进后的整体思路

本次改进后，完整思路如下：

## 3.1 控制连接仍然负责短命令

控制连接仍然负责：

1. `login`
2. `register`
3. `pwd`
4. `cd`
5. `ls`
6. `mkdir`
7. `touch`
8. `rm`
9. `rmdir`

此外，控制连接现在还新增了一个职责：

### 为 `puts/gets` 先签发一次性传输票据

也就是说：

- `puts/gets` 不再由控制连接直接传文件
- 但 `puts/gets` 需要先通过控制连接申请票据

## 3.2 传输连接仍然独立

客户端真正执行上传下载时，仍然是：

1. 主线程先发起预请求
2. 主线程拿到一次性票据
3. 客户端启动传输线程
4. 传输线程自己建立一条新的传输连接
5. 传输连接只把票据发给服务端
6. 服务端校验票据后开始真正传输

也就是说，传输连接“独立连接”的特点没有变。

## 3.3 传输连接不再直接使用登录 JWT

本次改进后，传输连接不再直接携带登录时拿到的 JWT，而是改为：

1. 控制连接先申请一次性传输票据
2. 传输线程只携带这张票据

所以现在的职责分工变成：

### 登录 JWT

负责：

1. 表示登录成功
2. 保留用户身份凭证语义

不再负责：

1. 每次上传下载的直接认证

### 一次性传输票据

负责：

1. 表示“这一次具体的 `puts/gets` 已被控制连接批准”
2. 绑定用户身份
3. 绑定命令类型
4. 绑定目标完整路径
5. 限制有效时间
6. 限制只能成功使用一次

---

## 4. 改进后的完整流程

下面以 `puts file.txt` 为例说明新流程。

## 4.1 客户端控制连接先发预请求

用户输入：

```text
puts file.txt
```

客户端不会再像旧方案那样直接启动传输线程并带着登录 JWT 去建传输连接。

而是先做：

1. 控制连接向服务端发送一个普通命令包
2. 命令类型仍然是 `CMD_TYPE_PUTS`
3. 参数是文件名 `file.txt`

此时它的语义不再是“现在就传文件”，而是：

> “我准备上传当前目录下的 `file.txt`，请先给我一张一次性传输票据。”

## 4.2 服务端控制连接签发票据

服务端收到这个预请求后，会：

1. 根据当前控制连接的 `ClientContext`
2. 结合客户端传来的文件名
3. 计算完整虚拟路径，例如 `/doc/file.txt`
4. 生成一张短时一次性传输票据
5. 把票据放进服务端票据表
6. 把票据通过专门的响应结构体返回给客户端

此时控制连接的作用就体现出来了：

- 只有控制连接仍然有效，才有资格申请这张票据

## 4.3 客户端拿到票据后再启动传输线程

客户端只有在成功收到：

```text
传输票据申请成功
```

之后，才会：

1. 创建传输线程
2. 传输线程新建独立传输连接
3. 把一次性票据发给服务端

## 4.4 服务端传输线程校验并消费票据

服务端传输线程拿到票据后，会：

1. 校验票据签名和过期时间
2. 解析出票据中的：
   - `user_id`
   - `cmd_type`
   - `full_path`
   - `ticket_id`
3. 去服务端票据表里查这个 `ticket_id`
4. 如果找到并且当前仍有效，则立即把它消费掉
5. 消费成功后，才开始真正执行 `puts/gets`

这里“消费掉”是关键点。

因为消费成功后，这张票据会立刻从票据表里移除，所以：

> 同一张票据不能再次成功使用。

---

## 5. 这次改进的直接收益

## 5.1 控制连接重新成为传输请求的必经入口

旧方案里，客户端只要还保留着登录 JWT，就可能继续直接发起传输连接。

新方案里，客户端每次发起 `puts/gets` 都必须先经过控制连接申请票据。

这意味着：

1. 控制连接失效后，无法再申请新票据
2. 控制连接失效后，新的传输任务也就无法再启动

这使“控制连接负责会话控制”的语义变得更完整。

## 5.2 传输认证范围从“长期凭证”缩小到“单次凭证”

旧方案里，一张登录 JWT 可以多次复用到很多传输连接里。

新方案里：

1. 每次上传下载都拿一张新票据
2. 每张票据绑定一次具体命令
3. 每张票据绑定一个具体目标路径
4. 每张票据只能成功使用一次

这样就把传输认证的粒度从：

- “登录后长期有效”

收紧成了：

- “本次上传或下载”

## 5.3 更符合控制面 / 传输面分离的设计目标

新方案下：

### 控制面负责

1. 短命令
2. 当前目录状态
3. 会话是否仍然活着
4. 传输请求是否允许发起

### 传输面负责

1. 真正的文件上传下载
2. 使用控制面已经批准的一次性票据

这比旧方案更符合第四期整体架构目标。

## 5.4 为后续继续增强安全控制预留了空间

有了一次性票据后，后面如果要继续增强，也更容易做：

1. 票据绑定更多元数据
2. 更短的过期时间
3. 票据黑名单
4. 传输限流
5. 更精细的审计日志

---

## 6. 具体代码改动说明

## 6.1 协议层改动

涉及文件：

- `include/protocol.h`
- `src/common/protocol.c`

### 改动点 1：传输连接认证包改成只携带一次性票据

旧版 `transfer_auth_packet_t` 里包含：

1. `cmd_type`
2. 登录 JWT
3. `full_path`
4. `file_name`

本次改成：

1. 只保留一次性传输票据 `ticket`

这样做的原因是：

1. 具体命令类型和完整路径已经在票据内部签名
2. 传输连接不需要再重复携带一套明文上下文
3. 协议更简单

### 改动点 2：新增一次性传输票据响应结构体

新增：

```c
typedef struct {
    int success;
    char message[CMD_DATA_LEN];
    char ticket[TRANSFER_TICKET_LEN];
} transfer_ticket_reply_packet_t;
```

它的作用是：

1. 控制连接收到 `puts/gets` 预请求后
2. 服务端把“票据申请成功/失败”的结果返回给客户端

### 改动点 3：新增对应的初始化、发送、接收函数

协议层同时新增了：

1. `init_transfer_ticket_reply_packet`
2. `send_transfer_ticket_reply_packet`
3. `recv_transfer_ticket_reply_packet`

这样客户端和服务端都能继续使用固定结构体完整收发，和现有项目风格保持一致。

---

## 6.2 JWT 工具层改动

涉及文件：

- `include/jwt_utils.h`
- `src/common/jwt_utils.c`

### 改动点 1：保留原有登录 JWT

原有：

1. `jwt_create_for_user`
2. `jwt_verify_and_get_user`

继续保留，用于登录成功时生成用户身份 JWT。

### 改动点 2：新增传输票据专用的签发与校验函数

新增：

1. `jwt_create_transfer_ticket`
2. `jwt_verify_transfer_ticket`

传输票据使用单独的：

1. `issuer`
2. `audience`
3. 有效期

避免和登录 JWT 混用。

### 改动点 3：传输票据中新增了 4 类 claim

传输票据里包含：

1. `uid`：用户 id
2. `cmd`：本次命令类型
3. `path`：本次完整虚拟路径
4. `tid`：本次票据唯一编号

这样服务端在传输线程里拿到票据后，就能直接知道：

1. 这是谁的请求
2. 这是上传还是下载
3. 作用于哪个目标路径
4. 这张票据在票据表里对应哪个唯一编号

---

## 6.3 服务端一次性票据模块

涉及文件：

- `include/transfer_ticket.h`
- `src/server/transfer_ticket.c`

这是本次新增的核心模块。

### 改动点 1：新增票据表

服务端增加了一个固定大小的内存票据表，用来保存：

1. 票据唯一编号
2. 票据是否仍有效
3. 票据过期时间

这里没有把设计做得很重，而是采用了适合学习项目的简单实现：

1. 固定大小数组
2. `pthread_mutex_t` 保护
3. 每次签发和消费时顺手清理过期记录

### 改动点 2：新增票据签发函数

`issue_transfer_ticket` 负责：

1. 生成随机票据编号
2. 调用 JWT 工具生成票据字符串
3. 把票据编号和过期时间存入票据表

### 改动点 3：新增票据消费函数

`verify_and_consume_transfer_ticket` 负责：

1. 校验票据签名和过期时间
2. 解析票据负载
3. 到票据表中查找这张票据
4. 如果存在则立刻消费并移除

这里“校验”和“消费”被放在同一个函数里，是为了让代码路径更直观：

1. 校验通过
2. 立即消费
3. 成功后开始传输

---

## 6.4 服务端会话处理改动

涉及文件：

- `src/server/session.c`

### 改动点 1：新增控制连接预请求处理逻辑

`dispatch_control_command` 中，`CMD_TYPE_PUTS` 和 `CMD_TYPE_GETS` 不再简单返回：

```text
文件传输请使用独立传输连接
```

而是改成：

1. 根据当前控制连接上下文和文件名，拼接完整虚拟路径
2. 调用 `issue_transfer_ticket`
3. 把票据响应返回给客户端

### 改动点 2：新增完整路径构造函数

新增了 `build_transfer_full_path`，负责根据：

1. 当前控制连接的 `current_path`
2. 本次 `puts/gets` 的文件名参数

拼出完整虚拟路径。

这个函数的意义是：

1. 让控制连接自己决定“本次请求操作的是哪个完整路径”
2. 避免客户端在控制连接预请求阶段再发一份明文完整路径

### 改动点 3：传输线程改为校验并消费一次性票据

`handle_transfer_request` 现在的流程是：

1. 接收传输认证包
2. 从包里取出票据
3. 调用 `verify_and_consume_transfer_ticket`
4. 从票据中还原：
   - `user_id`
   - `cmd_type`
   - `full_path`
5. 再构造传输上下文
6. 最后进入 `handle_puts` 或 `handle_gets`

这样传输线程彻底不再依赖登录 JWT。

## 6.5 客户端命令分发改动

涉及文件：

- `include/client_command_handle.h`
- `src/client/client_command_handle.c`

### 改动点：新增申请一次性传输票据的公共函数

新增：

```c
request_transfer_ticket(...)
```

它负责：

1. 在控制连接上发送 `puts/gets` 预请求
2. 接收服务端返回的票据响应
3. 把成功返回的一次性票据复制给调用方

这样后续 `client_puts.c` 和 `client_gets.c` 都可以复用这条逻辑，避免写两份重复代码。

## 6.6 客户端上传下载改动

涉及文件：

- `src/client/client_puts.c`
- `src/client/client_gets.c`

### `client_puts.c` 改动点

1. `PutsTask` 不再保存登录 JWT
2. `PutsTask` 不再保存当前路径
3. 改为保存一次性传输票据
4. 在启动传输线程前，先通过控制连接申请票据
5. 传输线程建立独立连接后，只发送票据

### `client_gets.c` 改动点

1. `GetsTask` 不再保存登录 JWT
2. `GetsTask` 不再保存当前路径
3. 改为保存一次性传输票据
4. 在启动下载线程前，先通过控制连接申请票据
5. 传输线程建立独立连接后，只发送票据

### 这样改的直接结果

客户端的 `puts/gets` 现在变成了两个阶段：

#### 第一阶段：控制连接申请票据

负责：

1. 由当前有效控制会话批准本次传输

#### 第二阶段：传输线程发起真正传输

负责：

1. 使用已批准的一次性票据完成本次传输

## 7. 本次改动后的关键行为变化

## 7.1 正常上传下载时的客户端表现

现在执行 `puts/gets` 时，客户端会先看到：

```text
传输票据申请成功
```

然后才会看到：

```text
上传任务已启动。
```

或者：

```text
下载任务已启动。
```

这说明当前流程已经明确分成了：

1. 预请求
2. 拿票据
3. 起传输线程

## 7.2 控制连接超时后，新传输任务无法再启动

旧方案里，控制连接超时后，旧 JWT 仍然可能被继续复用。

新方案里，控制连接超时后，再执行：

```text
gets ticket_demo_423.txt
```

客户端表现为：

```text
接收传输票据失败
```

这说明：

1. 控制连接已经无法再完成预请求
2. 客户端没有拿到新票据
3. 传输线程不会继续建立新的有效传输链路

也就是说：

> 控制连接失效后，新的传输任务已经不能再被正常发起。

这正是本次改进最重要的效果。

## 9. 当前保留的边界

虽然这次已经比旧方案更合理，但仍有几个边界需要明确。

## 9.1 登录 JWT 仍然保留，但不再直接用于传输连接

当前代码中，登录成功后服务端仍然会返回 JWT，客户端状态结构中也仍然会保存它。

这样做的原因是：

1. 先保持登录流程和前一版兼容
2. 不把这次改动扩展到“彻底删掉登录 JWT”
3. 把本次优化重点集中在“传输认证改成一次性票据”

也就是说：

### 当前事实

1. 登录 JWT 仍然存在
2. 但传输连接已经不再直接使用它

## 9.2 一次性票据表当前是固定大小内存数组

当前实现选择：

1. 固定大小数组
2. 互斥锁保护
3. 签发和消费时顺手清理过期项

这是为了保持代码简单直观。

如果后续连接量和传输量继续提高，可以再考虑：

1. 更灵活的数据结构
2. 更细的回收策略
3. 更完整的统计和监控信息

## 9.3 这次主要解决的是“新传输任务发起控制”

本次改进最核心解决的是：

> 控制连接失效后，不能再正常发起新的传输任务。

它并不是在做：

1. 已经开始的传输任务中途强制终止
2. 多设备统一登录态撤销
3. 全局级别的强会话注销

这些可以作为后续版本继续增强的方向。

---

## 10. 后续可以继续优化的方向

在当前这版基础上，后续如果还要继续增强，我建议优先考虑以下几项。

## 10.1 明确登录 JWT 在后续版本里的定位

当前登录 JWT 已不再直接参与传输认证，因此后续可以进一步明确：

1. 它是否还需要继续保留
2. 它是否只用于未来扩展场景
3. 是否要把客户端状态结构中的这个字段进一步弱化

## 10.2 为票据增加更细的失败原因返回

当前票据失败时，客户端看到的主要是：

1. `传输预请求失败`
2. `接收传输票据失败`

后续可以进一步区分：

1. 控制连接已断开
2. 票据已过期
3. 票据已被使用
4. 票据签发失败

这样调试体验会更好。

## 10.3 补一组“票据重复使用”专门测试

当前代码实现上已经支持：

1. 一张票据只允许成功消费一次

后续可以补一个专门的自动化测试或辅助工具，去验证：

1. 同一张票据第二次使用会被拒绝

这会让“一次性”语义验证得更完整。

---

## 11. 最终结论

本次优化后，第四期架构相比旧实现又前进了一步：

1. 控制连接继续负责短命令和会话控制
2. 传输连接继续保持独立
3. 登录 JWT 不再被传输连接长期直接复用
4. 每次 `puts/gets` 都必须先经过控制连接申请一次性传输票据
5. 传输线程只使用短时、一次性的票据进行本次传输

因此，当前方案相比旧方案更符合第四期真正想要的结构：

> 控制面决定是否允许传输，传输面只执行已经被批准的单次任务。

这使得：

1. 架构边界更清楚
2. 控制连接的作用更完整
3. 传输认证粒度更细
4. 后续继续扩展也更顺
