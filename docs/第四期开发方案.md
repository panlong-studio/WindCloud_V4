# 第四期开发方案

## 1. 文档目标

本文档用于作为 WindCloud 项目第四期开发的正式实施方案。

后续开发统一以本文档为准，目标是：

1. 将 `docs/项目概述.md` 中第四期的要求，转化为可执行的技术方案。
2. 在不破坏当前 V3 已有功能的前提下，完成第四期核心改造。
3. 保持实现简单直观，适合 C 语言学习项目持续演进。

---

## 2. 第四期范围

第四期只做以下三项核心内容：

1. 长短命令分离
2. JWT 身份凭证机制
3. 控制连接超时踢出，使用时间轮

### 2.1 本期短命令范围

短命令定义为：

- `login`
- `register`
- `pwd`
- `cd`
- `ls`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

特点：

- 处理时间短
- 协议交互简单
- 适合由服务端主线程集中管理

### 2.2 本期长命令范围

长命令定义为：

- `puts`
- `gets`

特点：

- 处理时间长
- 传输过程中可能持续占用连接
- 不适合与短命令共用同一条控制连接

---

## 3. 当前 V3 基线

当前 V3 的真实模型是：

1. 客户端只有一条连接。
2. 上传、下载、普通命令全部复用该连接。
3. 服务端主线程只负责 `accept`。
4. 工作线程从队列取出 `client_fd` 后，会一直处理该连接直到断开。

这意味着当前项目虽然有线程池，但它仍然是：

> 每客户端单连接、每连接单线程长期服务

第四期的改造目标，不是在当前结构上简单“加线程”，而是把整体模型调整为：

> 控制连接处理短命令，传输连接处理长命令

---

## 4. 第四期总体设计

## 4.1 总体原则

本期开发遵循以下原则：

1. 优先保证结构正确，再追求功能完整。
2. 优先选择易读、易实现、易调试的方案。
3. 不在同一条连接上同时混跑短命令和长命令。
4. JWT 只承担身份认证职责，不承担目录状态职责。
5. 控制连接超时管理先覆盖控制连接，不强行一步覆盖全部传输连接。

## 4.2 总体架构

第四期采用“双连接职责分离”架构：

### 客户端

1. 主线程维护一条控制连接。
2. 主线程负责短命令发送与响应处理。
3. 遇到 `puts/gets` 时，主线程创建传输任务。
4. 每个传输任务由一个子线程独立处理。
5. 每个传输子线程自己新建一条传输连接。

### 服务端

1. 主线程负责 `accept` 新连接。
2. 新连接建立后，先做“连接角色握手”。
3. 控制连接由主线程 `epoll` 直接管理。
4. 传输连接进入传输线程池。
5. 传输线程独占处理一次 `puts/gets`，完成后关闭连接。

---

## 5. 核心设计决策

## 5.1 长短命令必须分连接，不只分线程

本期明确采用：

- 控制连接：短命令
- 传输连接：长命令

不采用：

- 多线程共用同一个 `sock_fd`

原因：

1. 共用同一 socket 易导致协议串包。
2. 当前服务端的连接处理逻辑是按连接串行处理，不具备同连接多命令并行能力。
3. 分连接后的协议边界更清晰。

## 5.2 客户端第一版不引入线程池

本期客户端长命令采用：

- 一个传输任务
- 一个传输线程
- 一条传输连接

不采用：

- 客户端复杂线程池

原因：

1. 更符合学习项目定位。
2. 生命周期简单。
3. 更容易调试。

后续如果需要支持多任务并发下载或上传，再考虑在第五期或后续版本引入客户端线程池。

## 5.3 JWT 只放身份字段

JWT 中建议只放：

- `uid`
- `iat`
- `exp`

不放：

- `current_path`
- `current_dir_id`
- 文件名
- 上传目标目录

原因：

1. 路径属于高频变化状态。
2. JWT 更适合保存稳定的身份字段。
3. 目录状态仍应由连接上下文维护。

## 5.4 路径状态的职责划分

本期路径采用如下分工：

### 控制连接

服务端维护：

- `current_path`
- `current_dir_id`

用于支撑：

- `pwd`
- `cd`
- `ls`
- `mkdir`
- `touch`
- `rm`
- `rmdir`

### 传输连接

客户端显式传递：

- 目标完整虚拟路径 `full_path`

服务端传输线程不再依赖某条控制连接中的目录状态。

这样做的优点：

1. 传输请求具备独立性。
2. 传输线程不需要共享或继承控制连接上下文。
3. 更适合未来扩展多传输任务。

## 5.5 超时踢出只针对控制连接做时间轮

本期明确采用：

- 控制连接：`epoll + timerfd + 时间轮`
- 传输连接：socket 收发超时控制

不采用：

- 第一版就把控制连接和传输连接全部放入一套统一时间轮

原因：

1. 控制连接最适合时间轮。
2. 传输连接本期以“完整执行一次传输任务”为主，直接加收发超时更简单。
3. 可以明显降低实现复杂度。

## 6. 数据结构与模块规划

## 6.1 客户端新增状态结构

客户端新增统一状态结构：

```c
typedef struct {
    int ctrl_fd;
    int logged_in;
    int user_id;
    char token[1024];
    char current_path[256];
    pthread_mutex_t lock;
} ClientState;
```

职责：

1. 保存控制连接 fd
2. 保存登录结果和 JWT
3. 保存客户端视角下的当前远端路径
4. 为传输线程提供共享读取能力

## 6.2 服务端控制连接结构

服务端新增控制连接状态结构：

```c
typedef struct {
    int fd;
    int user_id;
    char current_path[256];
    int current_dir_id;
    long long expire_tick;
    int wheel_slot;
    void *wheel_node;
} ControlConn;
```

职责：

1. 表示一条控制连接当前的会话状态
2. 保存短命令所需上下文
3. 保存时间轮超时信息

## 6.3 新增协议结构

### 连接初始化包

```c
typedef enum {
    CONN_ROLE_CTRL = 1,
    CONN_ROLE_TRANSFER = 2
} conn_role_t;

typedef struct {
    int role;
} conn_init_packet_t;
```

作用：

- 新连接建立后，先说明自己是控制连接还是传输连接

### 传输认证包

```c
typedef struct {
    int cmd_type;
    char token[1024];
    char full_path[512];
    char file_name[256];
} transfer_auth_packet_t;
```

作用：

1. 传输线程声明本次命令类型
2. 携带 JWT
3. 携带本次完整虚拟路径

## 6.4 新增模块建议

建议新增以下模块：

- `include/jwt_utils.h`
- `src/common/jwt_utils.c`
- `include/time_wheel.h`
- `src/server/time_wheel.c`
- `include/control_conn.h`
- `src/server/control_conn.c`

## 7. 详细实施方案

## 7.1 第一阶段：协议扩展

### 目标

为控制连接和传输连接分离提供协议基础。

### 实施内容

1. 在 `protocol.h` 中新增连接角色定义。
2. 新增 `conn_init_packet_t`。
3. 新增 `transfer_auth_packet_t`。
4. 补充对应的初始化、发送、接收辅助函数。

### 阶段结果

服务端能够在连接建立后区分：

- 控制连接
- 传输连接

## 7.2 第二阶段：客户端状态改造

### 目标

让客户端具备：

- 保存 JWT
- 保存当前路径
- 支持后续传输线程读取共享状态

### 实施内容

1. 将客户端的连接状态统一收敛到 `ClientState`。
2. 登录成功后保存：
   - `logged_in`
   - `user_id`
   - `token`
   - `current_path="/"`  
3. `cd` 成功后同步更新客户端本地 `current_path`。
4. 为传输线程读取 `token/current_path` 增加互斥保护。

### 阶段结果

客户端具备长短命令分离所需的基础状态管理能力。

## 7.3 第三阶段：JWT 模块接入

### 目标

为跨连接身份识别提供统一工具。

### 实施内容

1. 新增 `jwt_utils` 模块。
2. 封装两个核心接口：
   - `create_jwt_for_user()`
   - `verify_jwt_and_get_user()`
3. 登录成功时，服务端签发 JWT。
4. 客户端接收并保存 JWT。

### 阶段结果

客户端后续新建传输连接时，可以携带 JWT 证明身份。

## 7.4 第四阶段：客户端长短命令分离

### 目标

让客户端上传下载不再阻塞主线程命令交互。

### 实施内容

1. 主线程保留控制连接，只处理短命令。
2. 用户输入 `puts/gets` 时：
   - 构造传输任务
   - 启动一个传输线程
3. 传输线程：
   - 新建传输连接
   - 发送 `conn_init_packet_t`
   - 发送 `transfer_auth_packet_t`
   - 执行上传或下载流程
4. 传输完成后，线程退出并关闭连接。

### 阶段结果

客户端在上传下载期间仍可继续输入短命令。

## 7.5 第五阶段：服务端连接模型改造

### 目标

将当前“连接级线程池”改造成“控制连接主线程处理、传输连接线程池处理”。

### 实施内容

1. `accept` 新连接后，先接收连接初始化包。
2. 若为控制连接：
   - 加入主线程 `epoll`
   - 建立 `ControlConn`
   - 主线程自己处理短命令
3. 若为传输连接：
   - 放入传输任务队列
   - 唤醒传输线程
4. 传输线程校验 JWT 后独立完成一次 `puts/gets`。

### 阶段结果

服务端短命令不再被上传下载长期占住。

## 7.6 第六阶段：传输逻辑按完整路径改造

### 目标

让传输连接独立于控制连接目录状态。

### 实施内容

1. 传输请求统一携带 `full_path`。
2. `handle_puts/handle_gets` 新增或改造成按：
   - `user_id`
   - `full_path`
   处理。
3. 传输线程不再依赖控制连接中的 `current_path/current_dir_id`。

### 阶段结果

上传下载逻辑从“依赖会话目录”升级为“请求自包含”。

## 7.7 第七阶段：控制连接超时踢出

### 目标

为控制连接引入统一的空闲回收机制。

### 实施内容

1. 新增 `time_wheel` 模块。
2. 用 `timerfd` 每秒触发一次 tick。
3. 控制连接建立时加入时间轮。
4. 控制连接每次收到命令或成功发送响应后，刷新过期位置。
5. 到期槽位中的空闲控制连接关闭并释放。

### 阶段结果

控制连接超过阈值无活动时，服务端可自动踢出。

---

## 8. 推荐开发顺序

后续代码开发严格按以下顺序推进：

1. 扩展协议结构
2. 客户端引入 `ClientState`
3. 接入 JWT 工具模块
4. 客户端实现独立传输线程
5. 服务端区分控制连接和传输连接
6. 改造 `gets`
7. 改造 `puts`
8. 引入时间轮处理控制连接超时
9. 补充异常处理与兼容逻辑

### 为什么先改 `gets` 再改 `puts`

因为：

1. `gets` 流程更简单
2. 不涉及服务端接收大文件写入
3. 不涉及秒传与上传断点续传的复杂状态

所以本期建议：

- 先完成独立下载链路
- 再迁移上传链路

## 9. 验收标准

## 9.1 长短命令分离验收

满足以下条件即认为通过：

1. 客户端执行大文件 `puts` 时，主线程仍可继续输入 `pwd/ls/cd`。
2. 客户端执行大文件 `gets` 时，主线程仍可继续输入 `pwd/ls/cd`。
3. 上传下载与短命令不再共用同一条连接。
4. 服务端控制命令处理不再依赖“一个线程长期守一个连接”。

## 9.2 JWT 验收

满足以下条件即认为通过：

1. 登录成功后客户端可收到并保存 JWT。
2. 传输连接不重复登录，只携带 JWT 即可完成身份认证。
3. 服务端能从 JWT 中解析出 `user_id`。
4. 无效 JWT、过期 JWT 会被拒绝。

## 9.3 超时踢出验收

满足以下条件即认为通过：

1. 控制连接超过超时阈值后被服务端关闭。
2. 正在执行传输任务的连接不因控制连接超时而直接中止。
3. 客户端在控制连接被踢后不会整体崩溃。

## 10. 测试方案

本期至少覆盖以下测试：

### 功能测试

1. 登录成功并获取 JWT
2. 控制连接下的普通短命令正常执行
3. 独立传输连接下的 `gets` 正常执行
4. 独立传输连接下的 `puts` 正常执行
5. 秒传仍然可用
6. 断点续传仍然可用

### 并发测试

1. 一个客户端上传时继续执行短命令
2. 一个客户端下载时继续执行短命令
3. 两个不同用户同时上传
4. 两个不同用户同时下载

### 超时测试

1. 控制连接空闲超时后被踢出
2. 控制连接超时后客户端再次操作的表现符合预期

### 异常测试

1. token 无效
2. token 过期
3. 传输中断
4. 控制连接被踢时仍有传输任务在进行

---

## 11. 暂不纳入本期范围

本期明确不做以下内容：

1. refresh token
2. token 黑名单
3. 客户端复杂线程池
4. 控制连接自动重连
5. 传输连接统一纳入时间轮
6. 多点下载
7. 分布式 session 或多机共享 token 状态

这些内容不属于第四期核心交付，后续如有需要再进入下一阶段方案。

---

## 12. 风险与控制

## 12.1 协议升级风险

风险：

- 新旧协议混用时容易出现收发错位

控制：

- 先完成协议层改造和单元测试，再进入业务层改造

## 12.2 上传链路复杂度风险

风险：

- `puts` 同时涉及秒传、断点续传、真实文件写入、数据库补录

控制：

- 先迁移 `gets`
- 再迁移 `puts`
- `puts` 改造时保持原有核心传输逻辑不变，只调整身份与路径获取方式

## 12.3 超时误踢风险

风险：

- 时间轮刷新时机设计不当，可能误踢活跃连接

控制：

- 在“收到命令”和“发送响应成功”两个关键时机都刷新
- 第一版只针对控制连接

---

## 13. 最终结论

第四期的本质不是单独增加 JWT 或时间轮，而是完成一次连接模型升级：

1. 控制连接处理短命令
2. 传输连接处理长命令
3. JWT 解决跨连接身份识别
4. 时间轮解决控制连接空闲回收

后续开发应严格按本文档的阶段顺序实施，避免在实现过程中重新回到“单连接承载全部命令”的旧模型。
