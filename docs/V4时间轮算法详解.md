# WindCloud_V4 时间轮算法详解

## 1. 文档目标

这份文档专门解释两件事：

1. 时间轮算法本身的基本原理是什么
2. 当前 WindCloud_V4 项目是怎样把时间轮算法接到真实代码中的

这份文档不是只讲抽象概念，而是会结合当前仓库里的真实代码来说明：

- 时间轮的数据结构
- 刷新超时位置的过程
- 推进时间轮的过程
- 为什么当前实现不需要“从旧槽位删除旧节点”
- 服务端主循环是怎样使用时间轮关闭空闲主连接的

当前项目中与时间轮直接相关的代码主要有：

- `include/time_wheel.h`
- `src/server/time_wheel.c`
- `include/conn_manager.h`
- `src/server/conn_manager.c`
- `src/server/server.c`

---

## 2. 为什么需要时间轮

第四期要解决的一个实际问题是：

> 主连接建立后，如果用户长时间不再发送短命令，服务端需要把这条空闲连接关闭

如果不用时间轮，最直观的做法通常有两种：

1. 每次检查所有连接，逐个比较“当前时间 - 最后活跃时间”
2. 每个连接单独维护一个定时器

这两种方法都能做，但对当前项目来说都不够合适：

### 2.1 为什么不直接每秒扫描所有连接

假设服务端有很多主连接，每秒都遍历一遍全部连接：

- 实现简单
- 但每秒都要做一轮完整扫描

当前项目虽然连接数不算特别大，但第四期新增了：

- 主连接长期维护
- 独立传输连接和主连接并存
- `ConnManager` 中维护连接状态

如果继续用“每秒遍历全部连接”的思路，后面连接数一增长，效率会越来越差。

### 2.2 为什么不为每条连接单独开一个定时器

每条连接单独维护一个定时器，理论上也可以。

但对当前项目来说，这样会带来：

- 额外的定时器管理复杂度
- 超时刷新逻辑更分散
- 和当前“主线程统一维护连接状态”的结构不够匹配

### 2.3 时间轮适合这个项目的原因

时间轮特别适合处理这类问题：

> 大量“若干秒后检查一次是否超时”的连接对象

它的优势是：

1. 刷新超时位置的操作比较轻
2. 每一秒只处理当前槽位，不用扫描全部连接
3. 数据结构简单，适合当前项目风格
4. 能很自然地接入 `server.c` 的主循环

## 3. 时间轮算法的基本原理

## 3.1 可以先把时间轮想成一个循环数组

时间轮最容易理解的方式，是把它想成一个循环数组。

例如：

- 一共有 60 个槽位
- 每推进一次表示 1 秒
- 指针每秒向前走 1 格
- 走到末尾后重新回到开头

可以把它理解成下面这样：

```text
槽位:   0   1   2   3   4   5   ...  59
指针:               ^
```

每个槽位里不直接放“时间”，而是放：

> 哪些对象预计会在这个时间点附近到期

## 3.2 一个连接如何放进时间轮

假设：

- 当前时间轮位置是 `current_tick = 100`
- 超时时间是 `30` 秒

那么一个刚刚活跃过的连接，它的理论过期时间就是：

```text
expire_tick = current_tick + timeout_seconds
            = 100 + 30
            = 130
```

接下来把它挂到哪个槽位呢？

做法是：

```text
slot_index = expire_tick % slot_count
```

如果：

- `slot_count = 60`

那么：

```text
slot_index = 130 % 60 = 10
```

于是这个连接就被挂到槽位 `10` 上。

## 3.3 时间轮为什么能工作

时间轮每推进一秒：

1. `current_tick += 1`
2. 找到当前应该检查的槽位
3. 检查这个槽位中的所有对象

因为之前把连接是按“过期 tick”映射到槽位里的，所以当时间轮再次走到那个槽位时，就有可能说明：

> 这些对象已经到了它们应该被检查的时刻

注意，这里是“应该被检查”，不是“肯定已经超时”。

这是因为一个连接可能在之后又活跃过一次，已经被重新安排了新的过期位置。

所以当前项目里还额外加了一层：

> `expire_tick` 精确校验

这一点是本项目实现的关键。

## 4. 经典时间轮和本项目实现的区别

## 4.1 经典理解：对象被移动到新槽位

很多教材会把时间轮讲成：

1. 连接活跃
2. 把它从旧槽位取下来
3. 再插入新槽位

这种理解没有问题，但实现起来通常要处理：

- 从旧链表里删除节点
- 更新前驱和后继指针
- 防止重复节点

这会让代码复杂不少。

## 4.2 本项目的做法：追加新节点，旧节点自然失效

当前项目没有在刷新时主动删除旧节点。

它的实际策略是：

1. 连接活跃时，直接追加一个新的时间轮节点
2. 同时把 `ServerConnState.expire_tick` 更新成最新值
3. 以后时间轮扫到旧节点时，拿旧节点里的 `expire_tick` 和当前连接状态里的 `expire_tick` 做比较
4. 如果两者不一致，说明这个旧节点已经过期了，直接忽略

这就是一种很适合当前项目的：

> 延迟失效

或者也可以理解成：

> 旧节点不立刻删除，而是在轮到它被检查时自然淘汰

## 4.3 为什么这种做法很适合当前项目

因为它能显著简化代码：

1. 刷新时不需要知道旧节点在哪条链表的什么位置
2. 不需要写“从链表中间删除任意节点”的逻辑
3. 只需要在检查槽位时做一次 `expire_tick` 比较

代价是：

- 同一个 fd 在时间轮中可能暂时存在多个旧节点

但这些旧节点会在后续轮到对应槽位时被释放掉，所以整体仍然是可控的。

## 5. 本项目的时间轮数据结构

当前定义在 `include/time_wheel.h` 中。

### 5.1 单个时间轮节点

```c
typedef struct TimeWheelNode {
    int fd;
    unsigned long long expire_tick;
    struct TimeWheelNode *next;
} TimeWheelNode;
```

每个节点记录两件关键事情：

1. 这个节点对应哪个连接 `fd`
2. 这个节点当时记录的过期刻度 `expire_tick`

这里没有保存 `last_active_time`，也没有保存复杂上下文。

原因是：

- 真实状态统一放在 `ServerConnState`
- 时间轮节点只负责“提醒主线程在某个时刻检查这个 fd”

### 5.2 单个槽位

```c
typedef struct {
    TimeWheelNode *head;
    TimeWheelNode *tail;
} TimeWheelSlot;
```

一个槽位本质上就是一条链表：

- `head` 指向链表头
- `tail` 指向链表尾

当前项目用尾插法追加节点，这样实现最直观。

### 5.3 整个时间轮

```c
typedef struct {
    int slot_count;
    int timeout_seconds;
    unsigned long long current_tick;
    TimeWheelSlot *slots;
} TimeWheel;
```

这几个字段分别表示：

- `slot_count`
  - 时间轮总槽位数
- `timeout_seconds`
  - 空闲多久算超时
- `current_tick`
  - 当前已经推进到第几个刻度
- `slots`
  - 槽位数组

## 6. 本项目的连接状态和时间轮是如何配合的

时间轮本身只知道：

- 某个 `fd`
- 某个 `expire_tick`

但它不知道这个连接现在是不是还有效，也不知道它是不是后来又被刷新过。

所以当前项目还需要一份独立的连接状态。

当前定义在 `include/conn_manager.h` 中：

```c
typedef struct ServerConnState {
    int fd;
    int is_logged_in;
    int user_id;
    int current_dir_id;
    int wheel_slot;
    unsigned long long expire_tick;
    time_t last_active_time;
    char current_path[CMD_DATA_LEN];
    char token[TOKEN_LEN];
    struct ServerConnState *next;
} ServerConnState;
```

这里和时间轮算法直接相关的字段是：

- `wheel_slot`
  - 当前最新一次刷新时，这个连接被挂到了哪个槽位
- `expire_tick`
  - 当前最新一次刷新后，这个连接真正应该到期的刻度
- `last_active_time`
  - 最近一次活跃时间，主要用于记录和观察

真正的判断依据里最关键的是：

> `ServerConnState.expire_tick`

因为时间轮扫到一个节点时，会拿这个节点记录的 `expire_tick` 和连接状态中的 `expire_tick` 比较。

如果两者不相等，就说明这个节点已经是旧节点了。

## 7. 初始化：时间轮是怎样创建出来的

初始化代码在 `src/server/time_wheel.c` 的 `time_wheel_init()` 中。

关键代码如下：

```c
int time_wheel_init(TimeWheel *wheel, int slot_count, int timeout_seconds) {
    if (wheel == NULL || slot_count <= 0 || timeout_seconds <= 0) {
        return -1;
    }

    memset(wheel, 0, sizeof(TimeWheel));

    wheel->slots = (TimeWheelSlot *)calloc((size_t)slot_count, sizeof(TimeWheelSlot));
    if (wheel->slots == NULL) {
        return -1;
    }

    wheel->slot_count = slot_count;
    wheel->timeout_seconds = timeout_seconds;
    wheel->current_tick = 0;
    return 0;
}
```

这个函数做了四件事：

1. 检查参数是否合法
2. 把 `TimeWheel` 结构体清零
3. 申请槽位数组
4. 记录槽位数量、超时时间和初始刻度

在当前项目中，`server.c` 里是这样调用的：

```c
#define SERVER_TIME_WHEEL_SIZE 60
#define SERVER_TIME_OUT_SECONDS 30

if (time_wheel_init(&time_wheel, SERVER_TIME_WHEEL_SIZE, SERVER_TIME_OUT_SECONDS) != 0) {
    LOG_ERROR("时间轮初始化失败");
    ...
}
```

也就是说，当前项目里：

- 时间轮总槽位数是 `60`
- 主连接超时阈值是 `30` 秒

这说明：

1. 当前项目每推进一秒，就相当于走一格
2. 一个连接默认会被安排到“30 秒之后”的某个槽位

## 8. 刷新：连接活跃时怎样重新安排超时位置

刷新逻辑在 `time_wheel_refresh()` 中。

关键代码如下：

```c
unsigned long long time_wheel_refresh(TimeWheel *wheel, ServerConnState *state) {
    unsigned long long expire_tick = 0;
    int slot_index = 0;

    if (wheel == NULL || wheel->slots == NULL || state == NULL) {
        return 0;
    }

    expire_tick = wheel->current_tick + (unsigned long long)wheel->timeout_seconds;
    slot_index = (int)(expire_tick % (unsigned long long)wheel->slot_count);

    if (append_wheel_node(&wheel->slots[slot_index], state->fd, expire_tick) != 0) {
        return 0;
    }

    state->expire_tick = expire_tick;
    state->wheel_slot = slot_index;
    conn_state_touch(state);
    return expire_tick;
}
```

这段代码的逻辑非常关键，可以拆成五步：

### 第一步：计算新的过期刻度

```text
expire_tick = current_tick + timeout_seconds
```

这表示：

> 从当前时刻开始，再往后推 `timeout_seconds` 秒，就是新的超时时刻

### 第二步：计算应该挂到哪个槽位

```text
slot_index = expire_tick % slot_count
```

这就是时间轮“循环数组”那一层的核心。

### 第三步：追加一个新节点到目标槽位

项目并没有把旧节点删掉，而是直接：

1. 创建一个新 `TimeWheelNode`
2. 记录 `fd`
3. 记录这次新的 `expire_tick`
4. 尾插到目标槽位链表

### 第四步：把连接状态中的超时信息同步成最新值

```c
state->expire_tick = expire_tick;
state->wheel_slot = slot_index;
```

这一步的意义是：

> 以后判断一个时间轮节点是不是最新节点，就靠这个最新 `expire_tick`

### 第五步：刷新最近活跃时间

```c
conn_state_touch(state);
```

当前项目会顺手更新：

- `last_active_time = time(NULL)`

这对日志和调试很有帮助。

## 9. 推进：时间轮每秒是怎样检查超时连接的

推进逻辑在 `time_wheel_tick()` 中。

关键代码如下：

```c
int time_wheel_tick(TimeWheel *wheel, ConnManager *manager, int *expired_fds, int max_expired) {
    int expired_count = 0;
    int slot_index = 0;
    TimeWheelNode *cur = NULL;

    if (wheel == NULL || wheel->slots == NULL || manager == NULL || expired_fds == NULL || max_expired <= 0) {
        return 0;
    }

    wheel->current_tick++;
    slot_index = (int)(wheel->current_tick % (unsigned long long)wheel->slot_count);
    cur = wheel->slots[slot_index].head;

    while (cur != NULL) {
        ServerConnState *state = conn_manager_get(manager, cur->fd);

        if (state != NULL &&
            state->fd == cur->fd &&
            state->expire_tick == cur->expire_tick &&
            expired_count < max_expired) {
            expired_fds[expired_count++] = cur->fd;
        }

        TimeWheelNode *next = cur->next;
        free(cur);
        cur = next;
    }

    wheel->slots[slot_index].head = NULL;
    wheel->slots[slot_index].tail = NULL;
    return expired_count;
}
```

这段代码可以拆成六步理解。

### 9.1 第一步：时间轮先向前走一格

```c
wheel->current_tick++;
```

这表示：

> 现在又过了一秒

### 9.2 第二步：定位本轮要检查的槽位

```c
slot_index = current_tick % slot_count
```

也就是说：

> 当前这一秒，只检查当前槽位中的节点

而不是去扫描所有槽位。

### 9.3 第三步：遍历当前槽位链表

```c
cur = wheel->slots[slot_index].head;
while (cur != NULL) {
    ...
}
```

每个节点都代表：

> 某个连接曾经被安排在这个时刻附近检查

### 9.4 第四步：通过 `ConnManager` 查当前真实连接状态

```c
ServerConnState *state = conn_manager_get(manager, cur->fd);
```

这一步非常关键。

因为时间轮节点本身只是历史记录，它不知道：

- 这个连接是不是已经被关闭了
- 这个连接是不是后来又被刷新过了

所以必须回到 `ConnManager` 中查当前真实状态。

### 9.5 第五步：只把“真正超时”的 fd 收集出来

当前代码的判断条件是：

```c
if (state != NULL &&
    state->fd == cur->fd &&
    state->expire_tick == cur->expire_tick &&
    expired_count < max_expired) {
    expired_fds[expired_count++] = cur->fd;
}
```

这三个条件分别意味着：

1. `state != NULL`
   - 这个连接现在还存在于状态管理器中
   - 如果已经被删除，就说明它不是当前需要处理的有效连接
2. `state->fd == cur->fd`
   - 基础一致性校验
3. `state->expire_tick == cur->expire_tick`
   - 这是最关键的一条
   - 说明当前槽位里的这个节点，仍然是这个连接最新一次超时安排

只有当这三个条件都成立时，当前节点才是真正需要超时关闭的连接。

### 9.6 第六步：当前槽位检查完后，释放全部节点

当前代码会把当前槽位链表全部释放掉：

```c
TimeWheelNode *next = cur->next;
free(cur);
cur = next;
```

最后再把槽位头尾指针清空：

```c
wheel->slots[slot_index].head = NULL;
wheel->slots[slot_index].tail = NULL;
```

这意味着：

> 时间轮节点只活到它被轮到检查的这一刻

无论它是：

- 真正超时节点
- 已经过期的旧节点

都会在这次检查里被统一释放。

## 10. 本项目最关键的设计点：为什么旧节点不会误杀新连接

这是当前实现里最值得单独讲清楚的一点。

## 10.1 看一个具体例子

假设：

- `slot_count = 60`
- `timeout_seconds = 30`
- 当前 `current_tick = 100`

某个连接 `fd = 12` 在这一刻活跃了，于是：

```text
expire_tick = 100 + 30 = 130
slot_index = 130 % 60 = 10
```

于是时间轮里挂入一个节点：

```text
(fd=12, expire_tick=130)
```

同时连接状态里保存：

```text
state->expire_tick = 130
```

## 10.2 如果这个连接在超时前又活跃一次

假设在 `current_tick = 108` 时，这个连接又发来了一条短命令。

此时刷新后：

```text
expire_tick = 108 + 30 = 138
slot_index = 138 % 60 = 18
```

于是项目不会去删掉原来的旧节点，而是直接再挂一个新节点：

```text
旧节点: (fd=12, expire_tick=130)  在槽位 10
新节点: (fd=12, expire_tick=138)  在槽位 18
```

同时连接状态更新成：

```text
state->expire_tick = 138
```

## 10.3 当时间轮走到槽位 10 会发生什么

轮到检查旧节点 `(fd=12, expire_tick=130)` 时：

1. `conn_manager_get()` 还能查到 `fd=12`
2. 但当前真实状态里的 `state->expire_tick = 138`
3. 旧节点里的 `cur->expire_tick = 130`

于是：

```text
state->expire_tick != cur->expire_tick
```

这个节点就不会被当成真正超时。

然后它会被释放掉。

## 10.4 当时间轮走到槽位 18 会发生什么

轮到检查新节点 `(fd=12, expire_tick=138)` 时：

1. `conn_manager_get()` 查到当前连接状态
2. `state->expire_tick == 138`
3. `cur->expire_tick == 138`

于是条件匹配，说明：

> 这就是这个连接当前最新的一次超时安排

如果它此时还没有再次活跃，就会被收集到 `expired_fds` 中，随后由主线程关闭。

这就是为什么当前项目不需要主动删除旧节点。

## 11. 时间轮在当前项目中是怎样接入主循环的

## 11.1 新连接到来时

在 `server.c` 中，`accept()` 新连接后会做这几步：

```c
add_epoll_fd(epfd, conn_fd);

ServerConnState *state = conn_manager_add(&conn_manager, conn_fd);
...

time_wheel_refresh(&time_wheel, state);
```

也就是说：

1. 新连接先加入 `epoll`
2. 再建立连接状态
3. 然后立刻安排一次超时位置

## 11.2 主连接每次处理完短命令后

在 `server.c` 中，普通命令处理成功后会：

```c
if (session_handle_main_command(fd, state, &cmd_packet) != 0) {
    ...
}

time_wheel_refresh(&time_wheel, state);
```

这说明：

> 每次短命令处理完成，主连接都会重新获得一个新的 30 秒超时时间

## 11.3 主循环每秒推进一次时间轮

在 `server.c` 中：

```c
time_t now_time = time(NULL);
while (last_tick_time < now_time) {
    process_time_wheel_tick(epfd, &conn_manager, &time_wheel);
    last_tick_time++;
}
```

这里的意思是：

1. 主循环拿当前系统时间和上次推进时间做比较
2. 如果已经过去了一秒或多秒，就补推进对应次数

这样做的好处是：

- 不依赖精确一秒一次的定时器
- 即使某轮 `epoll_wait()` 因为别的事情稍晚返回，也能把刻度补上

## 11.4 发现超时连接后，主线程怎样处理

`process_time_wheel_tick()` 的核心逻辑是：

```c
expired_count = time_wheel_tick(wheel, manager, expired_fds, 256);

for (int idx = 0; idx < expired_count; ++idx) {
    ServerConnState *state = conn_manager_get(manager, expired_fds[idx]);
    if (state == NULL) {
        continue;
    }

    close_managed_connection(epfd, manager, state->fd);
}
```

也就是说：

1. 时间轮只负责找出真正超时的 `fd`
2. 真正的关闭动作仍然由主线程完成

而 `close_managed_connection()` 会做三件事：

1. 从 `epoll` 中移除这个 fd
2. 关闭 socket
3. 从 `ConnManager` 中删除对应状态

这就完成了主连接的完整超时清理。

---

## 12. 独立传输连接和时间轮的关系

这一点在当前项目里很容易误解，必须单独说明。

## 12.1 从业务目标看

从业务目标看，时间轮真正想管理的是：

> 主连接

因为：

- 主连接是长期存在的
- 上传下载连接是短时存在的
- 传输连接任务结束后就会被关闭

## 12.2 从当前代码看

从当前实现看，新连接 `accept()` 之后都会先：

1. 创建 `ServerConnState`
2. 调用一次 `time_wheel_refresh()`

然后主线程再通过 `peek_cmd_type()` 判断这是不是认证连接。

如果首包是 `CMD_TYPE_AUTH`，主线程会在构造完 `transfer_task_t` 后执行：

```c
del_epoll_fd(epfd, fd);
conn_manager_remove(&conn_manager, fd);
```

这意味着：

1. 传输连接会短暂经过“加入状态管理、登记一次时间轮”的流程
2. 但一旦被识别为传输连接，就会从状态管理中移除
3. 以后时间轮即使扫到它的旧节点，也会因为 `conn_manager_get()` 返回 `NULL` 而直接忽略

所以更准确的说法应该是：

> 时间轮的长期管理对象是主连接  
> 传输连接只在接入初期短暂经过同一套登记流程

## 13. 一个完整例子：主连接是如何被时间轮关闭的

假设当前项目参数如下：

- `slot_count = 60`
- `timeout_seconds = 30`

现在有一条主连接 `fd = 15`。

### 第一步：连接刚建立

假设此时：

```text
current_tick = 0
```

新连接进入后调用 `time_wheel_refresh()`：

```text
expire_tick = 0 + 30 = 30
slot_index = 30 % 60 = 30
```

于是：

- 槽位 `30` 中追加一个节点 `(15, 30)`
- 连接状态中记录 `expire_tick = 30`

### 第二步：用户在第 10 秒发了一条短命令

此时：

```text
current_tick = 10
```

短命令处理完成后再次刷新：

```text
expire_tick = 10 + 30 = 40
slot_index = 40
```

于是：

- 槽位 `40` 中再追加一个节点 `(15, 40)`
- 连接状态中的最新 `expire_tick` 改成 `40`
- 槽位 `30` 中的旧节点 `(15, 30)` 暂时还在

### 第三步：时间轮走到槽位 30

此时会检查旧节点 `(15, 30)`。

但连接状态里保存的是：

```text
state->expire_tick = 40
```

所以它不会被判定为真正超时，只会被释放掉。

### 第四步：用户之后一直没有再发命令

当时间轮走到槽位 `40` 时：

- 当前连接状态还存在
- `state->expire_tick == 40`
- 节点里的 `expire_tick == 40`

于是它被判定为真正超时。

主线程随后：

1. 从 `epoll` 中移除这个 fd
2. 关闭连接
3. 删除连接状态

整个过程就完成了。

## 14. 这套实现的优点

### 14.1 刷新逻辑非常简单

当前项目在刷新时不需要：

- 找旧节点
- 删旧节点
- 改复杂链表关系

只需要：

1. 计算新的 `expire_tick`
2. 尾插一个新节点
3. 更新连接状态中的最新 `expire_tick`

### 14.2 每秒只检查一个槽位

时间轮推进时，不需要每秒遍历全部连接。

当前轮到哪个槽位，就只检查哪个槽位。

这就是时间轮相对“每秒扫描所有连接”的最大优势。

### 14.3 和当前主线程架构天然匹配

当前项目本来就是：

- 主线程维护 `ConnManager`
- 主线程处理短命令
- 主线程统一关闭超时连接

时间轮只需要把“哪些 fd 真正到期了”交给主线程，整体结构非常顺。

### 14.4 代码风格简单直观

当前实现没有引入：

- 多级时间轮
- 复杂回调系统
- 独立定时线程

而是用最容易讲清楚的：

- 循环数组
- 链表槽位
- `expire_tick` 校验

这和当前项目整体代码风格是一致的。

## 15. 当前实现的局限和后续可优化点

### 15.1 `ConnManager` 当前是单链表

`time_wheel_tick()` 检查每个节点时，都要调用：

```c
conn_manager_get(manager, cur->fd)
```

而当前 `conn_manager_get()` 是线性查找。

所以如果连接数继续增大，这里的查找成本会逐渐上升。

### 15.2 同一个连接可能会留下多个旧节点

这是当前实现故意接受的代价。

它换来的是：

- 刷新逻辑简单

代价是：

- 某些槽位里会出现旧节点
- 需要靠 `expire_tick` 比较把它们过滤掉

对当前项目规模来说，这个取舍是合理的。

### 15.3 时间轮推进精度是秒级

当前项目里：

- 一秒推进一次
- 超时阈值按秒计算

这对“主连接空闲超时断开”完全够用。

但如果以后需要更细的毫秒级超时控制，就需要重新设计推进粒度。

### 15.4 传输连接目前仍会先登记一次时间轮

这不会影响功能正确性，因为后面会从 `ConnManager` 中移除。

但如果以后想让逻辑更纯粹，也可以在更前面就把主连接和传输连接区分开，再决定是否调用 `time_wheel_refresh()`。

---

## 16. 一句话总结当前项目的时间轮实现

WindCloud_V4 当前使用的是：

> 基于循环数组和链表槽位的简单时间轮；连接活跃时不删除旧节点，而是追加新节点并更新 `expire_tick`；时间轮推进时只检查当前槽位，再通过 `ConnManager` 中保存的最新 `expire_tick` 判断节点是否真正超时；最终由服务端主线程关闭真正空闲过久的主连接。
