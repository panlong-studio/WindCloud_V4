# WindCloud_V5 学习文档

## 1. 文档目标

这份文档面向第一次系统学习 WindCloud 项目的人，目标不是只告诉你“有哪些文件”，而是帮助你真正看懂：

1. 这个项目从第一期到第五期，核心能力是怎么一点点长出来的。
2. 为什么第四期和第五期是整个项目的架构分水岭。
3. 当前第五期代码里，控制连接、传输连接、JWT、一次性票据、时间轮、多点下载分别承担什么职责。
4. 如果你要继续维护、调试、扩展这个项目，应该先从哪里看，后从哪里看。

这份文档重点放在第四期和第五期，因为：

1. 第一期到第三期主要是在“单连接模型”上堆功能。
2. 第四期开始，项目第一次从“命令功能实现”进入“架构升级”。
3. 第五期的多点下载，是当前项目里最长、最复杂、最能体现整体设计水平的一条链路。

---

## 2. 学习前先建立整体认识

### 2.1 这个项目到底在做什么

WindCloud 不是一个“直接把 Linux 文件系统暴露给客户端”的程序，而是一个带有虚拟目录层的网盘项目。

当前项目同时维护三套系统：

1. 逻辑文件系统
   - 面向用户
   - 用数据库 `paths` 表描述目录树和文件节点
   - 支撑 `pwd`、`cd`、`ls`、`mkdir`、`touch`、`rm`、`rmdir`
2. 真实文件系统
   - 面向服务端存储
   - 真实文件统一存放在 `test/server_files/<sha256>`
   - 支撑上传、下载、断点续传、秒传、去重
3. 数据源系统
   - 面向第五期多点下载
   - 用数据库 `file_sources` 表记录“哪台服务器拥有哪份真实文件”
   - 支撑控制服务器为客户端返回多点下载方案

所以当前项目的本质可以概括成一句话：

> 一个基于虚拟目录的网盘系统，底层使用按内容哈希命名的真实文件仓库，并在第五期增加了多数据源分片下载能力。

### 2.2 当前代码最重要的四个目录

如果你只想先记住最重要的目录，先记下面四个：

1. `src/client`
   - 客户端主流程、上传线程、下载线程、多点下载元数据
2. `src/common`
   - 协议、日志、配置、JWT、SHA-256、统一路径工具
3. `src/server/core`
   - 服务端主线程、连接分发、工作线程
4. `src/server/file`
   - 上传下载真正落业务的地方

## 3. 先理解第一期到第三期在做什么

第四期和第五期不好理解，通常不是因为它们本身太难，而是因为没有先搞清楚前三期打下了什么基础。

### 3.1 第一期解决的是“能不能像一个网盘一样工作”

第一期完成的是最基本的文件系统命令能力：

1. `pwd`
2. `cd`
3. `ls`
4. `mkdir`
5. `touch`
6. `rm`
7. `rmdir`

这一期真正建立的不是“传输”，而是“目录语义”。

也就是说，后面上传和下载时，文件名并不是直接对应 Linux 当前目录下的某个文件，而是要先落到用户自己的虚拟路径里。

### 3.2 第二期解决的是“文件真的能传，而且能断点续传”

第二期主要补齐：

1. `puts`
2. `gets`
3. 上传续传
4. 下载续传
5. 大文件 `mmap` 传输路径

这一期建立的核心协议骨架，到第五期仍然在复用：

1. 上传时：
   - 客户端先发 `file_packet_t`
   - 服务端回一个 `offset`
   - 客户端从这个 `offset` 继续发剩余内容
2. 下载时：
   - 服务端先发 `file_packet_t(file_size)`
   - 客户端回传本地已完成的 `offset`
   - 服务端从这个 `offset` 继续发剩余内容

第五期分片下载不是重写了这套协议，而是在这套协议外面又包了一层“下载方案 + 分片票据 + 多线程分片”。

### 3.3 第三期解决的是“用户系统、去重存储、秒传”

第三期主要补齐：

1. 用户注册 / 登录
2. 数据库存储
3. `users`、`paths`、`files` 三张核心表
4. SHA-256 去重
5. 秒传

这一期让项目从“传文件”变成了“网盘”：

1. 用户有身份
2. 文件有归属
3. 虚拟路径和真实文件分离
4. 同内容文件只保留一份真实实体

理解到这里，你就能知道为什么第四期必须升级架构：

> 一旦有登录态、当前目录、虚拟路径、上传下载、秒传这些能力之后，单连接模型就开始成为瓶颈。

## 4. 为什么第四期是架构分水岭

第四期引入了三个真正改变项目形态的能力：

1. 控制连接和传输连接分离
2. JWT 和一次性传输票据
3. 控制连接超时踢出

如果前三期是在一个旧房子里不断加家具，那么第四期是第一次动承重墙。

### 4.1 第四期之前的核心问题

前三期本质上是“单客户端单连接”模型：

1. 客户端从登录到 `pwd/cd/ls/puts/gets` 都走同一个 `sock_fd`
2. 服务端线程池虽然存在，但工作方式是“一个线程长期服务一条连接”
3. 所有命令都在同一条连接上串行处理

这会带来两个直接问题：

1. `puts/gets` 一旦执行，控制连接就被阻塞
2. 想并发跑短命令和长命令时，协议和线程模型都会打架

### 4.2 第四期的核心改法

第四期没有在旧连接上继续堆技巧，而是直接拆角色：

1. 控制连接
   - 负责登录、注册、短命令、票据申请、下载方案协商
2. 传输连接
   - 负责真正上传和真正下载

这一步的意义非常大：

1. 控制连接生命周期长，但每次命令很短
2. 传输连接生命周期短，但每次任务很重
3. 服务端终于可以用两套完全不同的并发策略处理两种连接

### 4.3 第四期后的服务端并发模型

第四期之后，服务端不再是“所有连接都交给线程池”，而是分成两种处理方式：

1. 控制连接
   - 主线程 `epoll` 直接管理
   - 控制连接超时由时间轮处理
2. 传输连接
   - 主线程只负责 `accept` 和分流
   - 真正上传下载交给线程池

这个变化是理解整个 V5 的前提。

如果你脑子里还是“一个工作线程长期服务一个客户端”的旧模型，那么第五期多点下载一定会看乱。

## 5. 第四期必须重点看懂的 5 个对象

### 5.1 `ClientState`

文件位置：

- `include/client_state.h`

这是客户端的统一状态对象，里面最重要的字段有：

1. `ctrl_fd`
2. `logged_in`
3. `user_id`
4. `token`
5. `current_path`
6. `server_ip`
7. `server_port`
8. `client_file_dir`

它的意义是：

> 客户端主线程和后台传输线程，不再各自维护一套零散状态，而是统一从 `ClientState` 读取控制连接相关信息。

### 5.2 `ClientContext`

文件位置：

- `include/protocol.h`

这是服务端“单条连接的会话上下文”，主要保存：

1. `user_id`
2. `current_path`
3. `current_dir_id`

要特别注意：

1. 它不是“全局用户状态”
2. 它是“某一条连接在服务端内存中的状态”
3. 控制连接和传输连接都可以临时拥有自己的 `ClientContext`

控制连接上的 `ClientContext` 是长期维护的。  
传输连接上的 `ClientContext` 是票据校验通过后临时恢复出来的。

### 5.3 JWT

文件位置：

- `src/common/jwt_utils.c`
- `src/server/security/auth.c`

当前 JWT 的主要作用不是做复杂分布式认证，而是：

1. 登录成功后给客户端一份身份凭证
2. 为一次性传输票据提供负载编解码工具

要理解清楚一点：

1. 登录 JWT 是“长期登录态的一部分”
2. 第四期真正用于上传下载认证的，不是直接复用登录 JWT
3. 传输连接最终依赖的是一次性传输票据

### 5.4 一次性传输票据

文件位置：

- `src/server/security/transfer_ticket.c`
- `src/server/core/session.c`

这是第四期最关键的安全对象之一。

它解决的问题是：

> 新开的传输连接，怎么证明自己是谁、要干什么、能连哪台服务器、能访问哪个文件、能访问哪个区间。

一张票据里绑定的信息包括：

1. `user_id`
2. `cmd_type`
3. `full_path`
4. `range_start`
5. `range_end`
6. `source_ip`
7. `source_port`
8. `ticket_id`
9. 过期时间

服务端对票据的处理流程是：

1. 签发时写入 JWT 负载
2. 同时登记到内存票据表
3. 使用时先校验 JWT
4. 再检查内存票据表
5. 成功后立刻消费，不能再次使用

### 5.5 时间轮

文件位置：

- `src/server/net/time_wheel.c`
- `src/server/core/server.c`

时间轮只服务控制连接，不服务传输连接。

它的职责是：

1. 新控制连接注册时挂到时间轮
2. 每处理完一条控制命令，就刷新超时位置
3. 到期时关闭控制连接

理解时间轮时，不要把它想成“定时器数组的小技巧”，而要把它想成：

> 服务端主线程用来大规模管理控制连接空闲状态的一套基础设施。

## 6. 第四期的关键代码阅读顺序

如果你现在准备真正读第四期代码，建议按下面顺序读：

1. `src/client/client.c`
   - 看客户端是怎么建立控制连接、进入登录菜单、进入命令循环的
2. `src/client/client_command_handle.c`
   - 看命令是怎么分类到登录、短命令、`puts`、`gets` 的
3. `src/server/core/server.c`
   - 看服务端如何区分控制连接和传输连接
4. `src/server/core/session.c`
   - 看控制命令如何分发，看传输连接如何校验票据并恢复上下文
5. `src/server/security/transfer_ticket.c`
   - 看票据的签发和消费
6. `src/server/file/file_transfer.c`
   - 看真正上传和下载

这条顺序的好处是：

1. 先看入口
2. 再看分流
3. 再看安全校验
4. 最后看真正业务

如果一上来就扎进 `file_transfer.c`，通常会被细节淹没。

## 7. 第五期在第四期基础上又做了什么

第五期只增强了一个命令：

- `gets`

但这一期实际上是整个项目目前最复杂的一期，因为它把“单线程下载一个文件”扩展成了：

> 控制连接申请下载方案 -> 为每个分片申请区间票据 -> 下载管理线程组织整轮下载 -> 多个分片线程并发下载 -> 合并最终文件 -> 支持本地恢复

### 7.1 第五期没有做什么

先记住第五期没有做的事情，这样你不会把实现想复杂：

1. 没有做多点上传
2. 没有做 P2P
3. 没有做服务器之间自动同步
4. 没有做块级分布式存储
5. 没有做自动重连

第五期采用的是最适合当前学习项目的简化模型：

1. 每台可用数据源服务器都持有完整文件
2. 客户端只负责把不同区间分配给不同服务器

### 7.2 第五期真正新增的核心对象

第五期最重要的新对象有三个：

1. `file_sources`
   - 数据库第四张表
   - 记录哪台服务器拥有哪份真实文件
2. `multi_gets_plan_packet_t`
   - 控制服务器返回给客户端的下载方案包
3. `.multipart`
   - 客户端本地分片任务目录
   - 保存 `meta.ini` 和 `part_i`

这三个对象合起来，才构成了完整的多点下载系统。

## 8. 第五期多点下载一定要先理解的 3 个前提

### 8.1 前提一：控制服务器和数据源服务器可以是同一台，也可以不是同一台

当前模型里：

1. 客户端先登录某台控制服务器
2. 控制服务器告诉客户端有哪些可用数据源
3. 客户端再去连接这些数据源下载分片

在单机测试时，这两个角色可以是同一台服务端。  
在双实例联调时，它们可以是不同实例。

### 8.2 前提二：数据源服务器登记的是“完整文件”

第五期不是块系统。

`file_sources` 里的含义是：

> 某台服务器拥有这份真实文件的完整实体

不是：

> 某台服务器只拥有第 0 到第 100MB

所以客户端之所以能并发下载，是因为：

1. 同一个完整文件存在于多个服务器
2. 客户端让不同服务器各发不同区间

### 8.3 前提三：分片恢复依赖本地文件，不依赖数据库

第五期断点恢复不是靠数据库记住客户端下载进度，而是靠客户端本地的：

1. `.multipart/<file_hash>/meta.ini`
2. `.multipart/<file_hash>/part_0`
3. `.multipart/<file_hash>/part_1`
4. ...

这让实现保持简单，也更容易调试。

## 9. 第五期多点下载完整流程

下面这条链路必须读熟，因为它是当前项目最核心的学习内容。

### 9.1 第一阶段：主线程申请下载方案

代码主线：

1. `process_command()`
2. `handle_gets_command()`
3. `request_multi_gets_plan()`
4. 服务端 `handle_multi_gets_plan()`

这一阶段做的事情是：

1. 客户端告诉控制服务器：我要下载哪个文件
2. 控制服务器根据当前用户和当前虚拟路径找到完整逻辑路径
3. 控制服务器查 `paths`
4. 控制服务器查 `files`
5. 控制服务器查 `file_sources`
6. 控制服务器返回：
   - 文件名
   - 文件总大小
   - 文件 hash
   - 可用数据源列表

这一阶段不传任何文件内容，只做协商。

### 9.2 第二阶段：客户端准备本地任务目录

代码主线：

1. `multipart_task_prepare()`
2. `multipart_task_sync_progress()`

这里做的事情是：

1. 创建 `.multipart/<file_hash>/`
2. 创建或加载 `meta.ini`
3. 按数据源数量平均切分分片区间
4. 为每个分片确定：
   - `range_start`
   - `range_end`
   - `source_ip`
   - `source_port`
   - `part_file_path`
5. 如果本地已经存在旧任务，就尝试恢复
6. 根据现有 `part_i` 真实大小刷新 `finished_bytes`

也就是说，第五期下载不是一上来就开线程，而是先把本地恢复现场准备好。

### 9.3 第三阶段：主线程为每个未完成分片申请区间票据

代码主线：

1. `request_gets_range_ticket()`
2. 服务端 `handle_gets_range_ticket_prepare()`

这一阶段的职责是：

1. 客户端只为“还没完成”的分片申请票据
2. 每个分片单独申请一张票据
3. 票据绑定：
   - 文件
   - 用户
   - 完整虚拟路径
   - 区间范围
   - 指定数据源服务器

这样做的好处是：

1. 权限边界清楚
2. 一个分片的票据不能拿去下载别的区间
3. 一个服务器的票据不能拿去连别的服务器

### 9.4 第四阶段：启动下载管理线程

代码主线：

1. `pthread_create(gets_manager_thread_func)`

主线程在这一刻就退出本次 `gets` 处理，立即返回命令循环。

这意味着：

1. 多点下载不会阻塞客户端继续输入其它短命令
2. 真正的下载组织工作交给后台管理线程

### 9.5 第五阶段：下载管理线程启动多个分片线程

代码主线：

1. `gets_manager_thread_func()`
2. `pthread_create(gets_part_thread_func)`

管理线程要做的事是：

1. 只为本轮未完成分片创建线程
2. 等待所有分片线程结束
3. 再统一做收尾判断

这里的设计很关键：

1. 分片线程只负责联网收数据
2. 管理线程负责整轮任务的总控

所以“合并最终文件”“决定是否清理任务目录”这些动作都不在分片线程里做。

### 9.6 第六阶段：单个分片线程执行真正下载

代码主线：

1. `gets_part_thread_func()`
2. `run_gets_part_transfer()`
3. 服务端 `handle_transfer_request()`
4. 服务端 `handle_gets_range()`

单个分片线程的步骤是：

1. 建立独立传输连接
2. 发送 `conn_init_packet(CONN_ROLE_TRANSFER)`
3. 发送本分片对应的区间票据
4. 服务端校验并消费票据
5. 服务端恢复：
   - 用户
   - 文件完整路径
   - 区间范围
   - 指定数据源地址
6. 服务端先发 `file_packet_t(file_size = 本分片长度)`
7. 客户端检查本地 `part_i` 已完成多少字节
8. 客户端回传 `offset`
9. 服务端从这个 `offset` 对应的位置继续发送剩余区间
10. 客户端写入 `part_i`

这一段最容易和旧版整文件下载搞混。要记住：

> 第五期分片下载内部，仍然复用了第二期的“服务端先发 file_size，客户端回 offset，再继续发送剩余内容”的断点续传骨架。

### 9.7 第七阶段：管理线程统一判断结果

代码主线：

1. `multipart_task_sync_progress()`
2. `all_parts_finished()`
3. `merge_part_files()`
4. `get_file_sha256()`
5. `multipart_task_cleanup()`

管理线程结束时会进入三种结果之一：

1. 仍有分片未完成
   - 保留 `.multipart`
   - 下次再次 `gets` 时继续恢复
2. 所有分片完成，但合并失败或最终 hash 不匹配
   - 保留 `.multipart`
   - 方便排查
3. 所有分片完成，合并成功，最终 hash 匹配
   - 删除 `meta.ini`
   - 删除各个 `part_i`
   - 删除任务目录

这一步一定要看清楚，因为这正是第五期“可恢复”能力的核心。

## 10. 第五期多点下载为什么这样设计

### 10.1 为什么先申请下载方案，而不是直接让客户端连多个服务器试探

因为当前项目已经有控制连接和登录态，所以让控制服务器统一做协商最合理。

这样做的好处：

1. 客户端不需要自己发现服务器
2. 文件权限校验集中在控制服务器
3. 哪些服务器有文件，也集中从 `file_sources` 查询

### 10.2 为什么每个分片都单独申请票据

因为第五期不是“拿一张大票据，客户端随便切分”。

每张区间票据都绑定：

1. 区间
2. 文件
3. 用户
4. 目标数据源服务器

这样做更安全，也更容易让服务端保持逻辑简单。

### 10.3 为什么分片不直接写最终文件

因为直接写最终文件会让问题立刻复杂起来：

1. 多线程同时写一个最终文件要处理并发定位
2. 中断恢复时不好判断哪些字节可信
3. 合并和校验过程会被迫变得隐式

当前实现选择：

1. 每个分片写自己的 `part_i`
2. 所有分片完成后再合并

这是最适合学习项目的实现。

### 10.4 为什么 `.multipart` 很重要

`.multipart` 不是一个临时小目录，而是第五期的核心状态载体。

它让项目具备了：

1. 客户端退出后还能继续下载
2. 分片线程中断后还能继续下载
3. 合并失败后还能保留现场

如果没有 `.multipart`，第五期就只是一版“会并发下载但不能恢复”的功能。

## 11. 当前第五期实现的边界

学习时必须知道当前实现做到哪里，没做到哪里。

### 11.1 当前已经做到的

1. 控制连接和传输连接完全分离
2. 传输连接使用一次性票据
3. 控制连接时间轮超时踢出
4. `gets` 多点下载方案协商
5. 每个分片独立票据
6. 多分片并发下载
7. 分片断点续传
8. 本地 `.multipart` 恢复
9. 合并后整文件 hash 校验

### 11.2 当前还没有做的

1. 多点上传
2. 服务器之间自动复制真实文件
3. 动态负载均衡切分策略
4. P2P 节点发现
5. 传输失败后的自动重试
6. 控制连接自动重连

这些都不是 bug，而是当前第五期第一版实现的边界。

## 12. 读第五期代码的推荐顺序

如果你要深入学习多点下载，建议按下面顺序看：

1. `src/client/client_command_handle.c`
   - 看 `gets` 是怎样从普通命令分流出去的
2. `src/client/client_gets.c`
   - 看主线程、管理线程、分片线程三段职责
3. `src/client/multipart_meta.c`
   - 看 `.multipart` 是如何创建、恢复、清理的
4. `src/server/core/session.c`
   - 看下载方案申请、区间票据申请、传输票据校验
5. `src/server/security/transfer_ticket.c`
   - 看票据为什么能做到“区间绑定 + 一次性消费”
6. `src/server/file/file_transfer.c`
   - 看 `handle_gets_common()` 如何同时支持整文件和区间下载
7. `src/server/data/dao_file_source.c`

这个顺序对应的是：

1. 先看调度
2. 再看客户端组织
3. 再看恢复
4. 再看服务端授权
5. 最后看真正发送数据

## 13. 学习第四期和第五期时最容易混淆的点

### 13.1 `ClientState` 和 `ClientContext` 不是同一个东西

1. `ClientState`
   - 在客户端
   - 保存控制连接 fd、登录状态、当前路径、token 等
2. `ClientContext`
   - 在服务端
   - 保存一条连接对应的用户 id、当前路径、当前目录 id

### 13.2 登录 JWT 和一次性传输票据不是同一个东西

1. 登录 JWT
   - 长期登录态的一部分
2. 传输票据
   - 一次性
   - 绑定命令、路径、区间、数据源

### 13.3 `gets` 和 `gets_range` 不是两个用户命令

对用户来说，只有：

- `gets 文件名`

`GETS_RANGE` 是第五期在控制连接内部新增的协商命令，用来给每个分片申请票据。

### 13.4 `file_sources` 不是“文件块表”

它记录的是：

> 哪台服务器拥有这份完整真实文件

不是：

> 哪台服务器拥有第几块

### 13.5 分片线程不会直接决定任务是否成功

分片线程只负责：

1. 建传输连接
2. 下载自己的区间
3. 写自己的 `part_i`

真正决定“这轮多点下载是否成功”的，是下载管理线程。

## 14. 调试第五期时建议重点观察什么

### 14.1 先看控制阶段有没有走通

如果多点下载失败，先不要直接怀疑传输线程，先看：

1. `request_multi_gets_plan()` 是否成功
2. 服务端是否返回了正确的 `source_count`
3. `request_gets_range_ticket()` 是否都成功

如果这一步没走通，后面的分片线程根本不会正常启动。

### 14.2 再看 `.multipart`

调试多点下载时，`.multipart` 是最直接的观察窗口。

重点看：

1. 有没有创建 `<file_hash>/meta.ini`
2. `part_i` 是否生成
3. `part_i` 大小是否增长
4. `finished_bytes` 是否和 `part_i` 大小一致

### 14.3 最后再看服务端区间发送

如果客户端票据和本地任务目录都正常，再看服务端：

1. 区间是否合法
2. `offset` 是否被错误重置为 0
3. 当前数据源服务器是否真的持有该真实文件
4. 是否走到了 `sendfile` 或 `mmap` 发送路径

## 15. 最后给学习者的建议

学习这个项目时，不要把注意力平均分给所有文件。

最有效的方式是：

1. 先看一条完整链路
2. 再看这条链路上的对象状态
3. 最后再回头看抽象设计

对当前 V5 来说，最值得你反复跟的两条链路只有两条：

1. 第四期 `puts`
   - 看控制连接如何签发票据
   - 看传输连接如何真正上传
   - 看秒传和续传如何在当前结构下共存
2. 第五期 `gets`
   - 看控制服务器如何协商方案
   - 看客户端如何组织分片线程
   - 看 `.multipart` 如何承担恢复功能
   - 看服务端如何在旧协议骨架上支持区间下载

如果你能真正把这两条链路走顺，这个项目最难的部分你就已经掌握了。

## 16. 一句话总结

WindCloud_V5 的核心，不是“又多了几个命令”，而是：

> 在虚拟目录、去重真实存储和登录态的基础上，用控制连接和传输连接分离、一次性票据、时间轮、多点下载协商和 `.multipart` 恢复机制，把一个教学型网盘项目推进到了完整的第五期架构。
